# 1.3 Abstract Classes and Interfaces

Both abstract classes and interfaces let you declare *what* without committing to *how*. The distinction is not "interfaces are better" or "use whichever feels right" — they answer different design questions. An abstract class is a partially-built class that descendants finish. An interface is a contract any class can sign, regardless of where it lives in the type hierarchy. Picking the right one is mostly about whether you're modeling *identity* (what something **is**) or *capability* (what something **can do**).

---

## Abstract classes

An `abstract` class can declare methods without bodies (abstract methods) and cannot itself be instantiated. Subclasses must implement every abstract method, or they too must be declared `abstract`.

```java
public abstract class Shape {
    private final String label;

    protected Shape(String label) {
        this.label = label;
    }

    public final String label() {
        return label;
    }

    public abstract double area();   // no body — subclass must provide one

    public String describe() {       // concrete method built on the abstract one
        return label + " has area " + area();
    }
}

public class Circle extends Shape {
    private final double radius;

    public Circle(double radius) {
        super("circle");
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}
```

What an abstract class gives you that an interface still can't:

- **State.** Instance fields, with full access control.
- **Constructors.** They can't be called via `new Shape(...)`, but subclass constructors call them with `super(...)` — useful for enforcing invariants that every subclass must satisfy.
- **Non-public members.** `protected` and package-private methods and fields are available to subclasses but hidden from outside callers.

What it costs you:

- **Single inheritance.** A subclass can only extend one class. If `Shape` is abstract and `Drawable` is also an abstract class, a `Circle` cannot be both.
- **Tight coupling to the hierarchy.** Adding a new abstract method later breaks every existing subclass. Adding a concrete method on the base class can silently change subclass behavior (the fragile base class problem, 1.4).

Use an abstract class when:

- Subclasses genuinely share state or partial behavior you don't want to duplicate.
- There's a meaningful is-a relationship you want to enforce (`Circle is-a Shape`).
- You want to constrain subclasses by funneling them through a common constructor.

## Interfaces

An `interface` declares a contract. Any class can implement any number of interfaces, regardless of what it `extends`. Interfaces are how Java models capability across unrelated type hierarchies.

```java
public interface Drawable {
    void drawOn(Canvas c);
}

public interface Resizable {
    void resize(double factor);
}

public class Circle extends Shape implements Drawable, Resizable {
    // ...
    @Override public void drawOn(Canvas c) { /* ... */ }
    @Override public void resize(double f) { /* ... */ }
}
```

A few things that trip people up:

- **All members are implicitly `public`.** You can write `public abstract` on a method or `public static final` on a field, but the keywords are redundant. Conversely, you cannot make an interface method package-private — if you want a "package-internal helper," it doesn't belong on the interface.
- **No instance state.** Interfaces can declare `public static final` constants, but they cannot hold instance fields. A class can implement the interface and store whatever state it needs; the interface itself remembers nothing.
- **No constructors.** There is no `super(...)` call to an interface. You can't enforce "every implementer must initialize these fields" the way an abstract class can.

Use an interface when:

- The capability is orthogonal to the class hierarchy (`Comparable`, `Iterable`, `AutoCloseable` — types implementing these have nothing else in common).
- You want multiple implementations from unrelated classes.
- You want to be able to mock the type easily in tests (1.3's DIY is a good example; Module 2 will lean on this heavily).

### Capability vs. identity, restated

A useful mental check: would it be reasonable for two completely unrelated classes to satisfy this type? If yes — interface. If the type only makes sense as a specialization of one specific concept — abstract class is on the table.

`Shape` is identity: a `Circle` *is a* `Shape`. Probably an abstract class (or a sealed interface, 1.5).
`Comparable` is capability: a `String`, a `BigDecimal`, and an `Instant` are all `Comparable` and have nothing else in common. Interface, obviously.

## Default and static methods on interfaces

Before Java 8, adding a method to an interface broke every existing implementation. Java 8 added `default` methods to fix that: a method on an interface that comes with a body, which implementers inherit unless they override it.

```java
public interface Repository<T, ID> {
    Optional<T> findById(ID id);
    T save(T entity);

    default boolean existsById(ID id) {
        return findById(id).isPresent();
    }

    default T findOrThrow(ID id) {
        return findById(id).orElseThrow(
            () -> new NoSuchElementException("not found: " + id));
    }
}
```

The two abstract methods (`findById`, `save`) are the genuine contract. The two `default` methods are *conveniences built on top* — every implementer gets them for free, and any implementer that has a faster way (e.g., a SQL `EXISTS` query) can override.

Static methods on interfaces are also legal since Java 8. They're useful for factory methods (`List.of(...)`, `Stream.of(...)`) and pure utility helpers. They are not inherited by implementers — `MyList.of(...)` does not exist just because `MyList implements List`.

Two related additions worth knowing exist but are used less often:

- **`private` methods on interfaces** (Java 9+) — used to share code between `default` methods without exposing it to implementers. Pure encapsulation tool.

### The diamond problem

If a class implements two interfaces, and both provide a `default` method with the same signature, the compiler refuses to guess.

```java
interface A { default String greet() { return "hi from A"; } }
interface B { default String greet() { return "hi from B"; } }

class C implements A, B {
    // won't compile until you resolve the conflict explicitly
    @Override
    public String greet() {
        return A.super.greet();   // pick one, or compose, or write your own
    }
}
```

Note the `A.super.greet()` syntax — that's how you call a specific interface's default implementation from a class that inherits multiple. Java's design here is conservative on purpose: rather than impose a resolution rule (depth-first? declaration order?), the language forces you to make the choice explicit. The diamond problem is solved by *requiring* a tiebreaker.

A subtler precedence rule: **classes win over interfaces.** If a superclass already provides a concrete `greet()`, it overrides any `default greet()` from an implemented interface, with no conflict and no warning. This is occasionally surprising; if you wanted the interface's default, the superclass's method has already taken its place.

## Marker interfaces

A *marker interface* is an interface with no methods. Its only purpose is to tag a type so other code can check for it at runtime.

```java
public interface Cacheable {}   // no methods

if (entity instanceof Cacheable) {
    cache.put(key, entity);
}
```

Historical examples: `java.io.Serializable`, `java.lang.Cloneable`, `java.util.RandomAccess`. They predate annotations — today, a runtime annotation (`@Cacheable`, see Module 8) is usually the better tool, because annotations can carry parameters and don't pollute the type hierarchy. Marker interfaces are still occasionally appropriate when you want compile-time enforcement — a method signature `void store(Cacheable c)` rejects non-cacheable arguments at compile time, which an annotation can't do.

## Functional interfaces (preview)

A *functional interface* is any interface with exactly one abstract method. Default and static methods don't count.

```java
@FunctionalInterface
public interface Validator<T> {
    boolean isValid(T value);
}
```

The single-abstract-method shape means an instance can be supplied as a lambda or method reference:

```java
Validator<String> nonEmpty = s -> !s.isEmpty();
Validator<String> nonEmpty2 = String::isEmpty;   // method reference (negated separately)
```

The `@FunctionalInterface` annotation is optional but recommended: it makes the compiler reject the interface if anyone later adds a second abstract method, which would silently break every lambda that targets it. Module 5 covers lambdas, the standard `Function` / `Predicate` / `Consumer` / `Supplier` interfaces, and method references in depth. For now, just recognize the shape.

## Picking between them — a decision sketch

| Question | If yes, lean toward |
|---|---|
| Do implementers need to share instance state or partial behavior? | Abstract class |
| Should implementers be forced through a common constructor for invariants? | Abstract class |
| Will unrelated classes (across hierarchies) need to satisfy this type? | Interface |
| Will I want lambdas to satisfy this type? | Interface (functional) |
| Will I want to add new default conveniences over time without breaking implementers? | Interface (with `default`) |
| Do I need a controlled, exhaustive set of subtypes? | Sealed class or sealed interface (1.5) |

When in doubt, start with an interface. You can always add an abstract base class later that implements the interface and provides shared scaffolding (`AbstractList` and `List`, `AbstractMap` and `Map`, `AbstractSet` and `Set` — the standard library does exactly this).

## DIY Exercise

Model a notification system using an abstract class and two interfaces.

- An abstract class `Notification` with a `String message` field (set via constructor) and a `String message()` accessor. Add an abstract method `String channel()` that returns where the notification is sent (e.g., `"email"`, `"sms"`). Add a concrete `String summary()` method that combines both: `"[email] password reset"`.
- An interface `Retryable` with an abstract `int maxAttempts()` and a `default` method `boolean shouldRetry(int attemptsSoFar)` implemented in terms of `maxAttempts()`.
- An interface `Loggable` with an abstract `void logTo(String destination)` and a `default` method `void logToConsole()` that calls `logTo("stdout")`.
- Two concrete classes: `EmailNotification` (extends `Notification`, implements `Loggable`) and `SmsNotification` (extends `Notification`, implements `Retryable` and `Loggable`).
- A `main` that creates one of each, calls `summary()` on both, exercises `shouldRetry` on the SMS one, and calls `logToConsole()` on both via the `Loggable` reference type.

Things to think about while you write it:

- `SmsNotification` implements both `Retryable` and `Loggable`. What does that mean for the call site — can you assign it to a `Retryable` variable? A `Loggable` variable? Both?
- If you added a `default void logToConsole()` on a second interface and `SmsNotification` implemented that too, what would the compiler say? Try it.
- Could `Notification` be an interface instead of an abstract class? What would you lose?
- Should `shouldRetry` be `default` or abstract? What changes if you make it abstract?
