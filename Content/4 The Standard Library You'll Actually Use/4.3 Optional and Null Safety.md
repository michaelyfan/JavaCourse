# 4.3 Optional and Null Safety

`null` is Java's original sin — Tony Hoare famously called it his "billion-dollar mistake." A reference can mean *a thing* or *nothing*, and the type system does not distinguish. Every method that might return "nothing" hands you a value you have to *remember* might be `null`, and forgetting is `NullPointerException` — at runtime, in production, often far from the line that returned the `null`.

`Optional<T>` (Java 8) is the standard-library answer for one specific slice of that problem: **a method that may not have a value to return**. It makes "this might be absent" part of the *return type*, so the compiler — and the caller's eyes — cannot miss it. Used well, `Optional` is one of the highest-leverage idioms in modern Java. Used as a general null-replacement, it is busywork that makes the code worse. This submodule is mostly about telling those apart.

A note on scope: this is being built ahead of 4.1 (Strings, Numbers, Dates) and 4.2 (I/O), because `Optional` is largely standalone — and because Module 5 (Streams) uses it constantly. Stream terminals like `findFirst`, `findAny`, and `reduce` all return `Optional`. Knowing it now means 5.2 reads cleanly.

## What `Optional<T>` is

`Optional<T>` is a *container* — a thin immutable wrapper around either one `T` or no value at all. The two states are `Optional.of(value)` / `Optional.empty()`:

```java
Optional<String> present = Optional.of("Ada");
Optional<String> absent  = Optional.empty();
Optional<String> maybe   = Optional.ofNullable(possiblyNull);   // empty if null, of(x) otherwise
```

You ask the container what to do about the absence rather than reaching in and finding out:

```java
String name = maybe.orElse("anonymous");
maybe.ifPresent(n -> log.info("hello {}", n));
int len = maybe.map(String::length).orElse(0);
```

That is the whole shape of the API: you *transform inside* the container (`map`, `flatMap`, `filter`) and *exit* it at one well-chosen place (`orElse`, `orElseGet`, `orElseThrow`, `ifPresent`).

### `Optional.of` vs. `Optional.ofNullable`

A common confusion. They are different by design:

- `Optional.of(x)` — `x` is expected to be non-null. If it *is* null, this throws `NullPointerException` immediately. Use it when you have a value in hand and want to assert that fact.
- `Optional.ofNullable(x)` — `x` might be null; produce `empty()` in that case, `of(x)` otherwise. Use it at the *boundary* where a legacy API hands you a possibly-null reference and you are wrapping it.

```java
Optional.of("Ada");          // ok
Optional.of(null);            // NullPointerException — by design, surfaces the bug
Optional.ofNullable(maybe);   // safe wrapper for an unknown input
```

`of` is louder. Prefer it whenever you know the value is present — letting `Optional.of(null)` throw is a feature: it catches a latent invariant violation right at the wrap site rather than letting an empty `Optional` propagate.

## The two halves of the API

`Optional` has a *transform* side and an *exit* side. Knowing which is which is most of the skill.

### Transform inside: `map`, `flatMap`, `filter`

These take an `Optional<T>` and return a new `Optional<R>` — never unwrap. If the source is empty, the result is empty; the lambda never runs.

```java
Optional<String> name = Optional.of("Ada Lovelace");

Optional<Integer> length = name.map(String::length);            // Optional[12]
Optional<String> upper   = name.map(String::toUpperCase);       // Optional[ADA LOVELACE]
Optional<String> short_  = name.filter(s -> s.length() < 5);    // Optional.empty()
```

`map` is for a function `T -> R` where `R` is a plain value. `flatMap` is for a function `T -> Optional<R>` — you use it when the *step itself* might be absent, to avoid an `Optional<Optional<R>>`:

```java
Optional<User> user = findUser(id);

// findManager returns Optional<User>; map would give Optional<Optional<User>>
Optional<User> manager = user.flatMap(this::findManager);

// each step in a chain returning Optional uses flatMap; the last one (returning a plain value) uses map
Optional<String> managerEmail = findUser(id)
    .flatMap(this::findManager)
    .map(User::email);
```

That is the same `flatMap` rule as in any other monadic container (and it will reappear in Streams in 5.2 with the same shape): `map` when the step returns a plain value, `flatMap` when the step returns the container.

### Exit at the end: `orElse`, `orElseGet`, `orElseThrow`, `ifPresent`

These leave the `Optional` world — they return a `T` (with a fallback), or perform a side-effect, or throw:

```java
String s1 = maybe.orElse("default");                            // always evaluates "default"
String s2 = maybe.orElseGet(() -> expensiveDefault());           // lazy — only if empty
String s3 = maybe.orElseThrow();                                 // NoSuchElementException if empty
String s4 = maybe.orElseThrow(() -> new UserNotFound(id));       // custom exception

maybe.ifPresent(value -> send(value));                           // side effect, only if present
maybe.ifPresentOrElse(this::send, this::logMissing);             // Java 9+
```

### `orElse` vs. `orElseGet` — a real performance trap

These look interchangeable. They are not.

```java
String name = lookup(id).orElse(loadDefaultFromDatabase());      // ALWAYS calls loadDefaultFromDatabase()
String name = lookup(id).orElseGet(() -> loadDefaultFromDatabase()); // calls it only when empty
```

`orElse` takes a *value*. The argument is evaluated **eagerly**, before `orElse` is even called — that is just how method arguments work in Java. So `lookup(id).orElse(loadDefaultFromDatabase())` performs the database hit every single time, including the (probably common) case where `lookup` already returned a value, and then *throws the result away*. If the fallback is anything more than a cheap literal or a constant, this is a real performance bug.

`orElseGet` takes a `Supplier<T>` — a lambda — and calls it only when the `Optional` is empty. The fallback is lazy.

> Rule of thumb: `orElse` only for a constant or trivial literal (`""`, `0`, `List.of()`). For anything that does work — a method call, an object construction, a default that allocates — use `orElseGet`.

A small confusion worth pre-empting: `orElse` is fine for `null` literals you would never bother making lazy, and for *real* constants. The problem is method calls that *look* cheap. `orElse(new ArrayList<>())` allocates a fresh `ArrayList` on every call, even when unused — surprisingly costly in a hot path. Reach for `orElseGet(ArrayList::new)`.

## `orElseThrow` and the `get` anti-pattern

`Optional` has a method called `get()`. It returns the value if present, throws `NoSuchElementException` if empty. It looks like the obvious way to "just get the thing out":

```java
Optional<User> user = findUser(id);
if (user.isPresent()) {
    return user.get().email();
}
```

This is the **`isPresent`/`get` anti-pattern**. It is a transliteration of a null check, and it gives up everything `Optional` was meant to give you — the structural assurance that you handled the absent case. The two halves are not connected by the type system; nothing stops you from `.get()` *without* `.isPresent()`, and you have just reinvented the `NullPointerException` you were trying to avoid (now spelled `NoSuchElementException`).

Two better forms:

```java
// chain
return findUser(id).map(User::email).orElse(null);

// or, if absence is truly an error here:
return findUser(id).orElseThrow(() -> new UserNotFound(id)).email();
```

`orElseThrow()` (no argument) — which throws `NoSuchElementException` — is the *only* reasonable use of "unwrap or fail", and even it should be rare; a typed exception via the lambda form is almost always more useful.

> The phrase "I needed to get the value out, so I called `.get()`" is a red flag. The shape of `Optional` is that you compose *inside* and exit *once*, intentionally. If you find yourself calling `.get()`, you can almost always restructure to `map` / `flatMap` / `orElseThrow` / `ifPresent` and delete the temporary.

(Java 10 renamed `get()` to `orElseThrow()`, leaving `get()` as a soft-deprecated alias. The rename itself is the point: there is no operation called "just get it".)

## Where `Optional` belongs — and where it does not

This is the most-misused class in the standard library. Brian Goetz, the Java language architect, has been explicit: `Optional` was designed for **one** purpose — a method return type expressing "no value." Anything else is off-label.

### Use `Optional<T>` as a **return type** when a method may have no result

This is the entire intended use:

```java
public Optional<User> findById(long id) { ... }
public Optional<String> firstHeader(String name) { ... }
```

The caller cannot ignore the absence: the type forces them to either unwrap with an explicit fallback or carry the `Optional` further. That is the whole win.

A `null` return *might* be handled. An `Optional` return *must* be acknowledged — the type system will not let you treat it as a `User`.

### Do **not** use `Optional<T>` as a field

```java
class User {
    private Optional<Address> address;     // wrong
}
```

Reasons:

- `Optional` is not `Serializable`. Marking a class `Serializable` and trying to put an `Optional` field on it fails — a small thing, but a sign you are misusing the type.
- It adds an allocation per field per instance, with no win — a `null` field already expresses "may be absent," and the public *getter* can wrap it: `public Optional<Address> address() { return Optional.ofNullable(address); }`.
- It is a cultural marker: anyone reading the class sees `Optional<Address> address` and asks "is this ever null?" — `Optional` itself can be null. Now you have *two* absent states.

The field is `null`able; the *getter* returns `Optional`. That is the idiom.

### Do **not** use `Optional<T>` as a method parameter

```java
public void update(User u, Optional<String> note) { ... }     // wrong
```

A caller now has three ways to pass "no note": `null`, `Optional.empty()`, or just not having an `Optional` to hand and constructing one to satisfy the signature. None of them is clearer than two overloads:

```java
public void update(User u) { ... }
public void update(User u, String note) { ... }
```

…or accepting `null` with documentation, or splitting the method. The cure is worse than the disease.

### Do **not** use `Optional<Collection>`

```java
Optional<List<Order>> orders();    // wrong
```

A collection already has an "empty" state — `List.of()`. `Optional<List<Order>>` invents a *second* one, and now callers have to handle both "absent list" and "present-but-empty list" with no real semantic difference. Return an empty list. Same goes for `Optional<Map<...>>`, `Optional<Set<...>>`, `Optional<int[]>`.

The exception is rare: when "no list" and "an empty list" genuinely mean *different things* in the domain. They almost never do.

### Do **not** use the primitive `Optional` types unless you have a measured reason

There are also `OptionalInt`, `OptionalLong`, `OptionalDouble` — boxed-free variants. They are awkward (no `map` to a non-primitive, different API surface) and exist primarily to interoperate with primitive streams (5.2). For business code, plain `Optional<Integer>` is fine; reach for the primitive ones only if profiling has flagged the allocation.

## The chain — the form `Optional` is built for

The motivating example is a nested null-walk:

```java
String zip = "unknown";
if (user != null) {
    Address addr = user.getAddress();
    if (addr != null) {
        City city = addr.getCity();
        if (city != null) {
            String z = city.getZip();
            if (z != null) zip = z;
        }
    }
}
```

Each level adds an indent, the meaningful step is buried, and adding a level mid-chain is a noisy refactor. If every accessor in that chain returns an `Optional`, the chain collapses:

```java
String zip = findUser(id)
    .flatMap(User::address)
    .flatMap(Address::city)
    .flatMap(City::zip)
    .orElse("unknown");
```

Each `flatMap` says "step into the next container, or remain empty." A failed step *at any point* short-circuits — the rest of the chain is skipped, the final `orElse` supplies the default. The nesting is gone; the default is named once, in the only place it is needed.

This is what `Optional` is designed for. The chain form is where it earns its keep.

---

## Interop with legacy `null`-returning code

Realistically, you will keep meeting `null`-returning APIs — the standard library itself is full of them (`Map.get`, `System.getenv`, almost any older library). Two idioms:

```java
// wrap at the boundary
Optional<V> maybe = Optional.ofNullable(map.get(key));

// or use a Map method that already returns Optional-shaped behaviour
V value = map.getOrDefault(key, defaultV);
```

The discipline is to **wrap once, at the edge**. The Optional-shaped chain stays internal; nulls do not leak past the call site. When you have to *hand a value back* to a null-expecting API, exit with `orElse(null)` — explicit, deliberate, and one line.

---

## A note on what `Optional` is *not*

`Optional` is not a checked exception. It does not force the caller to do anything; it only forces them to *see* the choice. You can still call `.get()` and blow up. The compiler will not stop you. The win is conventional, not enforced — `Optional` makes the absent case *visible* and the fix *idiomatic*, and that is enough to change behaviour at scale. Treat it as a tool that pays back its cost only when used the way it was intended: as a return type, in a chain, with a deliberate exit.

## DIY Exercise

This is a refactoring exercise: take a nested null-check chain and rewrite it as an `Optional` chain.

### Layout

```
src/main/java/
  profile/
    User.java          // record User(String name, Address address)
    Address.java       // record Address(City city)
    City.java          // record City(String zip)
    Directory.java     // service: lookups + zip-resolution methods
src/test/java/
  profile/
    DirectoryTest.java
```

- `User`, `Address`, `City` are **records** (1.5) — plain data carriers.
- `Directory` is a normal class with two instance methods (described below) and an in-memory map of users for the tests to populate. No statics-only utility class here — `Directory` holds state.
- Each top-level type lives in its own file in the `profile` package.

### Tasks

1. **The records.** `User` holds a `name` and an `Address`. `Address` holds a `City`. `City` holds a `zip`. **Any field may be null in the input data** — that is the whole point of the exercise. Build a few test fixtures that exercise every combination: full chain present, address null, city null, zip null, user not in the directory at all.

2. **The ugly version first — `Directory#zipForUserNested(long id)`.** Look the user up in the map. If anything in the chain is null, return `"unknown"`. Write this *with explicit nested null checks* — no `Optional`, no early returns chained with `?:`. Indent it ugly. This is the baseline the refactor will replace.

3. **Test the ugly version.** Pin its behaviour across all fixtures from task 1 — including missing user, each null link, and the full happy path. These tests stay green through every later step.

4. **The clean version — `Directory#zipForUser(long id)`.** Rewrite as an `Optional` chain.
   - `findUser(long id)` returns `Optional<User>` (wrap the map lookup with `Optional.ofNullable`).
   - Add `Optional<Address> address()` etc. on the records, **returning `Optional` from the getter** even though the field can be null — this is the "field nullable, getter optional" idiom.
   - The full chain in `zipForUser` should be `findUser(id).flatMap(...).flatMap(...).flatMap(...).orElse("unknown")` — four lines, no `if`, no `null`.

5. **The `orElse` vs. `orElseGet` test.** Change `"unknown"` to come from a method `expensiveDefault()` that logs every call. First write it as `.orElse(expensiveDefault())`. Run the happy-path test (user present, full chain) and check the log — `expensiveDefault` is called even though its value is unused. Now switch to `.orElseGet(this::expensiveDefault)` and confirm the log entry is gone. Keep this test (asserting on call count via a counter, not log inspection).

### Things to think about

- The `findUser` lookup is a `Map.get` — a `null`-returning legacy API. Your wrapper `Optional.ofNullable(map.get(id))` does the boundary conversion. Is there ever a reason `findUser` itself would *take* an `Optional<Long>` parameter? Argue why the parameter stays a plain `long`.
- The "field nullable, getter optional" idiom: why is this preferred over `private Optional<Address> address` as a field? Name two concrete problems with the field-level `Optional`. (One of them concerns the record's auto-generated `equals` — what happens if a record component is `Optional.empty()` vs. `null` in two otherwise-equal records?)
- `map` vs. `flatMap` in your chain: every step here uses `flatMap` because every accessor returns an `Optional`. Imagine adding a final step `City::zipFormatted` that returns a plain `String` (always non-null). Would that step be `map` or `flatMap`, and why? What is the type of the chain just before the `orElse` in each case?
- One of your test fixtures had the user *not in the map at all* — a missing user. Another had the user present but with a `null` address. Both produced `"unknown"`. Is that the right semantic? In a real system, would you want those to be distinguishable — and if so, how would you encode the difference *without* throwing away the chain form? (Hint: two methods, or a `Result` type.)
- Re-read your ugly nested version with the clean chain in hand. The ugly version has one quiet bug it is easy to write — count the indent levels and look for a missing `else` branch or a misplaced default. Did you make that bug? The clean version is structurally incapable of it; explain *why* — what property of `flatMap` rules out the class of mistake?
