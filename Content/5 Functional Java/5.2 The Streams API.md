# 5.2 The Streams API

If 5.1 was the vocabulary — `Function`, `Predicate`, `Consumer`, method references — this is the sentence those words were made for. `java.util.stream` lets you describe a *pipeline* over a sequence of values: "take these orders, keep the ones over $100, group by customer, sum the totals." You write that almost verbatim in stream code, and the runtime decides how to execute it. No mutable accumulator, no off-by-one index, no `for`-loop ceremony — and, importantly, no allocation per intermediate step, because the pipeline is **lazy**: nothing happens until a terminal operation pulls.

The honest framing first: streams are not a universal replacement for loops. They are a *different way of expressing the same computation* — clearer in some shapes, worse in others. The last section of this submodule is about telling those apart. The first three are about what streams actually do.

This builds on 5.1 (every stream method takes a functional interface), 3.3 (the collections you stream from and into), 3.4 (`Comparator` for `sorted`), and 4.3 (`Optional`, which every "might find nothing" terminal returns).

---

## A stream is not a collection

The single most common confusion. A `List<T>` *holds* `T`s. A `Stream<T>` is a *recipe* for processing `T`s as they flow through. Three differences worth committing to memory:

- **A stream has no storage.** It does not hold the elements; it pulls them from a source (a `List`, an array, a file, a generator) on demand.
- **A stream is single-use.** Once a terminal operation runs, the stream is consumed — calling another operation on it throws `IllegalStateException`. To "use it again," you re-derive it from the source.
- **A stream is lazy.** Intermediate operations (`filter`, `map`, `sorted`...) build up a *plan*. Nothing executes until a terminal operation (`collect`, `forEach`, `count`, `reduce`...) demands a result.

Visually:

```java
List<String> names = List.of("Ada", "Grace", "Linus", "Edsger");

names.stream()                        // source
     .filter(n -> n.length() > 3)     // intermediate — returns a Stream, runs nothing yet
     .map(String::toUpperCase)        // intermediate — still nothing
     .sorted()                        // intermediate — still nothing
     .forEach(System.out::println);   // TERMINAL — now the whole pipeline executes
```

The `forEach` is the trigger; everything before it has been queued. The runtime then walks the source once, pushing each element through `filter`, `map`, `sorted`, and out to `println` — element by element, not stage by stage. That fused, one-pass execution is what makes the abstraction cheap.

## Sources

A stream comes from somewhere. The common ones:

```java
Stream<String> s1 = names.stream();                       // any Collection
Stream<String> s2 = Stream.of("a", "b", "c");             // literal
Stream<Integer> s3 = Arrays.stream(new Integer[] { 1, 2 });
IntStream s4       = IntStream.range(0, 100);              // 0..99
IntStream s5       = IntStream.rangeClosed(1, 100);        // 1..100
Stream<String> s6 = Files.lines(Path.of("data.txt"));     // streams lines lazily (Module 4.2)
Stream<Integer> s7 = Stream.iterate(1, x -> x * 2).limit(10);   // infinite, capped
```

Two notes:

- The **primitive streams** — `IntStream`, `LongStream`, `DoubleStream` — exist to avoid boxing. They have specialised terminal ops like `sum()`, `average()`, `max()`. Use them when working over primitives; you can promote and demote with `mapToInt`, `mapToObj`, `boxed()`.
- **Infinite streams** are useful and only safe with a bounding intermediate like `limit` or a short-circuiting terminal like `findFirst`. Without one, you have written a quietly-infinite loop.

## Intermediate operations — `map`, `filter`, `flatMap`

These shape the pipeline. Each takes a stream and returns a stream — so they chain — and each is lazy.

### `filter` — keep what passes

```java
List<User> active = users.stream()
    .filter(User::isActive)              // Predicate<User>
    .toList();
```

`filter` takes a `Predicate<T>` (5.1). Elements where the predicate returns `true` move through; the rest are dropped.

### `map` — transform one-to-one

```java
List<String> emails = users.stream()
    .map(User::email)                    // Function<User, String>
    .toList();
```

`map` takes a `Function<T, R>`. Every element in becomes exactly one element out. The output stream's element type changes (`Stream<User>` → `Stream<String>`).

### `flatMap` — transform one-to-many, then flatten

`map` is one-in-one-out. `flatMap` is one-in-*many*-out: the function returns a *stream* per element, and `flatMap` concatenates those streams into a single flat stream.

```java
List<String> allTags = posts.stream()
    .flatMap(p -> p.tags().stream())       // Function<Post, Stream<String>>
    .distinct()
    .toList();
```

If `posts.size() == 3` and each post has tags `["java"]`, `["jvm","gc"]`, `["streams","gc"]`, the resulting stream walks `"java"`, `"jvm"`, `"gc"`, `"streams"`, `"gc"` — flat, in order. `distinct()` then drops the second `"gc"`.

This is the exact same shape rule as `Optional.flatMap` from 4.3: if the step itself returns the container (`Optional` there, `Stream` here), you `flatMap`; if it returns a plain value, you `map`. Use `map(p -> p.tags())` and you get a `Stream<List<String>>` — almost never what you want.

### `sorted` and `distinct`

```java
.sorted()                                 // requires T : Comparable (3.4)
.sorted(Comparator.comparingInt(User::age).reversed())
.distinct()                               // uses equals/hashCode (3.4)
```

`sorted` and `distinct` are **stateful** intermediate operations — they have to hold every element seen so far. That has two consequences:

- They cannot start producing output until they have read everything (sort) or have built up the seen-set (distinct).
- They break the elegant one-element-at-a-time pipelining. The runtime still executes the whole thing efficiently, but a `sorted` in the middle of a pipeline does buffer.

Use them when the semantics require them, not by default.

### `peek` is for debugging, not for side effects

```java
.peek(x -> log.debug("after filter: {}", x))     // ok for tracing
.peek(x -> sharedList.add(x))                    // wrong — meaningful side effect
```

`peek` lets you observe each element passing a stage. It is fine for tracing while you debug; it is not a hook for doing real work. Streams are allowed to skip `peek`-only stages entirely (the runtime sees the side-effect-free contract and optimises). If you need a side effect, the terminal `forEach` is honest about that intent.

## Terminal operations — what actually runs the pipeline

Until a terminal op fires, none of the intermediates have done anything. The terminals fall into a few groups:

### Collect into a structure — `collect`, `toList`

```java
List<String> names = stream.toList();                                  // Java 16+: unmodifiable list
List<String> names = stream.collect(Collectors.toList());               // older: ArrayList-backed
Set<String>  uniq  = stream.collect(Collectors.toSet());
Map<Long, String> byId = stream.collect(Collectors.toMap(User::id, User::name));
```

`toList()` (the shortcut introduced in Java 16) returns an **unmodifiable** list — a small change in contract from `Collectors.toList()`, whose result you could still mutate. For most code, the unmodifiable version is what you want; treat the difference as a feature.

`Collectors` is the workhorse — its own section below.

### Reduce to one value — `reduce`, `count`, `sum`, `min`, `max`

```java
int total = orders.stream().mapToInt(Order::quantity).sum();           // primitive stream
Optional<Order> biggest = orders.stream().max(Comparator.comparing(Order::total));
long count = orders.stream().filter(Order::shipped).count();
```

`reduce` is the general form — fold a stream down to one value:

```java
int sum = numbers.stream().reduce(0, Integer::sum);                    // identity + binary op
Optional<Integer> max = numbers.stream().reduce(Integer::max);          // no identity → Optional
```

The two-arg form takes an **identity** (the value to return for an empty stream — and the starting accumulator) plus a `BinaryOperator<T>`. The one-arg form has no identity, so it returns `Optional<T>` — empty when the stream is empty. The presence of `Optional<T>` here is exactly the pattern 4.3 prepared you for.

### Find one — `findFirst`, `findAny`

```java
Optional<User> first = users.stream().filter(User::isAdmin).findFirst();
```

Both return `Optional<T>`; both short-circuit (the rest of the source is never visited). `findFirst` honours encounter order; `findAny` does not — meaningful only with `parallelStream` (5.3) where letting any thread "win" is faster.

### Match — `anyMatch`, `allMatch`, `noneMatch`

```java
boolean hasAdmin = users.stream().anyMatch(User::isAdmin);
```

All three are short-circuiting boolean terminals. The names map to their semantics directly.

### Side effects — `forEach`, `forEachOrdered`

```java
events.stream().forEach(eventBus::publish);
```

`forEach` is the one terminal whose entire point is a side effect. Use it when that is what you want — but understand that, in a parallel stream, the order of calls is unspecified. `forEachOrdered` enforces source order at the cost of some parallelism.

### `toArray`

```java
String[] arr = stream.toArray(String[]::new);                          // constructor reference (5.1)
```

Useful interop point with array-shaped APIs.

## `Collectors` — the small language inside `collect`

`Collectors` is the most-reached-for static-utility class in modern Java. Most stream pipelines you read end in a `.collect(Collectors.something(...))` call. The five you must know:

### `toList`, `toUnmodifiableList`, `toSet`, `toUnmodifiableSet`

```java
List<String> names = stream.collect(Collectors.toUnmodifiableList());
```

`toList()` (the shortcut) is essentially `toUnmodifiableList()`. The collector form is there for older code and for cases where you specifically want a mutable `ArrayList`.

### `toMap` — key, value, *merge*

```java
Map<Long, User> byId = users.stream()
    .collect(Collectors.toMap(User::id, Function.identity()));
```

Two arguments: a key extractor (`Function<T, K>`), a value extractor (`Function<T, V>`). If the key extractor produces duplicates, the two-arg form **throws** `IllegalStateException`:

```java
// throws when two users share a name
users.stream().collect(Collectors.toMap(User::name, Function.identity()));
```

The three-arg form takes a merge function for collisions:

```java
Map<String, User> byName = users.stream()
    .collect(Collectors.toMap(User::name, Function.identity(), (a, b) -> a));   // keep the first
```

Forgetting the merge is a real bug — easy to miss in test data that happens to be unique. When in doubt, supply one.

### `groupingBy` — bucket by key

```java
Map<String, List<Order>> byCustomer = orders.stream()
    .collect(Collectors.groupingBy(Order::customerName));
```

`groupingBy(classifier)` returns `Map<K, List<T>>` — bucket each element under its key. The two-arg form lets you change the *downstream* collector — what to do with each bucket:

```java
Map<String, Long> countByCustomer = orders.stream()
    .collect(Collectors.groupingBy(Order::customerName, Collectors.counting()));

Map<String, BigDecimal> totalByCustomer = orders.stream()
    .collect(Collectors.groupingBy(
        Order::customerName,
        Collectors.reducing(BigDecimal.ZERO, Order::total, BigDecimal::add)));
```

This second form — `groupingBy` + a downstream `reducing` — is exactly what the DIY asks for, and it is *the* place collectors stop feeling like sugar and start feeling like a real composable language.

### `partitioningBy` — bucket by predicate

```java
Map<Boolean, List<Order>> partitioned = orders.stream()
    .collect(Collectors.partitioningBy(o -> o.total().compareTo(THRESHOLD) > 0));
```

A specialised `groupingBy` whose key is `Boolean`. The map is **guaranteed to have both `true` and `false` keys**, even if one bucket is empty — a real ergonomic win over `groupingBy(...)` with a `Boolean` key, where missing keys can quietly break downstream code.

### `joining`

```java
String csv = names.stream().collect(Collectors.joining(", ", "[", "]"));
```

The three-arg form takes a delimiter, prefix, and suffix. Reaching for `StringBuilder` and `for` here is mostly a sign that someone hasn't seen `joining` yet.

### Downstream collectors — the composition that earns its keep

The two-arg `groupingBy` and `partitioningBy` take a *second collector* — applied per bucket. That is the lever that makes `Collectors` a small DSL:

- `groupingBy(key, counting())` → `Map<K, Long>`
- `groupingBy(key, summingInt(...))` → `Map<K, Integer>`
- `groupingBy(key, averagingDouble(...))` → `Map<K, Double>`
- `groupingBy(key, mapping(Order::id, toList()))` → `Map<K, List<Long>>` (mapping inside the bucket)
- `groupingBy(key, reducing(identity, mapper, op))` → `Map<K, R>` (general fold per bucket)

The mental model: each bucket is *its own little stream*; the downstream collector is what you would have written if you had been streaming just that bucket. Once that clicks, recipes you used to write by hand collapse to one line.

## Lazy evaluation and short-circuiting

Two properties worth seeing concretely:

### Laziness — intermediates do not run until a terminal demands

```java
Stream<Integer> s = Stream.of(1, 2, 3, 4)
    .filter(x -> { System.out.println("filter " + x); return x > 1; })
    .map(x ->     { System.out.println("map "    + x); return x * 10; });
// nothing printed yet — no terminal

List<Integer> result = s.toList();
// now you see filter and map interleaved per element
```

The printed order is `filter 1, filter 2, map 2, filter 3, map 3, filter 4, map 4`. The runtime walks one element through the whole pipeline before starting the next. There is no intermediate list of "things that passed filter"; there is no intermediate list of "things after map" — that fusion is what makes a stream chain comparable in performance to a hand-written loop.

### Short-circuiting

```java
Optional<Integer> first = Stream.iterate(1, x -> x + 1)             // infinite
    .filter(x -> x % 7 == 0)
    .findFirst();                                                   // returns Optional[7] and stops
```

A short-circuiting terminal (`findFirst`, `findAny`, `anyMatch`, `allMatch`, `noneMatch`, `limit`) stops pulling from the source as soon as it has its answer. The infinite stream above is fine *because* `findFirst` halts after 7. Without short-circuiting, an infinite source is a hang.

The combination — laziness + short-circuiting — is why the pipeline form is not just prettier than a loop. The pipeline knows what to skip.

## When *not* to use streams

The case for streams is strong; the case against them is real. Four shapes where a plain loop is right:

- **Hot inner loops.** For ordinary code, the JIT closes most of the gap between a stream and a loop. In a profiled tight loop — millions of iterations, microsecond budget — the loop usually still wins, because lambda capture and the iteration overhead are not free. Reach for streams first, profile, and rewrite the bottleneck if measured.

- **Heavy side effects.** A stream's elegance is its functional, side-effect-free shape. A pipeline whose final `forEach` updates three external maps, writes to disk, and increments a counter is *imitating* a stream — but the loop reads more honestly and has fewer surprises. If the work is fundamentally imperative, write it imperatively.

- **Debuggability.** Stepping through a stream pipeline in a debugger is a mess. Each lambda is a synthetic class, the call stack passes through framework code, and a breakpoint inside a `map` lambda fires per element. A `for`-loop is one line per step. When the code is genuinely hard, the loop is easier to read at 2 a.m.

- **Checked exceptions.** None of the standard functional interfaces declare any checked exception. A stream pipeline whose lambdas need to call `IOException`-throwing code becomes an exercise in wrap-and-rethrow. Sometimes the loop is just better. (One Module 4 lookahead: `Files.lines` returns a `Stream<String>` that *can* throw an `UncheckedIOException` — the JDK had to invent that to keep streams composable. Treat it as a hint about the friction.)

The general rule, stated as a slogan and meant honestly: **use streams when the pipeline shape is what the code is about; use a loop when the loop is what the code is about.** If the most natural English description is "for each X, do Y," write a `for`. If it is "from these, keep these, then group these," write a stream.

## DIY Exercise

Take a flat list of `Order`s and group by customer, summing each customer's spend — using `groupingBy` with a downstream `reducing` collector, with no explicit loops, no `if` statements, and no mutable accumulator outside the collector.

### Layout

```
src/main/java/
  orders/
    Customer.java     // record Customer(long id, String name)
    Order.java        // record Order(long id, Customer customer, BigDecimal total)
    Orders.java       // utility class with the static aggregation method(s)
src/test/java/
  orders/
    OrdersTest.java
```

- `Customer` and `Order` are **records** (1.5).
- `Orders` is a **non-generic static utility class** — `private` constructor, only `static` methods. (Same shape as `Pairs` from 3.2.)
- All three top-level types in the `orders` package; each in its own file.
- Use `BigDecimal` for money, not `double` (3.4 already explained why).

### Tasks

1. **`Orders.totalByCustomer(List<Order> orders)`** — returns `Map<Customer, BigDecimal>`. Implement with `Collectors.groupingBy(Order::customer, Collectors.reducing(BigDecimal.ZERO, Order::total, BigDecimal::add))`. Three arguments to `reducing`: the identity (`BigDecimal.ZERO`), the value mapper (`Order::total`), the combiner (`BigDecimal::add`). No loops, no `if`. Test on a fixture with three customers and seven orders — assert the per-customer sum is right and that customers with no orders do not appear in the map at all.

2. **`Orders.orderCountByCustomer(List<Order> orders)`** — returns `Map<Customer, Long>`. Implement with `groupingBy` + `counting()`. One line.

3. **`Orders.topCustomerBySpend(List<Order> orders)`** — returns `Optional<Customer>`. Build on task 1 (compose, do not duplicate): take the `Map<Customer, BigDecimal>` it produces, stream its `entrySet`, find the max by value (`Map.Entry.comparingByValue()`), and extract the key. The return type is `Optional<Customer>` precisely because an empty input must produce empty — the type is enforcing the case you would otherwise forget. Test the empty case and a non-empty case.

4. **`Orders.bigSpenders(List<Order> orders, BigDecimal threshold)`** — returns `Set<Customer>` whose total exceeds the threshold. Compose from task 1's result; filter the entry stream by value; collect the keys into an unmodifiable set (`toUnmodifiableSet`). Test the boundary: `threshold == total` should *not* include the customer (strict greater-than).

5. **The verbosity check.** Replace the explicit collector type on one declaration with `var` (3.5). Does the code still read clearly? Where is the type "obvious" and where would `var` hurt? Write a one-line note in the test class commenting why you kept `var` (or did not) for `totalByCustomer`'s return.

### Things to think about

- The `reducing` collector in task 1 has *three* arguments. There is also a two-arg form `reducing(identity, op)` that requires the stream's element type to equal the accumulator type. Why is the three-arg form the right one here — what does the value mapper (`Order::total`) buy you? (Hint: try the two-arg form and read the compile error.)
- `groupingBy(Order::customer, ...)` uses `Customer` (a record) as a map key. What contract from 3.4 is the map relying on, and *which* property of records (1.5) makes you trust the contract without writing a single override?
- Task 3 returns `Optional<Customer>`. You could have made it return `Customer` and thrown on empty input. Argue why `Optional` is the better choice here — what does it tell the caller that a thrown exception does not? (Re-read 4.3 if needed.)
- Task 4 produced a `Set<Customer>`. Could you have built it in one pass — `groupingBy` + a downstream that conditionally includes the bucket? You can — but you would be filtering *after* collecting, which is awkward. The two-pass form (collect totals, then filter the map) is clearer. Is there a case where one-pass would *actually* matter? (Hint: stream size, memory.)
- Convert one of your collectors to a parallel stream (`orders.parallelStream()...`) and rerun the tests. They should still pass — the collectors used here are all combinable. Hold that observation; 5.3 is about *which* collectors are safe in parallel and which are not.
