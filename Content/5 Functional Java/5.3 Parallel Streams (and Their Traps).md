# 5.3 Parallel Streams (and Their Traps)

`.parallelStream()` is one of the most seductive method names in the standard library. The promise is that you replace one word — `stream` becomes `parallelStream` — and suddenly your pipeline uses every core on the machine. Sometimes that is exactly true. Often it is slower, and occasionally it is *wrong*. This submodule is about telling the three cases apart.

The short version: parallel streams are a fork/join wrapper around the *same pipeline* you wrote in 5.2. The fork/join mechanics are real concurrency; the pipeline still has to be shaped in a way that survives being split across threads. The good news is that most well-written stream pipelines from 5.2 already are. The bad news is that the parts that aren't tend to fail silently — a wrong answer rather than an exception.

This is also a deliberate preview of Module 6 (concurrency). The Java Memory Model, the executor, happens-before — they are coming. For now, treat what follows as the operational picture: enough to use parallel streams correctly and to recognise when not to.

---

## What `parallelStream` actually does

Two ways to start a parallel stream:

```java
list.parallelStream()...                 // straight from Collection
list.stream().parallel()...              // promote a sequential stream to parallel
```

Either way the pipeline is split into chunks by a **`Spliterator`** (the parallel cousin of `Iterator` — it can hand out *half* of itself), each chunk is processed concurrently, and a final stage combines the partial results. The work runs on the **common ForkJoinPool** — a JVM-wide thread pool, sized by default to `Runtime.getRuntime().availableProcessors() - 1` worker threads. Every parallel stream in your application shares it.

You did not start a thread. You did not pick a thread count. You did not pass an executor. All of that is implicit, and most of the surprises that follow come from the fact that the parallelism is *implicit*.

### The common ForkJoinPool — what is shared, what is not

The common pool is global. If two parts of your application both fire a `parallelStream`, they compete for the same workers. If one of those streams runs a slow `map` (say, a network call per element), it holds workers and blocks the other. In a web server with one request per CPU and a parallel stream per request, you can starve yourself.

There is a way to run a stream on a *different* pool — submitting it as a task to a custom `ForkJoinPool` — but it relies on a quirk of how stream evaluation reads the current pool. It is not a public API. If you need real isolation, you want `CompletableFuture` with an explicit executor (6.3), not parallel streams.

> Use `parallelStream` for **CPU-bound, self-contained** work in a single application context. Anything else — I/O, shared state, an application competing with itself for cores — wants a different tool.

## When parallelism helps

The classic case: a **large** dataset, a **CPU-heavy** per-element operation, and **no contention** for shared state.

```java
long primes = LongStream.rangeClosed(2, 10_000_000)
    .parallel()
    .filter(Primes::isPrime)
    .count();
```

Counting primes up to 10 million is embarrassingly parallel: each candidate is independent, the per-element work is CPU-bound (some divisions and a loop), and there is no shared state to coordinate. On a four-core laptop this typically runs ~3× faster than the sequential version — not the 4× a perfectly linear scaling would suggest, because the splitting and combining themselves cost something.

The shape that works:

- **N is large.** Splitting a 100-element stream and dispatching it across 8 cores spends more time on fork/join bookkeeping than the work itself.
- **Per-element cost is non-trivial.** A pipeline that does one cheap arithmetic step per element gets crushed by overhead. Parallelism needs *enough* work to amortise its cost.
- **The source splits well.** `ArrayList`, arrays, and the numeric ranges (`IntStream.range`) split cheaply and evenly. `LinkedList`, `Stream.iterate(...)`, and other sequential sources split badly — sometimes not at all.
- **The pipeline is pure.** No shared mutable state, no I/O, no order dependence.

A useful rough rule of thumb (not a guarantee): you usually need **N × (per-element cost)** to be in the milliseconds-or-greater range before parallelism pays back the overhead. Below that, sequential wins.

## When parallelism hurts

Three common ways it makes things slower:

### Per-element work is too small

```java
int sum = IntStream.range(0, 1_000_000).parallel().sum();          // probably slower than sequential
```

Summing ints is one ALU op per element. Splitting the work eight ways adds task-submission overhead that dwarfs the saving. The sequential `IntStream.range(0, 1_000_000).sum()` is hard to beat for an operation this cheap.

### The source does not split well

```java
List<Integer> linked = new LinkedList<>(numbers);
linked.parallelStream().filter(...).count();                       // splits poorly
```

A `LinkedList` cannot give you "the second half" without walking the first half. Its spliterator either walks one node at a time or splits unevenly, and the parallel run is rarely a win — and is sometimes much worse.

`Stream.iterate(seed, x -> next(x))` is *strictly* sequential — each element depends on the previous, so it cannot be split at all. Calling `.parallel()` on it does nothing useful and adds overhead.

`Files.lines(path)` reads sequentially from disk. Parallelising the resulting stream pushes the work onto multiple cores, but the cores all wait on the same single-threaded reader. The "parallel" is a fiction.

### Sorted streams pay twice

A `sorted()` in a parallel pipeline still has to globally sort. The sort itself can parallelise, but the pipeline now has a barrier where every worker must wait for the sort before downstream stages can proceed. Putting `sorted` in front of cheap per-element work usually negates the parallelism gain.

## When parallelism is *wrong*

This is the dangerous category — the pipeline runs and returns an answer, but the answer is incorrect.

### Shared mutable state

```java
List<Integer> result = new ArrayList<>();
numbers.parallelStream().filter(...).forEach(result::add);          // wrong: ArrayList is not thread-safe
```

`ArrayList.add` is not synchronised. Multiple parallel workers calling it can corrupt internal state, lose elements, or throw `ArrayIndexOutOfBoundsException` mid-stream. The right form is the collector you already know:

```java
List<Integer> result = numbers.parallelStream().filter(...).toList();
```

`toList()` (and every `Collectors.toList`-style collector) is designed for parallel — each worker writes into its own partial container, and the combine step merges them. **Build results with collectors, not with `forEach` plus an external container.** The collector handles parallelism so you do not have to.

### Order-dependent operations

```java
List<String> ordered = stream.parallel()
    .map(this::transform)
    .toList();                                                       // ok: encounter order is preserved
```

vs.

```java
AtomicInteger i = new AtomicInteger();
list.parallelStream().forEach(x -> log.info("{}: {}", i.getAndIncrement(), x));   // order is undefined
```

Stream pipelines distinguish two ideas: **encounter order** (the source's order) and **processing order** (the order workers happen to handle elements). Collectors that *preserve* encounter order (`toList`, ordered `collect`) work correctly in parallel. Operations that *depend on* processing order — `forEach` over a counter, `findFirst` interpreted as "first by my external index," any reducer that is not associative — give wrong answers.

`findAny` is honest about this: its name says "any element matching, fastest one wins." `findFirst` honours encounter order; in a parallel pipeline it may pay coordination cost. Prefer `findAny` when order does not matter.

### `reduce` with a non-associative operation

```java
int result = numbers.parallelStream().reduce(0, (a, b) -> a - b);    // wrong shape for parallel
```

Parallel `reduce` splits the input into chunks, reduces each chunk, then combines the partial reductions. That works *only* if the operation is **associative**: `(a op b) op c == a op (b op c)`. Subtraction is not. Parallel reduce over subtraction returns an undefined value depending on how the chunks fall.

Addition is associative; multiplication is; string concatenation is. Subtraction, division, and "first-non-empty" are not. Read every `reduce` you parallelise with associativity in mind.

The identity must also be a true identity for the operation: `0` for addition, `1` for multiplication, `""` for concatenation. A wrong identity (e.g., starting `reduce(1, Integer::sum)`) is invisibly wrong in sequential code but *compounded* in parallel — every chunk starts with the bad identity.

### Stateful lambdas

```java
Set<Long> seen = ConcurrentHashMap.newKeySet();
stream.parallel().filter(seen::add).forEach(...);                    // wrong shape
```

Even with a thread-safe set, the *pipeline* now depends on hidden state — which elements are processed first determines which "pass" the filter. The result is timing-dependent. The same code in a sequential stream may be fine, but the parallel version is non-deterministic. The fix is `distinct()`, which the stream framework implements correctly in parallel.

### Side effects in the wrong place

The general principle that ties these together:

> A parallel-stream pipeline must be **pure** — its lambdas must not read or write shared mutable state outside the stream. State that needs to be aggregated lives in a **collector**.

The collector framework is built around two operations a thread-safe accumulator must support: an *accumulator* that adds an element to a partial result, and a *combiner* that merges two partial results. Every `Collectors.xxx` you used in 5.2 already supplies both. That is why `.collect(...)` survives parallel and `.forEach(externalList::add)` does not.

## Measuring it — and why your measurements lie

Stream throughput is sensitive in ways that make casual measurement misleading. Three landmines:

1. **JIT warm-up.** The HotSpot JIT compiles hot code paths after they have run hundreds or thousands of times. A timing taken on the first run measures the interpreter; a timing taken on the tenth measures the JIT. Always warm the pipeline before measuring.

2. **`System.nanoTime` is monotonic; `System.currentTimeMillis` is not.** Use `nanoTime` for elapsed-time measurement. `currentTimeMillis` can go backwards if the system clock adjusts.

3. **The common pool is shared.** A parallel-stream benchmark run while the rest of your application does anything CPU-heavy is measuring contention, not parallelism. Run measurements on an otherwise-idle process.

For *serious* measurement, the right tool is JMH (the Java Microbenchmark Harness) — it handles warm-up, dead-code elimination, and statistical noise. JMH is out of scope for this course, but its name is worth knowing for when "casual timing" stops being enough.

For *casual* measurement — what the DIY asks for — the recipe is:

```java
// warm up
for (int i = 0; i < 5; i++) primes.countSequential(limit);

// measure
long start = System.nanoTime();
long result = primes.countSequential(limit);
long elapsed = System.nanoTime() - start;
```

Repeat both variants several times, take the median (not the mean — outliers from GC are common), and **report the relative ratio**, not absolute milliseconds. The point is *which* is faster and by *how much*, not the specific number, which depends on your hardware.

## A short decision guide

| Symptom | Reach for |
|---|---|
| Big array or `ArrayList`, CPU-bound per element, no shared state | `parallelStream()` is plausibly worth measuring |
| `LinkedList`, `Stream.iterate`, `Files.lines`, or any sequential source | Don't bother with parallel |
| The lambda does I/O or blocks | Don't use parallel streams. Use `CompletableFuture` (6.3) with an explicit executor |
| The lambda mutates external state | Restructure to a collector first, *then* consider parallel |
| You "feel like it might be faster" | Measure. The answer is usually no |
| Result must preserve order | `toList()` is fine; `findFirst` and `forEach` are slower; `findAny` is faster |
| Result is one number | `sum`/`reduce` on a primitive stream — measure; the gain depends on N × cost |

The summary line worth remembering: **parallel streams are not "free parallelism." They are a one-line interface to a shared global thread pool, and that one line carries every constraint of correct concurrent programming, just hidden.**

## DIY Exercise

You will write a CPU-bound task — counting primes in a range — in both sequential and parallel forms, measure both, and find the rough crossover point on your machine.

### Layout

```
src/main/java/
  primes/
    Primes.java          // the prime predicate + the counting methods
src/test/java/
  primes/
    PrimesTest.java      // correctness tests
    PrimesBench.java     // timing comparison; annotated @Disabled by default (see task 5)
```

- `Primes` is a non-generic static-utility class: `private` constructor, only `static` methods.
- Both test classes live in the `primes` package.
- The bench class is a JUnit test class for convenience (you run it from the existing JUnit setup), but it is `@Disabled` by default so it does not slow the test suite; you run it explicitly when you want a measurement.

### Tasks

1. **`Primes.isPrime(long n)`** — straightforward trial division up to `√n`. Handle `n < 2` (false), `n == 2` (true), and skip even numbers above 2. This is the per-element CPU work the rest of the exercise leans on.

2. **`Primes.countSequential(long limit)`** — `LongStream.rangeClosed(2, limit).filter(Primes::isPrime).count()`. One line. Test against a known answer: there are 25 primes below 100, 1229 primes below 10 000.

3. **`Primes.countParallel(long limit)`** — same pipeline with `.parallel()` inserted. Test against the same known answers. **The fact that both versions return identical results is part of the exercise** — parallel correctness is the property under test.

4. **Where do `parallel` and `sequential` agree at this scale?** Add a parameterised test: for `limit` in `[100, 1000, 10_000, 100_000]`, assert `countSequential(limit) == countParallel(limit)`. If they ever disagree, you have a bug in `isPrime` (a shared mutable static, perhaps?) — that is the lesson, not a failed exercise.

5. **The benchmark.** In `PrimesBench`, write a method that:
   - Warms up by running `countSequential(1_000_000)` and `countParallel(1_000_000)` five times each, *ignoring* the elapsed times.
   - Measures each variant five more times with `System.nanoTime()`, printing the median.
   - Reports the ratio: parallel time / sequential time.

   Annotate the class with `@Disabled` (JUnit 5) so it does not run in the normal test suite. To run it, comment out the annotation or use the IDE.

6. **Find the crossover.** Run the bench for `limit` values `100`, `10_000`, `100_000`, `1_000_000`, `10_000_000`. At small `limit`, parallel is slower (overhead dominates). At some point — somewhere around 10⁵ to 10⁶ on most hardware, but it varies — parallel begins to win. Record where it crosses over on *your* machine in a one-line comment at the top of the bench class. (No claim of generality — this is a measurement of your laptop, today.)

### Things to think about

- Why is `LongStream.rangeClosed` a good source for parallelism, where `Stream.iterate(2L, x -> x + 1).limit(limit - 1)` would be a bad one? Try replacing the source with `iterate` and re-run the bench at `1_000_000`. What changed, and what does that tell you about the role of the spliterator?
- At `limit = 100`, parallel is probably slower than sequential by a noticeable factor (often 5–10×). The work is genuinely "embarrassingly parallel" — there are no data dependencies. So why does parallelism *lose*? Identify two specific overheads, in your own words, that are paid even when each element is independent.
- Hypothesis: if you replaced `Primes::isPrime` with `n -> Thread.sleep(1)` (a blocking, non-CPU step), what would parallel-stream throughput look like, and why is that the wrong tool for the job? Argue why you would not even try to measure it — what guidance from the "When parallelism is wrong" section applies?
- Your `isPrime` is a pure function — `(long n) -> boolean`, no shared state. Add a static counter to `isPrime` that tracks how many times it was called. Run `countParallel(1_000_000)` and read the counter. Is the number correct? If you changed `int counter` to `static int counter` (no synchronisation), does the read-out match the expected call count? Explain in JMM-flavoured terms (visibility, atomicity) — even if Module 6 has not arrived yet. This is the preview.
- One last consistency check: in your parameterised test (task 4), is there *any* `limit` where `countSequential` and `countParallel` disagree? They should never. If you ever see disagreement, what is the most likely class of bug — and which property of a parallel-stream pipeline (the one this submodule kept emphasising) is being violated?
