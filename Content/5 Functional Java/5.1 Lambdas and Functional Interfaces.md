# 5.1 Lambdas and Functional Interfaces

The "functional" in this module name does not mean Java has gone Haskell. It means Java 8 added the smallest set of language features needed to **pass behaviour as a value** — and the standard library was rebuilt around them. The killer feature is not lambdas themselves; it is the API surface lambdas *unlocked* — Streams (5.2), `CompletableFuture` (6.3), `Comparator.comparing` (3.4 already touched it). All of those are functional interfaces being passed around. This submodule is about the mechanics underneath: what a lambda actually is, what the JVM does with it, when you need a method reference instead, and how to read the function-type alphabet (`Function`, `Predicate`, `Consumer`, `Supplier`).

1.7 set this up by contrasting anonymous classes against the lambda form that replaced most of them. This submodule is the other side of that comparison — written for when you reach for a lambda first and ask "what *is* this thing the compiler is making."

---

## A lambda is shorthand for a functional-interface instance

Java has no separate "function type." When you write a lambda, the compiler is constructing an instance of some **functional interface** — an interface with exactly one abstract method — and your lambda body is that method's implementation.

```java
Runnable r = () -> System.out.println("hi");

// is roughly equivalent to:
Runnable r = new Runnable() {
    @Override public void run() { System.out.println("hi"); }
};
```

The lambda has no type of its own. The variable's declared type — `Runnable` — tells the compiler which interface to target, which abstract method to bind, and therefore what shape the lambda's signature must have. This is called **target typing**, and it is why the same lambda can mean different things in different contexts:

```java
Runnable r          = () -> log.info("tick");       // SAM: void run()
Callable<String> c  = () -> "ok";                    // SAM: String call()
Supplier<Integer> s = () -> 42;                      // SAM: T get()
```

Three different interfaces, three different runtime types — same lambda *shape*, disambiguated by the left side. Without a target, a lambda has no type at all (`var f = () -> 1;` is a compile error — recall 3.5).

> **Functional interface** = an interface with one abstract method. The `@FunctionalInterface` annotation is not what makes it functional — the *single abstract method* does. The annotation just asks the compiler to enforce that going forward, so a future maintainer cannot accidentally add a second abstract method and break every caller.

`default` and `static` methods on the interface do not count against the "one abstract method" rule. `Comparator` declares dozens of default methods but is still a functional interface because only `compare` is abstract.

### Lambda syntax — the shapes

```java
() -> "ok"                         // no params, expression body
x  -> x + 1                        // one param, parens optional
(x, y) -> x + y                    // two params, parens required
(int x, int y) -> x + y            // explicit types (rare; almost always inferred)

x -> {                             // block body — needs an explicit return
    System.out.println(x);
    return x.length();
}
```

Two minor rules worth memorising once:

- An **expression body** (`x -> x + 1`) implicitly returns the expression.
- A **block body** (`x -> { ... }`) needs explicit `return` for any non-`void` target — like a regular method.

That is it for syntax. The interesting parts are what the lambda *captures* and what its `this` means.

## Capture — lambdas close over *effectively final* values

A lambda can read variables from its enclosing scope. The constraint:

```java
int factor = 2;
Function<Integer, Integer> times = x -> x * factor;     // ok — factor is effectively final

factor = 3;                                              // not allowed: factor must stay final
                                                         // (the lambda would not "see" 3 anyway)
```

`factor` does not need the literal `final` keyword, but it must be **effectively final** — never reassigned after initialization. The compiler enforces this. The reason is the JVM does not actually share a mutable variable slot with the lambda; it *captures the value at the moment the lambda is constructed*. If you reassigned `factor`, the lambda would still hold the old value, and that asymmetry is more confusing than the rule.

What this really means in practice: lambdas are for transformation, not shared mutable state. If you want shared mutation, you reach for fields (which *can* be reassigned because the lambda captures `this`, not the field), or for `AtomicInteger` / `AtomicReference` (which you mutate *inside* the holder rather than reassigning the variable):

```java
AtomicInteger count = new AtomicInteger();
events.forEach(e -> count.incrementAndGet());           // mutates the AtomicInteger, not the variable

int sum = 0;
list.forEach(x -> sum += x);                            // compile error: sum is reassigned
```

The second form is the wrong shape for streams anyway — that is `reduce`'s job (5.2). The compiler error nudges you toward it.

### `this` inside a lambda — *not* the lambda

Inside an **anonymous class** (1.7), `this` refers to the anonymous instance. Inside a **lambda**, `this` refers to the *enclosing* `this`:

```java
class Logger {
    private String prefix = "LOG";

    Runnable lambdaJob = () -> System.out.println(this.prefix);   // this == Logger instance

    Runnable anonJob = new Runnable() {
        @Override public void run() {
            System.out.println(this.prefix);                       // this == anon instance — no prefix field! compile error
        }
    };
}
```

This is one of the few real semantic differences from anonymous classes (1.7 listed the others). For most calls it does not matter; when it does, it is usually a feature — lambdas can refer to the enclosing instance's fields and methods without `OuterClass.this` gymnastics.

## The core functional interfaces — `java.util.function`

The standard library defines a small, deliberately spartan vocabulary of functional interfaces in `java.util.function`. Almost every functional API in the JDK speaks this vocabulary. Memorise these five:

| Interface | Abstract method | Reads as |
|---|---|---|
| `Function<T, R>` | `R apply(T t)` | "T in, R out" — a transformation |
| `Predicate<T>` | `boolean test(T t)` | "T in, boolean out" — a question |
| `Consumer<T>` | `void accept(T t)` | "T in, nothing out" — a side effect |
| `Supplier<T>` | `T get()` | "nothing in, T out" — a producer |
| `BiFunction<T, U, R>` | `R apply(T t, U u)` | "T and U in, R out" |

Read a stream pipeline and you are reading these:

```java
list.stream()
    .filter(s -> s.length() > 3)                  // Predicate<String>
    .map(String::toUpperCase)                      // Function<String, String>
    .forEach(System.out::println);                 // Consumer<String>
```

The names are not optional vocabulary — they are part of the contract you read in JavaDoc. `Stream.map` takes a `Function`; `Stream.filter` takes a `Predicate`. Knowing the five names means you can read the signatures.

### The arithmetic specializations

For primitive `int`/`long`/`double`, boxed `Integer`/`Long`/`Double` adds allocation overhead. The package defines unboxed variants — `IntFunction<R>`, `ToIntFunction<T>`, `IntPredicate`, `IntConsumer`, `IntSupplier`, plus the same for `Long` and `Double`. The pattern is:

- `IntFunction<R>` — `int` in, `R` out
- `ToIntFunction<T>` — `T` in, `int` out
- `IntPredicate` — `int` in, `boolean` out
- `IntUnaryOperator` — `int` in, `int` out (like `Function<Integer,Integer>` but unboxed)

You will rarely write these by hand; you will mostly *read* them in primitive-stream signatures (`IntStream.map` takes an `IntUnaryOperator`). Pattern-match the name and move on.

### The two-arg helpers — `UnaryOperator`, `BinaryOperator`

`UnaryOperator<T>` is `Function<T, T>` — `T` in, `T` out. `BinaryOperator<T>` is `BiFunction<T, T, T>` — two `T`s in, one `T` out (the right shape for `reduce`, 5.2). Both extend their `Function` counterpart, so you can pass a `UnaryOperator<String>` anywhere a `Function<String, String>` is expected. They exist to give cleaner names to a common shape; nothing more.

### Composing functional interfaces — `andThen`, `compose`, `and`, `or`, `negate`

The interfaces ship with default methods to chain them:

```java
Function<String, String> trim = String::trim;
Function<String, String> lower = String::toLowerCase;
Function<String, String> clean = trim.andThen(lower);      // trim first, then lowercase

Predicate<String> nonEmpty = s -> !s.isEmpty();
Predicate<String> short_   = s -> s.length() < 10;
Predicate<String> good     = nonEmpty.and(short_);          // both must hold
Predicate<String> bad      = good.negate();                 // logical NOT
```

`andThen` (run me, then them) and `compose` (run them, then me) are duals; `andThen` reads left-to-right and is usually clearer. `and`/`or`/`negate` on `Predicate` mirror boolean operators. Combinator code like this is where the functional vocabulary earns its keep — you build the predicate or transformation in pieces, name each piece, and pass the composed result on.

## Method references — point-free shorthand

When a lambda's body is *just calling one method*, the method reference form is shorter and almost always clearer. Four flavours:

```java
String::toUpperCase                  // unbound instance method      — Function<String, String>
System.out::println                  // bound instance method        — Consumer<String>
Integer::parseInt                    // static method                — Function<String, Integer>
ArrayList::new                       // constructor                  — Supplier<ArrayList>
```

| Form | Lambda equivalent | Read as |
|---|---|---|
| `Class::staticMethod` | `x -> Class.staticMethod(x)` | "call the static method on the arg" |
| `instance::method` | `x -> instance.method(x)` | "call the method on this captured instance" |
| `Class::instanceMethod` | `(obj, x) -> obj.method(x)` | "call the method *on* the first arg" |
| `Class::new` | `(x) -> new Class(x)` | "construct from the arg" |

The third form is the one that trips people up. `String::toUpperCase` looks like a static method reference, but `String.toUpperCase()` is an instance method. The convention is: when the receiver is going to come from the *stream / argument*, you write `Class::method`, and Java will treat the first argument as the receiver. So `Function<String, String> f = String::toUpperCase` and `f.apply("ada")` ends up calling `"ada".toUpperCase()`.

> Default to a method reference when the lambda would only call one method. Default to a lambda when you are doing anything else (a multi-step expression, a conditional, two method calls). Either is fine; the rule is consistency within a chain.

Constructor references (`Class::new`) are especially useful with `Stream.toArray`, `Collectors.toCollection`, and `Optional.orElseGet`:

```java
List<User> users = names.stream()
    .map(User::new)                                      // String -> User via constructor
    .collect(Collectors.toCollection(ArrayList::new));   // collect into a fresh ArrayList
```

## What the JVM actually does — `invokedynamic` and `LambdaMetafactory`

A small but useful piece of knowledge: a lambda is **not** compiled into an anonymous inner class. If it were, every lambda would mean a new `.class` file generated at compile time and loaded at startup — slow and bulky.

Instead, the compiler emits an `invokedynamic` instruction pointing at `LambdaMetafactory`, which the JVM resolves *the first time the lambda is encountered at runtime*. The factory generates the implementation class on the fly, caches it for reuse, and from then on the lambda is just another object. Three practical consequences:

- Lambdas that **capture nothing** are cached and reused — the same `Predicate<String>` literal evaluated twice produces the same object. Stateless lambdas are essentially free.
- Lambdas that **capture variables** allocate a small object per call (holding the captured values). Usually negligible; in a tight inner loop it can matter — profile, do not guess.
- The stack trace from inside a lambda points at a synthetic name like `Outer$$Lambda$42/0x000...`. It is legible, but less so than a named method. Method references give a slightly clearer trace because they point straight at the named method.

This is also why the syntax restrictions exist — a lambda has no type of its own because there is no class for it to *be* until the JVM makes one. The whole arrangement is what keeps "pass a function" cheap.

## When to *not* reach for a lambda

Lambdas are powerful enough to make any small bit of behaviour look like a one-liner. The discipline of holding back is the part that experience teaches:

- **Multi-line logic.** A four-line lambda inside a stream is often clearer as a named method passed by method reference. The name *is* documentation.
- **Side effects that touch external state.** `forEach(x -> sharedList.add(x))` is the wrong shape; that is what `collect(toList())` exists for (5.2). Reaching for a lambda to *mutate* something external is usually a signal that a stream operation is being abused.
- **Catching checked exceptions.** Built-in functional interfaces do not declare any. A lambda that needs to call a method throwing `IOException` has to wrap-and-rethrow, which is ugly; sometimes a plain `for`-loop is just better.
- **Performance-critical hot loops.** Most of the time the cost is unmeasurable, but if profiling shows a hot path dominated by capture allocation, a plain loop is right.

The good rule, the same as for `var` in 3.5: reach for the lambda when it makes intent clearer; do not reach for it when it obscures intent for the sake of looking modern.

## DIY Exercise

You will build a small `Pipeline<T>` — a chain of `Function<T, T>` steps applied in order. This is the simplest possible "compose behaviour" container, and writing it makes the functional-interface vocabulary concrete.

### Layout

```
src/main/java/
  pipeline/
    Pipeline.java         // the generic Pipeline<T>
    TextSteps.java        // static methods used as method references in the test
src/test/java/
  pipeline/
    PipelineTest.java
```

- `Pipeline<T>` is a **generic class** parameterised over the value type flowing through it. Each instance holds an ordered list of `Function<T, T>` steps.
- `TextSteps` is a non-generic utility class (1.4-style — `private` constructor, only `static` methods) holding three `String -> String` transformations: `trim`, `toLowerCase`, and a `collapseWhitespace` that replaces runs of whitespace with a single space.
- Both top-level types live in the `pipeline` package; each in its own file.

### Tasks

1. **`Pipeline<T>` core.** Provide:
   - A no-arg constructor.
   - `Pipeline<T> andThen(Function<T, T> step)` — return a *new* `Pipeline<T>` with `step` appended (do not mutate `this`; favour immutability). The signature returning `Pipeline<T>` lets calls chain: `new Pipeline<String>().andThen(...).andThen(...).andThen(...)`.
   - `T apply(T input)` — fold the steps left-to-right.
   - An empty pipeline's `apply` returns the input unchanged.

2. **`TextSteps`.** Each of `trim`, `toLowerCase`, `collapseWhitespace` is a plain `static String name(String s)` method — nothing special. Using them in the pipeline is the whole point of the next task.

3. **Compose without lambdas.** Build a `Pipeline<String>` whose three steps are `TextSteps::trim`, `TextSteps::toLowerCase`, `TextSteps::collapseWhitespace` — **all three referenced as method references**, no lambda bodies. Test that the pipeline transforms `"   Ada\tLOVELACE  \n"` into `"ada lovelace"`.

4. **Two flavours of empty.** Test that:
   - A pipeline with zero steps applied to `"hi"` returns `"hi"`.
   - A pipeline with one step (`String::strip`) applied to `"  hi  "` returns `"hi"`.

5. **A `BiFunction` extension.** Add `Pipeline<T> andThen(BiFunction<T, T, T> step, T context)` — the new step takes the current value *and* a captured context value. The context is curried in at composition time, not at `apply` time. Use it to add a step that prepends a fixed prefix: pipeline transforms `"world"` into `"hello world"` given a prefix `"hello "`. Write the test.

6. **Reuse a captured pipeline.** Construct one pipeline. Call its `apply` twice with two different inputs. Assert that the pipeline produces correct output both times — i.e., the pipeline does not have hidden per-call state. (The `andThen`-returns-new design from task 1 should make this trivially true; the test is documentation.)

### Things to think about

- The signature of `andThen` returning `Pipeline<T>` is what makes the call chain `.andThen(...).andThen(...).andThen(...)` work. What goes wrong if `andThen` returned `void` and mutated `this` in place? Name two real downsides — one about composition with `Stream` operations (where each step expects a value back), and one about thread safety.
- You used three method references in task 3 — `TextSteps::trim` etc. The compiler had to figure out the *target type* (`Function<String, String>`) from the `andThen` parameter. What would have happened if `andThen` were overloaded with both `Function<T,T>` and `Consumer<T>` taking the same name? Try it — what compile error do you get, and why is "ambiguous target type" the right error?
- `Function<T, T>` is also expressible as `UnaryOperator<T>`. Replace the parameter type and rerun the tests. Do they still pass? What changed in the contract a caller sees, and is that the *clearer* of the two names for this API?
- The `BiFunction` step in task 5 captures a `context` value at composition time. That is currying — fixing one argument early. How does this relate to "effectively final" capture? If `context` were a mutable `List<String>` that you later modified, would the captured step see the changes? Write a test that demonstrates the answer.
- Read the stack trace when one of your steps throws (e.g., make `TextSteps::trim` throw on a specific input). Compare the trace of the method-reference version against an inline lambda doing the same thing. Where in the trace does the synthetic lambda name appear, and what does that tell you about why method references are slightly easier to debug?

Next up is 5.2: the Streams API. You will not write a single `Pipeline.andThen` again — `Stream.map` is the same idea, scaled to the whole standard library and tuned by the JIT. But the vocabulary you used here — `Function`, `Predicate`, `UnaryOperator`, method references, capture rules — is *exactly* the vocabulary the Stream API speaks.
