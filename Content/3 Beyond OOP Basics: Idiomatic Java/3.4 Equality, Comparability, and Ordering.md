# 3.4 Equality, Comparability, and Ordering

3.3 said `HashSet` rejects duplicates "by `equals`" and `TreeMap` sorts keys "by `compareTo`." This submodule is the contract behind those phrases. Two questions: when are two objects *the same*, and given two objects, which comes *first*? Get the contracts wrong and the collections from 3.3 misbehave in ways that look like haunted-house bugs — an object you definitely put in a `HashMap` that `get` cannot find.

1.2 introduced `equals`/`hashCode`. This is the same material with the collections now in view, where the contract stops being theory and starts losing your data.

---

## `equals` — the contract

`Object.equals` defaults to `==` — reference identity, "the same object." For a *value* type (a `Point`, a `Money`, an `Employee`) that is wrong: two `Point(1, 2)` objects are equal *as values* even though they are distinct objects. So you override `equals`. The override must obey five rules — the **equivalence relation** contract:

| Rule | Means |
|---|---|
| **Reflexive** | `x.equals(x)` is `true`. |
| **Symmetric** | `x.equals(y)` ⟺ `y.equals(x)` — same answer both directions. |
| **Transitive** | `x.equals(y)` and `y.equals(z)` ⟹ `x.equals(z)`. |
| **Consistent** | Repeated calls give the same answer, as long as nothing used in `equals` changed. |
| **Non-null** | `x.equals(null)` is `false` — never throws. |

These are not pedantry. Collections *assume* them. A `HashSet` that calls a non-symmetric `equals` can contain what looks like the same element twice, or fail to find one it has, depending on argument order.

A correct hand-written `equals`:

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;                 // fast path, and handles reflexivity
    if (!(o instanceof Employee other)) return false;  // false for null AND wrong type
    return id == other.id
        && salary.equals(other.salary)
        && name.equals(other.name);
}
```

`instanceof` is `false` for `null`, so the non-null rule is free. Using `Objects.equals(a, b)` for each field instead of `a.equals(b)` is null-safe if any field can itself be `null`.

### The `instanceof` vs. `getClass()` problem

How `equals` decides "is `o` the right type" interacts badly with inheritance. Two options, each broken in a different way:

- **`instanceof`** — a `ColorPoint` can equal a plain `Point` (it *is* a `Point`). But `point.equals(colorPoint)` and `colorPoint.equals(point)` will likely disagree once `ColorPoint` adds color to its check — **symmetry breaks.**
- **`getClass()`** — `equals` requires the *exact* same class. Symmetry holds, but now a `Point` can never equal *any* subclass, even one that adds no state — which violates the Liskov substitution principle.

There is no override that satisfies both inheritance and the contract. The practical escapes:

1. **Do not add value fields in a subclass of a value class.** Then there is nothing to disagree about.
2. **Favour composition over inheritance** for value types (1.4) — a `ColorPoint` *has a* `Point` rather than *extends* it.
3. **Use `record`s** (1.5). A record is implicitly `final` and the compiler writes `equals`/`hashCode` for you, correctly, over exactly the components — the whole dilemma is designed out. For a plain data carrier, this is the answer.

## `hashCode` — the contract, and why it is not optional

`hashCode()` returns an `int` summarizing the object, used by every hash-based collection (`HashMap`, `HashSet`, `LinkedHashMap`...) to pick a bucket. Its contract:

1. **Equal objects must have equal hash codes.** `a.equals(b)` ⟹ `a.hashCode() == b.hashCode()`. **Mandatory.**
2. **Unequal objects *should* have different hash codes** — not required for correctness, but required for *performance*: a `hashCode` that returns a constant is "correct" and turns every `HashMap` into an O(n) list.
3. **Consistent** within a run, as long as `equals`-relevant fields do not change.

> **The iron law: override `equals`, override `hashCode`. Always both, together.** They are one feature in two methods.

### Why breaking it loses your data

Skip `hashCode` while overriding `equals`, and here is the failure — run it and watch:

```java
Map<Employee, String> roles = new HashMap<>();
roles.put(new Employee(1, "Ada"), "Engineer");
String r = roles.get(new Employee(1, "Ada"));   // null. The entry is "lost."
```

The two `Employee` objects are `equals` — but with the default `hashCode` they get *different* hash codes. `put` stored the entry in bucket A; `get` hashes the lookup key to bucket B and looks only there. `equals` is never even consulted, because the search never reaches the right bucket. The entry is in the map; `get` simply cannot find it.

### Mutability and hash-based collections

A second, nastier version of the same bug. Put an object in a `HashSet`, *then* mutate a field that `hashCode` depends on:

```java
Set<Employee> set = new HashSet<>();
Employee e = new Employee(1, "Ada");
set.add(e);                    // filed under hashCode at insert time
e.setName("Ada Lovelace");     // hashCode now computes to a DIFFERENT value
set.contains(e);               // false — even though e is literally in the set
```

The object is stranded in the bucket matching its *old* hash code. **A type used as a `Map` key or `Set` element should be immutable** — at minimum, immutable in the fields `equals`/`hashCode` use. This is one of the strongest practical arguments for records and immutability.

### Writing `hashCode`

Hand-written, use `Objects.hash` over the *same fields* `equals` compares:

```java
@Override
public int hashCode() {
    return Objects.hash(id, salary, name);   // same fields as equals — keep them in sync
}
```

The cardinal rule when maintaining these by hand: **whenever you add a field to `equals`, add it to `hashCode`** (and vice versa). Drift between the two reintroduces the lost-entry bug. Records remove the risk entirely — the compiler keeps them in lockstep over the components. Prefer records for value types; reach for hand-written versions only when you cannot.

## `Comparable` — natural ordering

Equality answers "same or not." Ordering answers "which comes first." `Comparable<T>` gives a type its **natural ordering** — the one, intrinsic, canonical sort order:

```java
public final class Version implements Comparable<Version> {
    private final int major, minor;

    @Override
    public int compareTo(Version other) {
        int byMajor = Integer.compare(this.major, other.major);
        return byMajor != 0 ? byMajor : Integer.compare(this.minor, other.minor);
    }
}
```

`compareTo` returns a *sign*, not a magnitude:

- **negative** — `this` comes before `other`
- **zero** — equal in this ordering
- **positive** — `this` comes after `other`

Implementing `Comparable` is what lets a type drop into `TreeSet`/`TreeMap` and `Collections.sort` with no extra argument. `Integer`, `String`, `BigDecimal`, `LocalDate` all do.

### The subtraction trap

The seductive one-liner `return this.value - other.value;` is **wrong** for `int` fields. If `value` can be large or negative, the subtraction *overflows* and the sign flips — `compareTo` returns "before" when it means "after." Always use `Integer.compare(a, b)` (and `Long.compare`, `Double.compare`). They are overflow-safe and say what they mean.

### `compareTo` consistency with `equals`

`compareTo` returning `0` means "equal *for ordering*." The contract *strongly recommends* this agree with `equals` — `x.compareTo(y) == 0` ⟺ `x.equals(y)` — and the recommendation has teeth, because **sorted collections use `compareTo`, not `equals`, to decide identity.** The famous violator is `BigDecimal`:

```java
new BigDecimal("1.0").equals(new BigDecimal("1.00"))      // false — different scale
new BigDecimal("1.0").compareTo(new BigDecimal("1.00"))   // 0    — equal value
```

Consequence: a `HashSet<BigDecimal>` can hold both `1.0` and `1.00` (distinct by `equals`), but a `TreeSet<BigDecimal>` treats them as one element and keeps only the first. Same values, two collections, different contents. Not a bug — a documented inconsistency you must *know*. When you write your own `Comparable`, keep `compareTo` consistent with `equals` unless you have a `BigDecimal`-grade reason and document it loudly.

## `Comparator` — ordering as a separate object

`Comparable` bakes *one* order into the type. But you often need *several* orders, or an order for a type you do not own, or a context-specific order that has no business being "natural." That is `Comparator<T>` — ordering as a standalone, passable object:

```java
List<Employee> staff = ...;
staff.sort(new Comparator<Employee>() {
    public int compare(Employee a, Employee b) {
        return a.name().compareTo(b.name());
    }
});
```

Nobody writes them like that anymore. The factory and combinator methods build them declaratively:

```java
Comparator<Employee> byName = Comparator.comparing(Employee::name);
Comparator<Employee> bySalary = Comparator.comparingInt(Employee::salary);
```

The toolkit:

| Method | Builds |
|---|---|
| `comparing(keyExtractor)` | Order by a key (e.g. `Employee::name`). |
| `comparingInt` / `comparingLong` / `comparingDouble` | Same, for a primitive key — **avoids boxing**. |
| `thenComparing(...)` | A tie-breaker, applied only when the prior comparator returns `0`. |
| `reversed()` | Flips the whole comparator. |
| `naturalOrder()` / `reverseOrder()` | The element's own `Comparable` order. |
| `nullsFirst(cmp)` / `nullsLast(cmp)` | Wrap a comparator to tolerate `null` elements. |

### Chaining — multi-key sort

`thenComparing` is how you express "by X, then by Y, then by Z." Each link is consulted only when the ones before it tie. To sort employees **by department ascending, then salary descending, then name ascending**:

```java
Comparator<Employee> order =
    Comparator.comparing(Employee::department)
              .thenComparing(Comparator.comparingInt(Employee::salary).reversed())
              .thenComparing(Employee::name);

staff.sort(order);
```

The one subtlety worth slowing down for: **`reversed()` reverses everything to its left.** To reverse *only the salary key*, you must reverse the salary comparator *before* handing it to `thenComparing` — `comparingInt(Employee::salary).reversed()` as its own argument — exactly as above. Writing `.thenComparing(Employee::salary).reversed()` would reverse the department ordering too. Parenthesize deliberately.

---

## `Comparator` must be a *total order*

A comparator (and a `compareTo`) must define a **total order**, and the implementation actually checks. The rules:

- **Antisymmetric** — `compare(a, b)` and `compare(b, a)` have opposite signs.
- **Transitive** — `a < b` and `b < c` ⟹ `a < c`.
- **Consistent** — `compare(a, b) == 0` ⟹ `a` and `b` compare *identically against every other element*.

Violate them and Java's sort (`TimSort`) detects the contradiction mid-sort and throws:

```
java.lang.IllegalArgumentException: Comparison method violates its general contract!
```

This is a *real* production exception with a confusing message. The usual causes: the int-subtraction overflow trap from earlier; a comparator built on a mutable field that changes during the sort; or a hand-rolled comparator with an inconsistent branch. When you see that message, audit the comparator — the data is rarely the problem.

(Aside: Java's sorts are **stable** — elements that compare equal keep their input order. Stability is what lets a *chained* comparator behave predictably, and it is why a single well-built `thenComparing` chain is cleaner than sorting three times in sequence.)

---

## `Comparable` or `Comparator` — which, and where

| Use `Comparable` | Use `Comparator` |
|---|---|
| There is *one* obvious, intrinsic ordering | There are several orderings, or it is context-specific |
| You own the type | You do not own the type |
| The order is part of the type's identity (`Version`, `LocalDate`) | The order is a property of *this use site* (this report, this screen) |

Decision rule: implement `Comparable` only when the ordering is genuinely *the* ordering for the type — something a stranger would predict. "Sort employees by salary" is **not** that — employees have no inherent order, and a different screen will want department or hire date. That ordering belongs in a `Comparator` at the call site. Forcing a debatable natural order onto a type via `Comparable` is a design smell; a type can perfectly well have *no* natural ordering and offer only comparators.

## DIY Exercise

Sort a `List<Employee>` two ways and feel where each tool belongs. Standard `src/main/java` + `src/test/java` layout with JUnit tests.

`Employee` has at least `department` (`String`), `salary` (`int`), and `name` (`String`).

### Part 1 — the chained `Comparator`

Sort by **department ascending, then salary descending, then name ascending**, using `Comparator.comparing` / `comparingInt` / `thenComparing` / `reversed`. Get the salary-only reversal right — reverse *just* the salary key, leaving department and name ascending. Write a JUnit test with employees that tie on department (to exercise the salary tiebreak) and tie on department *and* salary (to exercise the name tiebreak), and assert the exact resulting order.

### Part 2 — `Comparable`

Now make `Employee implements Comparable<Employee>` with that same three-key order as its `compareTo`, and sort with the no-argument `Collections.sort` / `List.sort(null)`. Implement `compareTo` *without* the subtraction trap. Assert the result matches Part 1 exactly.

### Part 3 — `equals` / `hashCode`

Give `Employee` a correct `equals`/`hashCode` (by `id`, if you add one, or by the natural-key fields). Drop your employees into a `HashSet` and a `HashMap` key and prove dedup/lookup work. Then *deliberately* delete the `hashCode` override, rerun the `HashMap` lookup test, and watch it fail — see the lost-entry bug with your own eyes before you restore the override.

### Things to think about

- Part 1 put the ordering in a `Comparator`; Part 2 put it in `compareTo`. Which belongs in real code, and why is "sort by salary descending" a poor candidate for an employee's *natural* order?
- In the chained comparator, what *exactly* does `.thenComparing(Employee::salary).reversed()` sort by — and how does it differ from `.thenComparing(comparingInt(Employee::salary).reversed())`? Build both and diff the output.
- In Part 3, before you ran it — *which bucket* did `put` use and which did `get` check? Explain the lost entry in terms of buckets and the fact that `equals` was never called.
- If `Employee` were mutable and you changed an employee's `name` *after* adding it to a `HashSet` keyed partly on `name`, what happens to `contains`? Tie this to 3.3's advice on what makes a good `Map` key.
- Rewrite `Employee` as a `record`. What do you no longer have to write — and what does the record's generated `equals`/`hashCode` compare? Does the record give you `compareTo` too? (It does not — note why, and what you would still write by hand.)
- Suppose `salary` were a `BigDecimal`. How does the `1.0`-vs-`1.00` inconsistency change what a `TreeSet<Employee>` ordered by salary would contain versus a `HashSet<Employee>`?
