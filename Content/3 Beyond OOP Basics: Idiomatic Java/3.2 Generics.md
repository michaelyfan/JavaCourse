# 3.2 Generics

You have already used generics — `List<String>`, the `Repository<T, ID>` interface from 1.3, every `assertEquals` overload. This submodule is about *writing* them and, more importantly, understanding the one fact that explains every confusing thing generics do: **they exist only at compile time.** Get erasure, and wildcards stop being mysterious.

---

## Why generics exist

Before Java 5, a `List` held `Object`. The cost was paid on the way out:

```java
List names = new ArrayList();   // pre-2004 Java
names.add("Ada");
String first = (String) names.get(0);   // cast required — and unchecked
names.add(42);                          // compiles fine. nothing stops you.
String second = (String) names.get(1);  // ClassCastException at RUNTIME
```

The collection had no idea what it was supposed to hold, so the compiler could not help. Every read was a manual cast, and a wrong element was a runtime crash far from the line that inserted it.

Generics move that knowledge into the type system. `List<String>` is a promise the *compiler* enforces: only `String` goes in, `String` comes out, no cast, and `names.add(42)` is a compile error — caught at the keystroke, not in production.

> Generics turn a class of runtime `ClassCastException`s into compile errors. That is the entire point. Everything else is mechanics.

---

## Generic classes

A type parameter is a placeholder, declared in angle brackets after the class name, that stands in for a real type chosen by each user of the class:

```java
public class Box<T> {
    private T value;

    public Box(T value) { this.value = value; }

    public T get() { return value; }
    public void set(T value) { this.value = value; }
}
```

`T` is not a type — it is a *parameter*. `Box<String>` and `Box<Integer>` are the two real types you get by substituting an argument. Inside the class, `T` behaves like an unknown type: you can declare fields and parameters of type `T`, return `T`, accept `T` — but you cannot do anything that needs to know what `T` *is* (no `new T()`, no `T.class` — the erasure section explains why).

The conventional single-letter names carry meaning; use them:

| Name | Stands for |
|---|---|
| `T` | Type (a general one) |
| `E` | Element (of a collection) |
| `K`, `V` | Key, Value (of a map) |
| `R` | Result / return type |
| `N` | Number |

A class can take several: `class Pair<A, B>`, `interface Map<K, V>`.

### The diamond

When the type is already obvious from the left side, the diamond `<>` lets you omit it on the right (Java 7+):

```java
Map<String, List<Order>> orders = new HashMap<>();   // not new HashMap<String, List<Order>>()
```

The compiler infers the arguments from the declared type. Repeating them is just noise.

## Generic methods

A *method* can declare its own type parameters, independent of any the class declares. The parameter list goes before the return type:

```java
public static <T> T firstOrNull(List<T> list) {
    return list.isEmpty() ? null : list.get(0);
}
```

`<T>` after `static` (and before `T`, the return type) introduces the parameter; it is scoped to this one method. At the call site you almost never write it — the compiler infers `T` from the argument:

```java
String s = firstOrNull(List.of("a", "b"));   // T inferred as String
```

When inference cannot work it out (rare — usually an empty-collection factory), you can supply an explicit *type witness*:

```java
List<String> empty = Collections.<String>emptyList();
```

A generic method is the right tool when the type relationship is *per-call*, not *per-instance*. `firstOrNull` does not need the whole class to be generic — only this one method cares about `T`.

## Bounded type parameters

`<T>` alone means "any type" — so inside the class you can only call `Object` methods on it. A **bound** narrows that and unlocks the API of the bound:

```java
public static <T extends Comparable<T>> T max(List<T> list) {
    T best = list.get(0);
    for (T item : list) {
        if (item.compareTo(best) > 0) {   // legal: T is known to have compareTo
            best = item;
        }
    }
    return best;
}
```

`<T extends Comparable<T>>` reads "T, whatever it is, must implement `Comparable<T>`." That promise is what makes `item.compareTo(best)` compile. Without the bound, `T` has no `compareTo` and the method cannot be written.

Note `extends` is used for both classes and interfaces here — there is no `implements` in a bound. And the bound can be self-referential: `T extends Comparable<T>` ("T is comparable *to itself*") is a standard, if initially odd-looking, idiom — you will see it again in 3.4.

A bound can also be a **class**, and can combine several types with `&`:

```java
<T extends Number>                          // T is a Number or subtype
<T extends Number & Comparable<T>>           // T is both — at most one class, then interfaces
```

## The invariance problem

Here is the fact that surprises everyone, and the reason wildcards exist:

```java
List<String> strings = new ArrayList<>();
List<Object> objects = strings;   // COMPILE ERROR — even though String IS-A Object
```

`String` is a subtype of `Object`, but `List<String>` is **not** a subtype of `List<Object>`. Generic types are **invariant**. And this is not a compiler being pedantic — it is preventing a real disaster. *If* the assignment were allowed:

```java
objects.add(42);                  // objects is typed List<Object> — 42 looks fine
String oops = strings.get(0);     // but strings and objects are the SAME list — boom
```

You would have an `Integer` inside a `List<String>`. Invariance forbids the assignment that would make that possible.

> Arrays, by contrast, *are* covariant — `Object[] a = new String[1];` compiles. That was a known design mistake: it just moves the failure to runtime, where `a[0] = 42;` throws `ArrayStoreException`. Generics chose compile-time safety instead. Arrays and generics genuinely do not mix well — a tension the erasure section returns to.

Invariance is safe but rigid. A method that wants to accept "a list of *any* kind of number" cannot — `List<Number>` accepts only exactly `List<Number>`, not `List<Integer>`. **Wildcards** are the escape hatch.

## Wildcards: `? extends`, `? super`, and PECS

A wildcard `?` is "some specific type I am not naming." It comes in three forms.

### `? extends T` — an upper bound (a *producer*)

`List<? extends Number>` means "a `List` of some *unknown* type that is `Number` or a subtype." It accepts `List<Integer>`, `List<Double>`, `List<Number>`.

What can you do with it? You can **read**:

```java
void printAll(List<? extends Number> list) {
    for (Number n : list) {        // OK — whatever the element type is, it IS-A Number
        System.out.println(n);
    }
}
```

You **cannot write** (except `null`):

```java
list.add(1);   // COMPILE ERROR
```

Why the ban? The list might *really* be a `List<Double>`. The compiler knows only "elements are *some* subtype of `Number`" — it cannot prove `1` (an `Integer`) is the right one. So it forbids all writes. An `? extends` collection is a **producer**: things come *out* (as `Number`), nothing safe goes *in*.

### `? super T` — a lower bound (a *consumer*)

`List<? super Integer>` means "a `List` of some unknown type that is `Integer` or a *supertype*." It accepts `List<Integer>`, `List<Number>`, `List<Object>`.

This is the mirror image. You can **write** an `Integer`:

```java
void addNumbers(List<? super Integer> list) {
    list.add(1);      // OK — whatever the list is, an Integer fits (it's a supertype list)
    list.add(2);
}
```

You **cannot usefully read** — the best the compiler can give you is `Object`:

```java
Object o = list.get(0);    // OK, but only as Object
Integer i = list.get(0);   // COMPILE ERROR — element could be any supertype of Integer
```

An `? super` collection is a **consumer**: things go *in*, and what comes *out* is only knowable as `Object`.

### PECS — Producer Extends, Consumer Super

The mnemonic, from *Effective Java*:

> **P**roducer — **E**xtends. **C**onsumer — **S**uper.

If a parameter *produces* values for your code (you read from it), bound it with `extends`. If it *consumes* values from your code (you write to it), bound it with `super`. The canonical example is a copy:

```java
public static <T> void copy(List<? extends T> src, List<? super T> dst) {
    for (T item : src) {     // src produces T  -> extends
        dst.add(item);       // dst consumes T  -> super
    }
}
```

`src` is the producer — `extends`. `dst` is the consumer — `super`. This single signature copies a `List<Integer>` into a `List<Number>`, a `List<String>` into a `List<Object>`, and so on — none of which the invariant `copy(List<T>, List<T>)` could do. The standard library's own `Collections.copy` has exactly this signature, for exactly this reason.

### Unbounded `?`

A plain `List<?>` is "a list of *something*." Use it when the method genuinely does not care about the element type:

```java
static int size(List<?> list) { return list.size(); }
```

You can read elements as `Object` and you cannot add anything (except `null`) — the same producer-side restriction, with no upper bound to read against beyond `Object`.

### When *not* to use a wildcard

Wildcards belong on **method parameters**. A `return` type should almost never be a wildcard — it just forces the caller to deal with one. And if a type parameter appears in *only one place* in a method signature, that place often wants a wildcard rather than a named parameter. `void printAll(List<? extends Number> l)` is better than `<T extends Number> void printAll(List<T> l)` — `T` is never used again, so naming it is pointless ceremony.

## Type erasure — the fact under everything

Here is the mechanism that explains every restriction generics impose: **generics are a compile-time-only feature.** The compiler uses them to type-check your code and insert casts — and then **erases** them. At runtime the type arguments are gone.

`Box<String>` and `Box<Integer>` are, at runtime, both just `Box`. A `List<String>` is, at runtime, just a `List`. The type parameter `T` is erased to its bound — `Object` for unbounded `T`, `Number` for `<T extends Number>`. This was a deliberate Java 5 choice for backward compatibility: pre-generics `.class` files and new generic ones had to interoperate, so generics could not change the runtime representation.

Proof you can run:

```java
List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();
System.out.println(a.getClass() == b.getClass());   // true — both are class ArrayList
```

The cost of those casts is *not* paid by you — the compiler inserts them. `String s = list.get(0)` compiles to `String s = (String) list.get(0)`. The cast is real; you just do not type it.

### What erasure forbids

Every one of these is a compile error, and now you know the reason — *the type does not exist at runtime*:

| Forbidden | Why |
|---|---|
| `new T()` | The runtime has no idea what `T` is — no constructor to call. |
| `new T[10]` | Same — and arrays need a real reified component type. |
| `obj instanceof T` | `instanceof` is a *runtime* check; `T` is gone by then. |
| `T.class` | There is no `Class` object for an erased parameter. |
| `catch (MyException<T> e)` | Exception matching is a runtime check; the type argument is invisible. |
| `class A<T> { static T x; }` | A `static` field is shared across *all* instantiations — there is no single `T`. |
| Two overloads `f(List<String>)` / `f(List<Integer>)` | Both erase to `f(List)` — same signature, name clash. |

### The `Class<T>` token workaround

When you genuinely need the runtime type — to construct an instance, to call `isInstance` — you cannot recover it from `T`. You pass it in explicitly as a **type token**:

```java
public static <T> T fromJson(String json, Class<T> type) {
    // 'type' carries the runtime Class that 'T' lost to erasure
    ...
}

Order o = fromJson(text, Order.class);
```

This is exactly why `Optional.empty()` needs a witness sometimes, why Jackson's `readValue` takes a `Class<T>`, and why JUnit's `assertThrows` takes `IllegalArgumentException.class` rather than a bare type parameter. Once you see erasure, that pattern is everywhere.

### Heap pollution and `@SafeVarargs`

A generic varargs parameter (`T... items`) is secretly a `T[]` — and arrays cannot be generic. The compiler creates one anyway and warns about *heap pollution*: the possibility that the array ends up holding the wrong type. If your method only ever *reads* the varargs (never stores the array, never writes to it), it is safe, and you assert that with `@SafeVarargs` on the method to silence the warning. Only apply it when you have actually checked.

## Raw types — a legacy hazard

A **raw type** is a generic type used with no arguments — `List` instead of `List<String>`. It exists only so pre-2004 code still compiles. Using one is not "generics off for that variable" — it is **generics off for everything you do through it**:

```java
List raw = new ArrayList<String>();
raw.add(42);                  // no error — raw type, no checking
String s = raw.get(0);        // unchecked warning, then ClassCastException at runtime
```

Never declare a raw type in new code. The honest "I do not care about the element type" is `List<?>` — which keeps the safety (you still cannot `add` junk) while expressing the same indifference. If you must touch raw-typed legacy code and have *proven* a cast is sound, `@SuppressWarnings("unchecked")` silences the warning — on the *narrowest possible scope* (a single statement, ideally its own local variable), never a whole method, and ideally with a comment explaining why it is safe.

## DIY Exercise

Build a small generic utility, in the `src/main/java` + `src/test/java` layout.

### Layout

The exercise has **more than one top-level type, so more than one file** — every top-level class lives in its own `.java` file. Put them all in one package, e.g. `pairs`:

```
src/main/java/
  pairs/
    Pair.java      // the generic data carrier
    Pairs.java     // the static-method utility class
src/test/java/
  pairs/
    PairsTest.java
```

- **`Pair`** is a *generic class* — `Pair<A, B>`. Every `Pair` object really does hold an `A` and a `B`, so the type parameters belong on the class.
- **`Pairs`** is a *utility class* — no instances, only `static` methods. `zip` lives here; `copy` and `max` can share it. It is named in the plural by the standard-library convention for static-method holders (`Collection`/`Collections`, `Path`/`Paths`, `Object`/`Objects`). You never write `new Pairs(...)` — give it a `private` constructor to say so.
- `Pairs` is deliberately **not** a generic class. Class-level type parameters parameterize *instances*, and a utility class has none for them to bind to. Each method carries its own parameters instead: `zip` declares `<A, B>`, `copy` and `max` declare `<T>` (the "Generic methods" section above).

### Tasks

1. **`Pair<A, B>`** — an immutable two-value carrier with `A first()` and `B second()`. Consider: a `record` (1.5) gives you this in one line — write it as a record, then also sketch the plain-class version and note what the record saved you. Either way, the type takes *two* parameters.

2. **`Pairs.zip(List<A>, List<B>)`** — a generic *method* returning `List<Pair<A, B>>`, pairing elements by index. Decide what to do when the lists differ in length (truncate to the shorter? throw `IllegalArgumentException`? — pick one and defend it). Note that `zip` needs its own `<A, B>` method-level parameters; the *class* `Pairs` is not generic.

3. **`copy(List<? extends T> src, List<? super T> dst)`** — implement it, then *prove the wildcards earn their place*. Write tests that:
   - copy a `List<Integer>` into a `List<Number>` and a `List<Object>`;
   - confirm (by trying it and reading the compile error) that the invariant signature `copy(List<T>, List<T>)` rejects all of those.

4. **`max`** — write `<T extends Comparable<T>> T max(List<T> list)` from the bounded-types section. Test it on `Integer`s and `String`s. Then try to call it on a `List<Object>` and read the compiler's complaint about the bound.

### Things to think about

- In `copy`, walk the PECS reasoning *out loud*: which list is the producer, which the consumer, and what specific operation would fail to compile if you swapped `extends` and `super`?
- Try to add an element to the `src` parameter inside `copy`. Read the error. Explain it in terms of "the compiler knows only a *bound*, not the exact type."
- `Pairs.zip` could have been written as a method on a generic *class* `Pairs<A, B>` instead of a generic method on a non-generic class. Why is the generic-method version better here? (Hint: how many `Pairs` *instances* do you ever need?)
- Run the `a.getClass() == b.getClass()` experiment from the erasure section with your own `Pair<String, Integer>` and `Pair<Double, Long>`. Predict the result before you run it.
- Erasure forbids `new T()`. Suppose `zip` needed to create a *default* `Pair` — how would the `Class<T>` token pattern let you do it, and why is passing the token unavoidable rather than just inconvenient?
- You wrote `max` with `<T extends Comparable<T>>`. What breaks if you weaken the bound to `<T extends Comparable<?>>`? What about plain `<T>`?
