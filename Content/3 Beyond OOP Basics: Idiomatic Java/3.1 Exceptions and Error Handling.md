# 3.1 Exceptions and Error Handling

Modules 1 and 2 built the language and a way to verify it. Module 3 shifts to *idiom* — the difference between Java that compiles and Java that another engineer reads without wincing. Error handling is the first stop because it is where well-meaning code goes wrong most quietly: a swallowed exception doesn't fail a test, it just deletes information, and the bug surfaces a week later somewhere else.

This submodule is about exceptions as a *design tool* — what to throw, what to catch, what to wrap, and what to leave alone. It uses a little file I/O for examples and the DIY; the full treatment of I/O is 4.2, so the I/O here stays deliberately shallow.

---

## The `Throwable` hierarchy

Everything you can `throw` or `catch` descends from `java.lang.Throwable`. It has two branches, and the split is the whole design:

```
Throwable
├── Error                    — unchecked. The JVM is in trouble.
└── Exception                — checked (mostly).
    └── RuntimeException      — unchecked. Your code has a bug.
```

- **`Error`** — `OutOfMemoryError`, `StackOverflowError`, `NoClassDefFoundError`. The JVM itself is failing. You do not catch these; there is nothing useful to do. Code that catches `Error` (or `Throwable`, which includes it) is almost always wrong.
- **`Exception`** minus `RuntimeException` — the **checked** exceptions: `IOException`, `SQLException`, `InterruptedException`. The compiler forces you to acknowledge them.
- **`RuntimeException`** — the **unchecked** exceptions: `NullPointerException`, `IllegalArgumentException`, `IllegalStateException`, `ClassCastException`, `IndexOutOfBoundsException`. The compiler ignores them entirely.

"Checked" and "unchecked" describe exactly one thing: **whether the compiler makes you handle it.** A checked exception must be either caught or declared in the method's `throws` clause — the code does not compile otherwise. An unchecked exception has no such requirement; it can propagate out of any method silently as far as the compiler is concerned.

---

## Checked vs. unchecked — the philosophy and the criticism

The original design intent, as Java's authors framed it:

- **Checked** = a *recoverable* condition the caller can reasonably be expected to handle. A file might not exist; a network call might fail. These are not bugs — they are foreseeable facts of the world. Forcing the caller to confront them, the argument goes, prevents the failure from being ignored.
- **Unchecked** = a *programming error*. A `null` you didn't expect, an index past the end of an array, an argument that violates a documented precondition. The fix is to *correct the code*, not to write a `catch` block.

That is the theory. The practice has not been kind to it, and the criticism is mainstream enough that you should know it:

1. **Checked exceptions don't compose.** A `Function`, a `Stream` lambda, a `Comparator` — none of their interfaces declare `throws IOException`. The moment you want to do checked-exception work inside a lambda (Module 5) you are forced to catch-and-wrap right there, which is pure noise.
2. **They leak implementation details up the call stack.** If a method `throws SQLException`, every caller, and every caller's caller, now knows there is a database behind it. Swap the database for an HTTP call and every signature in the chain changes.
3. **They pressure people into the worst possible response.** Faced with a checked exception they don't know how to handle, too many engineers write an empty `catch` block to make the compiler stop complaining. The mechanism meant to prevent ignored failures actively produces them.

The verdict of the wider ecosystem is telling: **no major language designed after Java adopted checked exceptions.** C#, Kotlin, Scala, and Swift all looked at the feature and declined. Within Java itself, modern libraries lean heavily unchecked — Spring wraps `SQLException` in an unchecked `DataAccessException` precisely to stop it leaking.

### A practical rule

You will still meet checked exceptions constantly because the standard library is full of them. But for exceptions *you define*:

> **Default to unchecked (`extends RuntimeException`).** Reach for a checked exception only when the caller realistically has a *specific, local* recovery action and you want the compiler to guarantee they at least see it.

Most of the time the honest answer is "the caller cannot recover here, it can only log and fail" — and that is an unchecked exception.

## `try` / `catch` / `finally`

The mechanics, quickly, because one corner of them is a genuine trap.

```java
try {
    risky();
} catch (IOException e) {
    // handle or translate
} catch (IllegalStateException | IllegalArgumentException e) {  // multi-catch
    // one block for several unrelated types
} finally {
    // runs no matter what — return, exception, or normal exit
}
```

- **`catch` order matters.** Catch the most specific type first. `catch (Exception e)` before `catch (IOException e)` is a compile error — the second clause is unreachable.
- **Multi-catch** (`A | B`) is for when two unrelated exception types get the *same* handling. The caught variable is effectively final and typed as the common supertype.
- **`finally` always runs** — after a `return`, after a `throw`, after a normal exit. It is the classic place for cleanup.

### The `finally` trap: never `return` (or `throw`) from `finally`

A `return` or `throw` inside `finally` *overrides* whatever the `try` block was doing — including an exception in flight:

```java
try {
    throw new IOException("disk failed");
} finally {
    return 0;   // BUG: silently swallows the IOException
}
```

The `IOException` is discarded. The method returns `0` as if nothing happened. This is one of the most effective ways to lose a failure in all of Java. **`finally` is for cleanup, not for control flow** — no `return`, no `throw`, nothing that can complete abruptly.

## `try-with-resources` and `AutoCloseable`

`finally` was, for years, how you closed resources. That code is genuinely hard to get right. Here is the pre-Java-7 idiom for reading a file:

```java
BufferedReader reader = new BufferedReader(new FileReader(path));
try {
    return reader.readLine();
} finally {
    reader.close();   // looks fine. it is not.
}
```

The bug is subtle: if `readLine()` throws an `IOException` *and then* `close()` also throws an `IOException`, the exception from `close()` **replaces** the one from `readLine()`. You lose the real failure — the disk error — and see only the close error, which is almost never the interesting one. Writing this *correctly* by hand requires a nested `try` inside the `finally`, and almost nobody did.

**`try-with-resources`** (Java 7) solves it. Any resource declared in the parentheses is closed automatically, in the right order, with the right exception precedence:

```java
try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
    return reader.readLine();
}
// reader.close() is called automatically — even on exception, even on return
```

What it gives you that the manual version did not:

- **Guaranteed close.** The resource is closed whether the block exits normally, via `return`, or via a thrown exception. No `finally` to forget.
- **Correct exception precedence.** If the body throws *and* `close()` throws, the body's exception is the one that propagates. The close exception is not discarded — it is attached as a **suppressed exception**, retrievable via `Throwable.getSuppressed()`. You see the real failure first and the cleanup failure is still there if you want it.
- **Reverse-order closing.** Multiple resources in one `try` are closed in the reverse of declaration order — the natural order for nested resources:

  ```java
  try (var in = new FileInputStream(src);
       var out = new FileOutputStream(dst)) {
      in.transferTo(out);
  }   // out.close() runs first, then in.close()
  ```

### `AutoCloseable`

`try-with-resources` works with any type that implements **`AutoCloseable`** — a one-method interface:

```java
public interface AutoCloseable {
    void close() throws Exception;
}
```

`Closeable` (from `java.io`) is a sub-interface that narrows `close()` to `throws IOException`. Anything you write that owns a resource — a connection, a pool, a lock handle — should implement `AutoCloseable` so callers get the same guarantee:

```java
class ConnectionLease implements AutoCloseable {
    @Override public void close() {
        pool.release(connection);   // close() need not throw
    }
}
```

Since Java 9, the resource can also be an already-declared *effectively final* variable, not just a fresh declaration:

```java
var reader = openReader();
try (reader) { ... }   // legal since Java 9
```

## Exception chaining: preserve the cause

A core idiom of layered code: a low-level exception is *translated* into a domain-level one as it crosses an abstraction boundary. Your `OrderService` should not throw `SQLException` — that exposes the database. It should throw an `OrderLookupException`. But translation must not destroy the original.

**Wrong** — the cause is thrown away:

```java
catch (SQLException e) {
    throw new OrderLookupException("could not load order " + id);
    //                                       ^ the SQLException, with its
    //                                         stack trace and message, is gone
}
```

When this fails in production, the stack trace stops at your `catch` block. The actual database error — connection refused? constraint violation? — is unrecoverable.

**Right** — pass the cause:

```java
catch (SQLException e) {
    throw new OrderLookupException("could not load order " + id, e);
    //                                                           ^ the cause
}
```

`Throwable` has constructors taking a `cause`, and every well-designed exception forwards it. The printed stack trace then shows the full story:

```
OrderLookupException: could not load order 4471
    at OrderService.load(OrderService.java:88)
    ...
Caused by: java.sql.SQLException: connection refused
    at ...
```

That `Caused by:` chain is the single most useful thing in a production log. Always preserve it. (If you have an exception already constructed without a cause, `initCause(e)` attaches one after the fact — but the constructor argument is cleaner.)

### Writing a custom exception

A custom exception is a small, boring class. The one rule: provide the cause-accepting constructors so callers *can* chain.

```java
public class OrderLookupException extends RuntimeException {
    public OrderLookupException(String message) {
        super(message);
    }
    public OrderLookupException(String message, Throwable cause) {
        super(message, cause);
    }
}
```

Add fields if the *handler* needs structured data (`orderId`, an error code) rather than parsing the message string. Otherwise keep it minimal. Choosing `extends RuntimeException` vs. `extends Exception` is the checked/unchecked decision from earlier — default unchecked.

## Anti-patterns

These are the failure modes that turn up in real code review. Each one is a way of *losing information* about a failure.

### 1. Swallowing the exception

```java
try {
    save(record);
} catch (IOException e) {
    // nothing here
}
```

An empty `catch` block claims "this can never happen, or if it does it doesn't matter" — and that claim is almost always false. The program continues as if the save succeeded when it didn't. A bare `e.printStackTrace()` is only marginally better: it dumps to `System.err`, which in a real deployment nobody is watching, and then *also continues as if nothing happened*. If you genuinely can ignore an exception, prove it with a comment that says *why* — and that comment had better be convincing.

### 2. Catching too broadly

```java
try {
    return Integer.parseInt(input);
} catch (Exception e) {        // catches NumberFormatException — and everything else
    return 0;
}
```

You meant to handle a bad number. `catch (Exception e)` *also* catches a `NullPointerException` from a bug three lines into a helper, a `ClassCastException`, anything — and quietly turns all of it into `0`. Catch the **narrowest type that names the situation you actually understand** — here, `NumberFormatException`. Catching `Throwable` is worse still: it swallows `Error`, including `OutOfMemoryError`.

### 3. Throwing raw `Exception` (or `Throwable`)

```java
public void process() throws Exception { ... }   // throws *what*?
```

A method that declares `throws Exception` tells the caller nothing and forces them to either catch `Exception` (anti-pattern 2) or propagate the vagueness upward. Declare the *specific* types you actually throw. The `throws` clause is documentation; `throws Exception` is documentation that says "good luck."

### 4. Exceptions as control flow

```java
try {
    int i = 0;
    while (true) {
        process(array[i++]);   // "loop until ArrayIndexOutOfBoundsException"
    }
} catch (ArrayIndexOutOfBoundsException e) {
    // done
}
```

This "works" and is wrong twice over. It is *unreadable* — the exit condition is invisible. And it is *slow*: constructing an exception fills in a stack trace by walking the call stack, which is expensive relative to an `i < array.length` check. Exceptions are for the **exceptional** — conditions outside the normal flow. A loop ending is not exceptional. (For a value that may legitimately be absent, the answer is often `Optional` — 4.3 — not an exception at all.)

### 5. Log-and-rethrow

```java
catch (IOException e) {
    log.error("save failed", e);
    throw new StorageException("save failed", e);   // will be logged AGAIN higher up
}
```

Each exception should be logged **once**, at the level that actually handles it (or at the top, if it reaches the top). Logging *and* rethrowing produces the same failure in the log two, three, four times with different stack depths — and now you cannot tell whether you had one failure or four. Decide per `catch`: either *handle* it (which may include logging) or *translate and rethrow* it — not both.

## A quick word on `InterruptedException`

You will meet `InterruptedException` in Module 6, but the wrong reflex forms early, so: when you catch `InterruptedException` and do not rethrow it, **restore the interrupt flag**:

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // re-set the flag you just cleared
    // ... then handle
}
```

Catching `InterruptedException` *clears* the thread's interrupted status. Swallowing it without restoring the flag hides a cancellation request from the rest of the stack. This is the single most common concurrency bug in otherwise-careful code. Filed here so the habit is in place before 6.x needs it.

## DIY Exercise

Build a `FileLineCounter` that counts the lines in a text file, using everything above.

This is the first DIY that touches I/O. Keep it minimal — a `BufferedReader` over a file, `readLine()` in a loop until it returns `null`. The full I/O toolkit is 4.2; you need only enough to have a real resource to manage.

Use the `src/main/java` + `src/test/java` layout from Module 2.

### Tasks

1. **Define a domain exception.** Write a `CountingException` — decide checked vs. unchecked and be ready to defend the choice. Give it both a `(String)` and a `(String, Throwable)` constructor.

2. **Write `FileLineCounter`** with a method `long countLines(Path path)`:
   - Open the file with `try-with-resources` so the handle is closed on every exit path.
   - Catch the low-level `IOException` and rethrow it wrapped in a `CountingException` — *with the original as the cause.*
   - The wrapper message should name the file that failed.

3. **Prove no handle leaks.** Write a test that points `countLines` at a file that does not exist. Assert it throws `CountingException`, then assert via `getCause()` that the cause is the original `IOException` (likely a `NoSuchFileException`/`FileNotFoundException`). The fact that `try-with-resources` ran `close()` before the exception propagated is the leak protection — there is no `finally` for you to forget.

4. **Happy path.** A test that counts the lines of a small fixture file you create in the test (write it in `@BeforeEach`, delete it in `@AfterEach`, or use JUnit's `@TempDir`). Assert the exact count.

5. **See suppression in action.** This is the instructive part. Write a tiny `AutoCloseable` whose `close()` deliberately throws. Use it as a resource in a `try-with-resources` whose *body also* throws. Catch the exception that escapes and inspect `getSuppressed()`. Confirm with your own eyes: the body's exception is the one you caught, and the close exception is in the suppressed array — not lost, not in front.

### Things to think about

- You chose checked or unchecked for `CountingException`. Walk the decision: can a *caller* of `countLines` realistically recover from a missing file? If yes, what would that recovery look like — and does that change your answer?
- In task 3, what *exactly* would be lost if you had written `throw new CountingException("could not count " + path)` with no cause argument? Be specific about what disappears from a production stack trace.
- Rewrite the `try-with-resources` as a pre-Java-7 `finally`-based close. Now make it *correct* — the body exception must win over a `close()` exception. How much code does that take? That gap is why the language feature exists.
- `BufferedReader` implements `Closeable`, whose `close()` is declared `throws IOException`. If you wrote a resource whose `close()` threw a *checked* exception of some other type, what would `try-with-resources` require of the surrounding method? (Hint: `AutoCloseable.close()` is declared `throws Exception`.)
- Anti-pattern 4 was "exceptions as control flow." Is `readLine()` returning `null` at end-of-file an example of *avoiding* that anti-pattern? What would the API look like if end-of-file were signalled by an exception instead, and why is `null` (or, better, `Optional` — 4.3) the right call here?
