# 3.3 The Collections Framework

3.2 gave you the type machinery; the Collections Framework is the standard library's biggest, most-used application of it. You have reached for `List` and `Map` already. This submodule is about reaching for the *right* one — and about the handful of behaviours (iteration, immutability, ordering) that bite people who picked a collection by habit.

---

## The shape of the framework

Two separate hierarchies. The first is rooted at **`Iterable`** — anything you can run a for-each loop over — and then **`Collection`**, the supertype of every "bag of elements":

```
Iterable
└── Collection
    ├── List      — ordered, indexed, duplicates allowed
    ├── Set       — no duplicates
    └── Queue     — ordered for processing; Deque extends it (both ends)
```

**`Map` is the second hierarchy, and it is *not* a `Collection`.** A map is pairs of keys and values, not a bag of elements — it does not implement `Iterable`, you cannot for-each it directly. That separation is deliberate, and forgetting it is a common beginner stumble.

The golden rule throughout: **declare the interface, instantiate the implementation.**

```java
List<String> names = new ArrayList<>();      // not ArrayList<String> names
Map<String, Integer> counts = new HashMap<>();
```

The variable, the field, the parameter, the return type — all typed as the *interface*. Only the `new` names a concrete class. This keeps the choice of implementation a local, swappable decision instead of something baked into every signature that touches the value.

## `List` — ordered, indexed, duplicates

A `List` is a positional sequence. Two implementations matter.

| | `ArrayList` | `LinkedList` |
|---|---|---|
| Backing | A resizable array | A doubly-linked chain of nodes |
| `get(i)` / `set(i)` | O(1) | O(n) — walk from an end |
| `add` at end | O(1) amortized | O(1) |
| `add`/`remove` in middle | O(n) — shift elements | O(1) *once you are there* — but getting there is O(n) |
| Memory | Compact; one array | A node object + 2 pointers per element |

The instinct is "lots of insertions → `LinkedList`." **Resist it.** `ArrayList` wins in practice almost always, because:

- Reaching the insertion point in a `LinkedList` is itself an O(n) walk — the O(1) splice is only free if you already hold the node.
- `ArrayList`'s array is *contiguous* in memory, so iteration is cache-friendly. `LinkedList`'s nodes are scattered across the heap; every step is a likely cache miss. On modern hardware this dominates, and `ArrayList` routinely beats `LinkedList` even at tasks the big-O table says `LinkedList` should win.

> **Default to `ArrayList`.** `LinkedList`'s honest niche is being used *as a `Deque`* (queue from both ends) — and even there `ArrayDeque` is usually better. It is rare to have a real reason to pick `LinkedList`.

Sizing tip: if you know roughly how many elements are coming, `new ArrayList<>(expectedSize)` pre-allocates the array and skips the grow-and-copy cycles.

## `Set` — no duplicates

A `Set` rejects duplicate elements (by `equals` — which is why 3.4 on the equality contract matters here). Three implementations, distinguished by **iteration order**:

| Implementation | Order when iterated | `add`/`contains` | Needs |
|---|---|---|---|
| `HashSet` | **None** — arbitrary, can change between runs | O(1) | good `hashCode`/`equals` |
| `LinkedHashSet` | **Insertion order** | O(1) | good `hashCode`/`equals` |
| `TreeSet` | **Sorted** | O(log n) | `Comparable` elements or a `Comparator` |

`HashSet` is the default. Choose `LinkedHashSet` when you want predictable, reproducible iteration (it costs only a little memory for the linkage — and reproducibility is worth it: a test that iterates a `HashSet` and asserts on order is *flaky*). Choose `TreeSet` when you need the elements *sorted* or need range queries (`first`, `last`, `headSet`, `tailSet`, `ceiling`, `floor`).

## `Map` — keys to values

The single most-used data structure in backend Java. Same three-way split as `Set`, on the *keys*:

| Implementation | Key order | `get`/`put` | Notes |
|---|---|---|---|
| `HashMap` | None | O(1) | The default. |
| `LinkedHashMap` | Insertion order — *or access order* | O(1) | The access-order mode is the LRU hook (see DIY). |
| `TreeMap` | Sorted by key | O(log n) | Range queries: `firstKey`, `floorKey`, `subMap`, ... |

A glance under `HashMap`'s hood, because it explains the `equals`/`hashCode` dependency: keys are distributed into *buckets* by `hashCode()`. A lookup hashes the key to find the bucket, then walks that bucket comparing with `equals()`. Good hashing spreads keys evenly so buckets stay tiny; a bad `hashCode` that returns a constant collapses every key into one bucket and turns the map into an O(n) linked list. (Since Java 8, a bucket that grows pathologically long *treeifies* into a red-black tree, capping the worst case at O(log n) — a safety net, not a substitute for a real `hashCode`.)

### Map methods worth knowing

Plain `get`/`put` leave a lot of clumsy code on the table. These remove it:

```java
counts.getOrDefault(key, 0)                   // value, or a default if absent — no null check

counts.putIfAbsent(key, 0)                    // set only if not already present

counts.merge(word, 1, Integer::sum)           // the idiomatic word-count: insert 1, or add 1

map.computeIfAbsent(key, k -> new ArrayList<>())  // lazily build a value; perfect for multimaps
   .add(item);

map.forEach((k, v) -> ...)                    // iterate pairs without entrySet boilerplate
```

`merge` and `computeIfAbsent` in particular collapse the classic "get, check null, create, put" four-liner into one expression. Learn them — they are everywhere in idiomatic Java.

## `Queue` and `Deque`

A `Queue` orders elements for *processing*; a `Deque` ("deck") is a double-ended queue — add and remove at *both* ends, so it serves as both a FIFO queue and a LIFO stack.

- **`ArrayDeque`** — the default for both queue and stack use. Array-backed, fast, no per-node overhead.
- **`PriorityQueue`** — not FIFO: `poll()` always returns the *smallest* element (by `Comparable` or a `Comparator`). A binary heap. The tool for "process highest-priority first."
- **`Stack`** — a legacy class from Java 1.0. It extends `Vector` and is synchronized on every operation. **Do not use it.** For LIFO, use `ArrayDeque` (`push`/`pop`/`peek`). `Stack` survives only for backward compatibility.

Each `Queue` operation has two forms — one that throws on failure, one that signals with a return value:

| | Throws on failure | Returns special value |
|---|---|---|
| Insert | `add(e)` | `offer(e)` → `false` |
| Remove head | `remove()` | `poll()` → `null` |
| Inspect head | `element()` | `peek()` → `null` |

Pick the throwing form when an empty/full queue is genuinely a bug; pick the return-value form when it is an expected, ordinary state.

## Picking one — a decision tree

```
Need key → value pairs?
  └─ yes → Map
        keys sorted? ............ TreeMap
        remember insertion order? LinkedHashMap
        otherwise ............... HashMap

Need to forbid duplicates?
  └─ yes → Set
        sorted? ................. TreeSet
        remember insertion order? LinkedHashSet
        otherwise ............... HashSet

Process from the ends (FIFO / LIFO / priority)?
  └─ yes → Deque (ArrayDeque) — or PriorityQueue if "smallest first"

Otherwise — an ordered, indexed sequence:
  └─ List → ArrayList   (you will almost never want LinkedList)
```

Two reflexes worth building: when in doubt it is `ArrayList` or `HashMap`; and "I need order" splits three ways — *insertion* order (`Linked*`), *sorted* order (`Tree*`), or *don't care* (`Hash*`) — so always ask *which* order you mean.

## Immutable and unmodifiable collections

"This collection should not change" has three different mechanisms, and they are not equivalent.

### `List.of`, `Set.of`, `Map.of` — genuinely immutable (Java 9+)

```java
List<String> colors = List.of("red", "green", "blue");
Map<String, Integer> limits = Map.of("max", 100, "min", 0);
```

These are **truly immutable** — every mutator (`add`, `remove`, `set`, `clear`) throws `UnsupportedOperationException`. They are also compact and a good default for constants and return values. Three sharp edges:

- They **reject `null`** — `List.of("a", null)` throws `NullPointerException`. (`HashMap`/`ArrayList` permit nulls; these do not.)
- `Set.of` / `Map.of` throw on **duplicate elements / keys** at construction.
- `Map.of` only goes up to 10 pairs by overloads; beyond that use `Map.ofEntries(entry(k, v), ...)`.

`List.copyOf(existing)` makes an immutable *snapshot* of an existing collection — a defensive copy in one call.

### `Collections.unmodifiableList` — an unmodifiable *view*, not a copy

```java
List<String> backing = new ArrayList<>(List.of("a", "b"));
List<String> view = Collections.unmodifiableList(backing);

view.add("c");        // throws — you cannot mutate through the view
backing.add("c");     // succeeds — and now view shows ["a","b","c"] too!
```

This is the trap. `unmodifiableXxx` wraps the *same backing collection*. It blocks mutation *through the wrapper*, but the original reference is still live and changes through it **show through the view**. It is not a copy. If you hand a caller an `unmodifiableList` but keep mutating the backing list, you have given them a moving target. To hand out a genuinely frozen value, copy *then* wrap — or just use `List.copyOf`.

### `Arrays.asList` — fixed-size, array-backed

```java
List<Integer> list = Arrays.asList(1, 2, 3);
list.set(0, 9);    // OK — set is allowed
list.add(4);       // throws — the size is fixed (it is backed by the array)
```

`Arrays.asList` is *fixed-size*, not immutable: `set` works, `add`/`remove` do not, and writes are reflected straight into the backing array. A different beast from `List.of` — know the distinction.

### Defensive copying

The practical upshot, and a habit to build now: when a constructor *accepts* a collection or a getter *returns* one, copy it. Otherwise a caller holds a reference to your internal state and can mutate it behind your back — breaking exactly the encapsulation 1.1 was about.

```java
public OrderBatch(List<Order> orders) {
    this.orders = List.copyOf(orders);   // caller's later edits cannot reach us
}
public List<Order> orders() {
    return orders;                       // already immutable — safe to hand out as-is
}
```

## Iteration pitfalls

### `ConcurrentModificationException`

Modify a collection's *structure* while a for-each loop is iterating it, and you get this — despite the name, with **no concurrency involved**, on a single thread:

```java
for (String name : names) {
    if (name.isBlank()) {
        names.remove(name);   // ConcurrentModificationException
    }
}
```

The standard collections' iterators are **fail-fast**: they keep a `modCount` and check, on each step, that the collection has not been structurally changed out from under them. The for-each loop is sugar over an `Iterator`, so removing via the *collection* invalidates the loop's iterator and it throws on the next step. This is a *feature* — failing loudly and immediately beats silently skipping an element or looping forever. The correct ways to remove during iteration:

```java
names.removeIf(String::isBlank);              // best — concise and clear

Iterator<String> it = names.iterator();        // explicit iterator: its own remove() is safe
while (it.hasNext()) {
    if (it.next().isBlank()) it.remove();
}
```

`removeIf` is the idiomatic answer. The explicit-iterator form is what `removeIf` does underneath, and is the tool when the removal logic is too involved for a single predicate.

### Fail-fast vs. fail-safe

- **Fail-fast** — `ArrayList`, `HashMap`, `HashSet`, ... — detect concurrent structural modification and throw `ConcurrentModificationException`. The detection is best-effort, not a guarantee; never *rely* on the throw, just understand it.
- **Fail-safe** — `CopyOnWriteArrayList`, `ConcurrentHashMap`, ... — iterate over a *snapshot* (or a weakly-consistent view), so they never throw `CME`, but the iteration may not reflect modifications made after it began.

That contrast is your bridge to concurrency: the fail-safe collections exist *for* multi-threaded use, and they are covered properly in **6.2**. For now, the single-threaded lesson: do not structurally modify a standard collection while a for-each is walking it — use `removeIf` or the iterator.

## DIY Exercise

Build an `LRUCache<K, V>` — a fixed-capacity cache that, when full, evicts the **least recently used** entry. Standard `src/main/java` + `src/test/java` layout, with JUnit tests.

The intended foundation is `LinkedHashMap`. Investigate two of its features:

- Its constructor `LinkedHashMap(int initialCapacity, float loadFactor, boolean accessOrder)` — passing `accessOrder = true` makes *every `get` and `put`* move that entry to the most-recently-used end. That is the "recently used" half, handed to you.
- Its protected method `removeEldestEntry(Map.Entry)` — `LinkedHashMap` calls it after every insertion, and if you override it to return `true`, it drops the eldest (least-recently-used) entry. That is the "evict" half.

### Tasks

1. **`LRUCache<K, V>`** with a fixed capacity set at construction. Decide: subclass `LinkedHashMap`, or *compose* one as a private field and expose your own small API (`get`, `put`, `size`)? Recall the 1.4 argument — and notice that subclassing here means inheriting `LinkedHashMap`'s entire mutable `Map` surface, including methods that could bypass your eviction. Pick deliberately and be ready to defend it.

2. **Eviction.** When a `put` pushes size past capacity, the *least recently used* entry must be gone. Wire up `accessOrder` and `removeEldestEntry`.

3. **Tests** that pin the behaviour:
   - Fill to capacity, add one more — assert the eldest entry is evicted and the rest survive.
   - `get` an old entry, *then* add a new one — assert the entry you just *accessed* survived and a different one was evicted. This is the test that distinguishes least-recently-*used* from least-recently-*inserted*; make it unambiguous.
   - Assert size never exceeds capacity.

### Things to think about

- `accessOrder = true` means `get` *mutates* the map's internal order. What does that imply for calling `get` from two threads at once? (You do not need to fix it — just locate the hazard. 6.2 is where the fix lives.)
- You picked subclassing or composition for task 1. If you subclassed: can a caller still call inherited `LinkedHashMap` methods that sidestep your intent? If you composed: what did you have to give up, and was it worth it?
- Your eviction test for "recently *used*" — if you had built the cache on a plain `HashMap` instead, which exact guarantee would you have lost, and why can `HashMap` not provide it?
- A cache returning "miss" for an absent key is routine, not exceptional. Should `get` return `null`, or `Optional<V>` (4.3)? Tie this back to 3.1's "exceptions as control flow" anti-pattern.
- Suppose two `LRUCache` instances must be `equals`-comparable. What would `equals`/`hashCode` need to consider — and does access-order history count as part of a cache's "value"? (3.4 is next, and this is exactly its territory.)

Next, 3.4 confronts the contract this whole submodule quietly leaned on: `equals`, `hashCode`, and ordering — the rules that decide whether your objects behave correctly *inside* these collections.
