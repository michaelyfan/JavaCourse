# 3.5 Modern Syntax You Should Be Reaching For

Module 3 has been about idiom — code that is *correct* versus code that another engineer reads cleanly. This last submodule is the smallest-grained version of that: three syntax features added since Java 10 that remove ceremony. `var`, text blocks, and switch expressions. None of them changes what your program *does*. All of them change how fast a reader sees what it does.

A theme worth stating up front: two of these are nearly pure wins, and one — `var` — has a genuine readability tradeoff. Knowing which is which is most of this submodule.

---

## `var` — local-variable type inference (Java 10)

`var` lets the compiler infer a local variable's type from its initializer:

```java
var count = 0;                                  // int
var name = "Ada";                               // String
var orders = new ArrayList<Order>();             // ArrayList<Order>
var entry = Map.entry("k", 1);                   // Map.Entry<String, Integer>
```

Two things `var` is **not**:

- **It is not dynamic typing.** `var` is 100% statically typed. `var name = "Ada"` makes `name` exactly a `String`, forever — `name = 42` is a compile error just as it would be with `String name`. The type is fixed at compile time; `var` only spares you *writing* it.
- **It is not a runtime feature.** Like generics' erasure (3.2), `var` vanishes during compilation. The `.class` file is identical to one written with the explicit type.

### Where `var` is allowed

Deliberately narrow — **local variables only**:

| Allowed | Not allowed |
|---|---|
| Local variable with an initializer | Fields (instance or static) |
| `for` / for-each loop variable | Method parameters |
| `try-with-resources` resource | Method return types |
| | Any variable with no initializer (`var x;`) |
| | `var x = null;` — nothing to infer from |
| | A lambda with no target type (`var f = () -> 1;`) |

The restriction is the point. `var` is confined to the one place a type is most often *redundant* — a local whose initializer is right there on the same line. It is kept out of API surfaces (fields, parameters, returns), where an explicit type is documentation a reader depends on.

### When `var` helps

When the right-hand side **already names the type**, repeating it on the left is pure noise:

```java
// the type is stated twice — the left side adds nothing
Map<String, List<Order>> ordersByCustomer = new HashMap<String, List<Order>>();

// var: stated once, still completely clear
var ordersByCustomer = new HashMap<String, List<Order>>();
```

A constructor call, a `List.of(...)` / `Map.of(...)` factory, a string or numeric literal — in all of these the initializer makes the type obvious, and `var` removes the redundant half. It is especially kind to long generic types, where the explicit form is mostly angle brackets.

### When `var` hurts

When the right-hand side **does not** reveal the type, `var` deletes information the reader needs:

```java
var result = service.process(request);   // ...what is result? you must go read process()
```

With `Invoice result = ...`, the type is right there. With `var`, the reader has to navigate to `process` to learn what they are holding. The cost is real.

Two specific traps:

```java
var list = new ArrayList<>();    // inferred ArrayList<Object> — the diamond had nothing
                                 // to infer from, so it widened to Object. Almost never
                                 // what you wanted. Write the type argument explicitly.

var id = 0;                      // int. If a method wants a long, you have a silent
                                 // surprise. var y = 0L; is the long.
```

### The guideline

> Use `var` when the initializer plainly states the type — a `new`, a known factory, a literal. Avoid it when the type is not visible at the declaration. The reader should never have to leave the line to know what they are holding.

`var` is a *readability* tool. When it improves readability, use it. When it costs readability, the few extra characters of an explicit type are cheap. It is not a style to apply uniformly — it is a judgement call per declaration, which is exactly why the DIY asks you to justify each one you keep.

## Text blocks (Java 15)

Multi-line strings — SQL, JSON, HTML — used to be a wall of `\n`, `+`, and escaped quotes:

```java
String query = "SELECT id, name, salary\n" +
                "FROM employee\n" +
                "WHERE department = ?\n" +
                "ORDER BY salary DESC";
```

A **text block** is a string literal delimited by `"""`, written across real lines:

```java
String query = """
        SELECT id, name, salary
        FROM employee
        WHERE department = ?
        ORDER BY salary DESC""";
```

It produces an ordinary `String` — identical to the concatenated version, indistinguishable at runtime. It is purely better source.

### The rules that actually matter

1. **The opening `"""` must be followed by a line terminator.** `"""SELECT` on the same line is a compile error. Content starts on the *next* line.

2. **Incidental whitespace is stripped.** This is the feature that makes text blocks usable inside indented code. The compiler finds the *least-indented* non-blank line (the closing `"""` counts), and strips that much leading whitespace from every line. So you may indent the whole block to match your code; that indentation is *incidental* and removed. Indentation *beyond* the common minimum is *essential* and kept. The position of the closing `"""` is therefore meaningful — it sets the left margin.

3. **Trailing whitespace on each line is stripped** — invisible spaces cannot sneak into the value. To *keep* a trailing space, end the line with the escape `\s` (one space) or use `\` as a line-continuation (joins to the next line with no newline).

4. **Quotes need no escaping.** `"` sits in a text block freely — a real gift for JSON and HTML.

5. **No interpolation.** Java text blocks do *not* substitute variables (unlike Kotlin/JS template strings). Combine with `String.format`, or the `formatted` instance method that reads cleanly on a block:

   ```java
   String json = """
           { "user": "%s", "active": %b }""".formatted(name, active);
   ```

Use a text block whenever a string spans more than one line, or contains quotes you would otherwise escape. For a single-line string, a normal `"..."` literal is still right.

## Switch expressions (Java 14)

The old `switch` is a **statement** — it *does* something but does not *produce* a value — and it carries two long-standing hazards:

```java
String label;
switch (day) {
    case SATURDAY:
    case SUNDAY:
        label = "weekend";
        break;                 // forget this -> fall-through bug
    default:
        label = "weekday";
}
```

- **Fall-through.** Execution drops into the next `case` unless you `break`. A forgotten `break` is a classic, silent bug.
- **It is not an expression.** It cannot yield a value, so you declare `label` uninitialized beforehand and hope every branch assigns it.

A **switch expression** fixes both:

```java
String label = switch (day) {
    case SATURDAY, SUNDAY -> "weekend";
    default               -> "weekday";
};
```

What changed:

- **Arrow labels (`->`).** The right side runs for that case *only* — **no fall-through, no `break`.** The forgotten-`break` bug is gone by construction.
- **Multiple labels per case** — `case SATURDAY, SUNDAY ->` — comma-separated, replacing stacked empty `case`s.
- **It is an expression.** `switch (...) { ... }` evaluates to a value you assign directly. `label` is `final`-eligible, declared and assigned in one statement, with no uninitialized window.
- **For a block body, `yield` produces the value:**

  ```java
  int score = switch (grade) {
      case 'A' -> 4;
      case 'B' -> 3;
      default  -> {
          log.warn("unknown grade {}", grade);
          yield 0;            // a block must yield its value
      }
  };
  ```

### Exhaustiveness — a switch expression must cover every input

Because it must produce a value, a switch *expression* has to handle every possible input — the compiler enforces it. For an arbitrary type that means a `default`. But over an **`enum`**, if you list *every* constant, no `default` is needed — and that is a feature worth wanting:

```java
int priority = switch (status) {   // Status is an enum
    case NEW       -> 1;
    case PAID      -> 2;
    case SHIPPED   -> 3;
    case DELIVERED -> 4;
    case CANCELLED -> 0;
};                                 // no default — all constants covered
```

Now add a `RETURNED` constant to `Status`. Every `default`-less exhaustive switch over `Status` becomes a **compile error**, pointing you straight at every place that needs the new case. A `default -> ...` would have silently swallowed `RETURNED` into the fallback and shipped the bug. **Prefer omitting `default` on an enum switch** precisely so the compiler hands you that checklist. (This is the same exhaustiveness guarantee a `sealed` type gives — 1.5.)

### Use the arrow form everywhere

The arrow syntax also works for a switch *statement* (a `switch` used purely for side effects, yielding nothing) — and you should use it there too, for the no-fall-through safety:

```java
switch (command) {
    case START -> engine.start();
    case STOP  -> engine.stop();
    default    -> log.warn("unknown command {}", command);
}
```

> Reach for the arrow `switch` by default — expression form when you need a value, statement form when you do not. The colon-and-`break` form survives mainly in old code; new fall-through `switch`es are rarely worth writing.

A forward note: Java 17 *previewed* **pattern matching for `switch`** (`case Circle c -> ...`, matching on type and shape). It is not finalized in 17 — it stabilized in Java 21. 1.5 already used pattern matching for `instanceof`, which *is* stable in 17. The rule for this course: type-pattern `switch` is a Java 21 feature; do not lean on it in 17 code. The plain value-and-enum switch expressions above are fully stable.

## The thread tying these together

`var`, text blocks, and arrow `switch` all do one thing: cut ceremony so *intent* is what is left on the page. A doubled generic type, a `\n`-and-`+` ladder, a `break`-littered `switch` — each is mechanism crowding out meaning. Removing it lets the next reader see the *what* without first parsing the *how*.

The honest asterisk: text blocks and switch expressions are close to free wins — strictly clearer, no real downside. `var` is the one with a genuine tradeoff, because it can *remove* intent (the type) as easily as it removes noise. That is why it is a per-declaration judgement and the other two are nearly automatic. "Modern syntax you should be reaching for" — yes — but reach for `var` with your eyes open.

## DIY Exercise

This is a *refactoring* exercise. You will be given (write it yourself, deliberately ugly, from the description) a single ~60-line method that does the following, in the worst reasonable style:

- Builds a multi-line SQL string with `"..." + "\n" + "..."` concatenation.
- Declares variables with long explicit generic types (`HashMap<String, List<Integer>> x = new HashMap<String, List<Integer>>();` and similar).
- Contains a colon-style `switch` *statement* with stacked `case`s, `break`s, and at least one intentional fall-through that is currently "load-bearing" (a case that genuinely relies on falling through).

Put it in the `src/main/java` + `src/test/java` layout.

### Tasks

1. **Write the ugly version first** and **write tests against it** — pin its current behaviour, *including* whatever the load-bearing fall-through produces. These tests are your safety net: they must stay green through every step.

2. **Convert the SQL** to a text block. Get the incidental-whitespace stripping right so the runtime string is unchanged — your tests will tell you. If the SQL has interpolated values, use `formatted`.

3. **Apply `var`** — but only where it *helps*. Convert the declarations whose initializer already names the type. **Leave explicit** any whose type would otherwise be invisible. For every `var` you keep, write a one-line comment-free justification in your notes (not the code): why is the type still obvious here?

4. **Convert the `switch`** to an arrow switch — expression form if it is computing a value, statement form if not. The load-bearing fall-through is the interesting part: arrow switches *cannot* fall through, so you must make that shared behaviour explicit — either by listing multiple labels on one case (`case A, B ->`) or by factoring the shared code into a method both cases call. Decide which, and why.

5. **Rerun the tests.** Every one still green. The behaviour did not change — only the reading did.

### Things to think about

- For each `var` you *rejected*, name the specific thing a reader would have lost. For each you *kept*, would a reader genuinely never need to leave the line? Be honest — this is the whole skill.
- The load-bearing fall-through: was the original fall-through a deliberate design or an accident that happened to work? After your refactor, is the shared behaviour now *obvious* or merely *preserved*? Which labels-on-one-case vs. extract-a-method did you choose, and what made it the better fit?
- If the `switch` is over an enum and you wrote it as an exhaustive expression with no `default` — add a new constant to the enum. Where does the compiler send you? Now imagine you had kept a `default` instead: what would have happened, and is that better or worse?
- Your text block is indented to match the surrounding method. Move the closing `"""` four spaces left, recompile, and diff the runtime string. Explain exactly what changed in terms of the incidental-whitespace rule.
- One refactor you did *not* make: did any explicit generic type survive because it was a *field* or a *method parameter*, where `var` is not even allowed? Why is `var` deliberately banned there — what would be lost if a public method's parameter could be `var`?
