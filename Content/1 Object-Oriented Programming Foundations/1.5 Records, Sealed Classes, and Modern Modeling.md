# 1.5 Records, Sealed Classes, and Modern Modeling

The features in this submodule — records, sealed types, pattern matching, switch expressions — were added across Java 14–17. They aren't separate ideas thrown into the same release; they're pieces of one coherent shift in how Java wants you to model data. Records give you immutable data carriers without ceremony. Sealed types let you say "these are the only valid subtypes, and the compiler knows it." Pattern matching and switch expressions let you take that compile-time knowledge and write code that the compiler can check for completeness. Together they let you express **algebraic data types** — closed sums of fixed shapes — which is what most "this thing is one of N variants" modeling actually wants.

Before Java 14 you wrote `equals`, `hashCode`, `toString`, and getters by hand (or generated them with the IDE and re-generated whenever a field changed), used `if (x instanceof Foo) { Foo f = (Foo) x; ... }` chains, and had no way to tell the compiler "this is the complete list of subtypes." All three are gone now.

---

## Records

A `record` is a class whose entire purpose is to carry a fixed set of values. You declare the components in the header; the compiler generates the field declarations, the canonical constructor, the accessors, `equals`, `hashCode`, and `toString`.

```java
public record Point(int x, int y) {}
```

That single line gives you:

```java
public final class Point {
    private final int x;
    private final int y;
    public Point(int x, int y) { this.x = x; this.y = y; }
    public int x() { return x; }
    public int y() { return y; }
    public boolean equals(Object o) { /* compares x and y */ }
    public int hashCode()           { /* derived from x and y */ }
    public String toString()        { return "Point[x=" + x + ", y=" + y + "]"; }
}
```

A few things to notice about that expansion:

- Records are **implicitly `final`** — you can't extend one. Records model values, and value semantics don't play well with subtype polymorphism (a `ColoredPoint extends Point` would break `equals` symmetry, the same problem covered in 1.2).
- Records **implicitly extend `java.lang.Record`** — they can't extend any other class. They *can* implement interfaces, and they often do; that's how a record participates in a sealed hierarchy (next section).
- Accessors are named `x()`, not `getX()`. This is deliberate — records aren't JavaBeans, and the bare-name accessor signals "this is a component of the value," not "this is a property someone might write to."
- All fields are `final`. There are no setters, ever. Records are immutable by construction.

### Compact constructors

The canonical constructor is fine for assignment, but you usually want to **validate or normalize** the inputs. The compact constructor lets you do that without re-listing every parameter:

```java
public record Email(String value) {
    public Email {
        if (value == null || !value.contains("@")) {
            throw new IllegalArgumentException("invalid email: " + value);
        }
        value = value.toLowerCase();   // normalization
    }
}
```

Two surprises here for a Java reader seeing this for the first time:

1. There's no parameter list on `public Email { ... }`. The compact constructor borrows the canonical signature.
2. The assignment `value = value.toLowerCase()` looks like it's a no-op on a parameter, but the compiler emits `this.value = value` *after* the compact body runs. So mutating the parameter inside the body is how you normalize before the field gets set. You never write `this.value =` yourself in a compact constructor — that happens implicitly at the end.

If you need a different kind of constructor (different parameters, or to copy-modify from another record), declare a normal constructor instead — but it must end up delegating to the canonical one with `this(...)`.

### When records are the right answer

A record is the right call when:
- The object is defined entirely by its components — two instances with the same field values are interchangeable.
- You don't need to extend a class (you can't anyway).
- The fields don't need to change after construction.

This is most "data" in a typical codebase: DTOs, response objects, coordinates, money amounts, identifiers, query results. The friction-free `equals`/`hashCode` means records also work well as `HashMap` keys.

A record is the *wrong* call when the object has identity that matters beyond its fields (a `User` row in a database might have the same email and name as another but be a different user), when fields legitimately need to change over time (most domain entities), or when you need an inheritance hierarchy. For those cases, write a normal class.

## Sealed classes and interfaces

A `sealed` type names the exact set of types allowed to extend or implement it. Anyone else trying to extend it is a compile error.

```java
public sealed interface Shape permits Circle, Rectangle, Triangle {}

public record Circle(double radius) implements Shape {}
public record Rectangle(double width, double height) implements Shape {}
public record Triangle(double base, double height) implements Shape {}
```

That `permits` clause is the whole point. Before sealed types, an `abstract class Shape` could be extended by anyone, anywhere — the compiler had no idea how many subtypes existed, so a `switch` on subtype could never be "exhaustive." With `sealed`, the compiler *knows* there are exactly three implementations, which unlocks the exhaustiveness checking we'll use in switch expressions.

Every permitted subtype must declare its own modality — it has to pick one of:

- **`final`** — no further extension. Records are implicitly `final`, which is why they slot into sealed hierarchies cleanly.
- **`sealed`** — continues the sealing one level deeper, with its own `permits` clause.
- **`non-sealed`** — opens the subtree back up. Anyone can extend a `non-sealed` subtype.

`non-sealed` is the escape hatch for the inevitable "we want a controlled top-level set, but this one branch genuinely needs to be open for plugins to extend." Use it sparingly — every `non-sealed` you add is a place where exhaustiveness checking stops working below that node.

Sealed types and permitted subtypes must live in the **same module** (or, on the classpath, the same package). The compiler enforces this — you can't have a sealed interface in one library and a permitted subtype in another unless they share a module. This is what makes the closed set actually closed: a downstream consumer can't sneak in a new subtype.

If `permits` is omitted, the compiler infers it from the subtypes declared in the same compilation unit (file). For small hierarchies you can put the sealed interface and all its records in one file and skip the `permits` clause:

```java
// Shape.java
public sealed interface Shape {}
record Circle(double radius) implements Shape {}
record Rectangle(double width, double height) implements Shape {}
record Triangle(double base, double height) implements Shape {}
```

### Why sealed types matter for modeling

The pattern sealed + records expresses is **"this value is one of N fixed shapes, each carrying its own data."** Functional programmers call this a sum type or an algebraic data type. In Java before 17, the closest equivalents were:

- An enum — but enums can't carry per-variant data of different shapes.
- An abstract class with subclasses — but the hierarchy was open, the compiler couldn't check exhaustiveness, and there was no concise way to declare immutable value classes.

Sealed + records closes both gaps. The `Shape` example above is the simplest version. A more practical one is the **`Result<T>`** type — a value that is either a success carrying a `T` or a failure carrying an error — which is the DIY for this submodule and a pattern you'll see repeatedly in Module 6 (concurrency) and Module 7 (patterns).

## Pattern matching for `instanceof`

This is a small syntactic feature that compounds nicely with the rest. The old form:

```java
if (obj instanceof String) {
    String s = (String) obj;
    return s.length();
}
```

becomes:

```java
if (obj instanceof String s) {
    return s.length();
}
```

The `s` is a **pattern variable** — bound and typed only inside the branch where the `instanceof` succeeded. The cast disappears because the compiler already knows the type.

The scope rule is "wherever the compiler can prove the check passed." That means you can also write:

```java
if (!(obj instanceof String s)) {
    return 0;
}
return s.length();    // s is in scope here — the early return proves obj was a String
```

This is more useful than it looks. Most legacy `instanceof` chains end with a default branch and a series of casts; rewriting them with pattern variables removes the casts and makes the intent obvious.

## Switch expressions

`switch` in Java was historically a statement: it didn't return a value, it fell through between cases unless you wrote `break`, and it was a frequent source of bugs. The **switch expression** (Java 14) fixes all three:

```java
String label = switch (day) {
    case MONDAY, TUESDAY, WEDNESDAY, THURSDAY, FRIDAY -> "weekday";
    case SATURDAY, SUNDAY -> "weekend";
};
```

Three things changed:

1. **It's an expression** — it produces a value, which you can assign to a variable, return from a method, or pass to another expression.
2. **The arrow form (`->`) doesn't fall through.** Each case is its own branch. No `break` needed, no bug from forgetting one.
3. **Exhaustiveness is checked.** Because `Day` is an enum, the compiler knows all the cases. If you miss one, it's a compile error. If you want to be lenient, add `default ->`.

If the right-hand side needs multiple statements, use a block with `yield`:

```java
int code = switch (status) {
    case "OK" -> 200;
    case "NOT_FOUND" -> 404;
    default -> {
        log.warn("unknown status {}", status);
        yield 500;
    }
};
```

`yield` is the switch-expression equivalent of `return` for a single case. You'll rarely need it — most cases are one-liners — but it's there.

The old `switch` statement (with `case X:` and `break;`) still works and isn't going anywhere. But for any new code that's computing a value from a discrete input, the expression form is what you want.

### Exhaustiveness on sealed types

The killer combination: a sealed interface + a switch expression with no `default`. The compiler checks that every permitted subtype is handled. If you later add a fourth `Shape`, every switch on `Shape` that lacks a `default` becomes a compile error until you add the new case. That's the whole point of sealing: changes to the hierarchy can't silently slip past existing code.

```java
double area = switch (shape) {
    case Circle c    -> Math.PI * c.radius() * c.radius();
    case Rectangle r -> r.width() * r.height();
    case Triangle t  -> 0.5 * t.base() * t.height();
};
```

No `default` clause, no `instanceof`, no casts. Each case binds a pattern variable typed to the specific subtype, so you can call its accessors directly. If anyone adds a `Square` to `Shape`'s permits list, this code stops compiling — exactly the behavior you want.

The `case Circle c ->` form is **type patterns in switch**, the natural extension of pattern matching from `instanceof` to `switch`. In Java 17 this is a *preview* feature; in Java 21 it's finalized. The version you have determines whether you need `--enable-preview` to use it. For this course we'll use the Java 21 syntax (no preview flag needed) because it's what you'll be writing in production now. If you're stuck on a Java 17 codebase, the rest of the lesson — records, sealed types, pattern matching for `instanceof`, switch expressions on enums — is fully stable; only the type-pattern-in-switch piece is preview-gated, and the workaround is an `if`/`else if` chain of pattern-matching `instanceof` statements.

### `null` and the `default` case

A switch expression on a reference type that's exhaustive over a sealed hierarchy still needs to handle `null`. The default behavior is to throw `NullPointerException` before any case runs, which is usually fine. If you want to handle null explicitly, add `case null -> ...` (Java 21+). For Java 17, check for null before the switch.

## Putting it together

The four features compose. A sealed hierarchy of records, consumed by a switch expression, is the modern shape of "this is one of these things, do the right thing for each":

```java
public sealed interface PaymentMethod permits CreditCard, BankTransfer, Cash {}
public record CreditCard(String number, YearMonth expiry) implements PaymentMethod {}
public record BankTransfer(String iban) implements PaymentMethod {}
public record Cash() implements PaymentMethod {}

String describe(PaymentMethod pm) {
    return switch (pm) {
        case CreditCard cc   -> "card ending " + cc.number().substring(cc.number().length() - 4);
        case BankTransfer bt -> "transfer from " + bt.iban();
        case Cash c          -> "cash";
    };
}
```

Compare that to the equivalent Java 8 code: an `interface PaymentMethod`, three classes with manually written `equals`/`hashCode`/`toString`/getters, and a `describe` method full of `instanceof` checks and casts ending in a `throw new IllegalStateException("unknown")` because the compiler couldn't prove exhaustiveness. The modern version is shorter, more correct, and breaks loudly when the hierarchy changes.

---

## What this replaces, and when not to use it

These features are the right default for value-shaped data and closed variant sets. They are not the right default for:

- **Domain entities with mutable state and identity.** A `User` that gets renamed, an `Order` whose status changes — these aren't records. Records are for snapshots and messages, not for things that change.
- **Open hierarchies meant for third-party extension.** A plugin interface that downstream code implements is the opposite of a sealed type. Use a plain `interface`.
- **Cases where you genuinely need inheritance for behavior reuse**, not modeling. Records can't extend a class, so if you have a base class with substantial logic to share, records won't help. (Often a better factoring is to keep the data in records and put the logic in a regular class that consumes them.)

The mental model: **records describe values, sealed types describe variants, switch expressions consume both.** When a problem fits that frame, the new features will simplify the code dramatically. When it doesn't, reach for the classic tools.

## DIY Exercise

You're going to build `Result<T>` — a value that is either a `Success<T>` carrying a payload or a `Failure<T>` carrying an error — and consume it with a switch expression. This pattern shows up everywhere: it's the explicit alternative to "return null on failure" and "throw checked exceptions everywhere," and you'll see it again in Module 6 when we wrap async results.

**Part 1 — define the sealed hierarchy.**

- Declare `Result<T>` as a `sealed interface` with two permitted subtypes: `Success<T>` and `Failure<T>`. Both subtypes should be records.
- `Success<T>` carries a single `T value`.
- `Failure<T>` carries a single `Throwable error`. The `<T>` on `Failure` is a **phantom type parameter** — `Failure` doesn't actually use it for anything, but it has to be there so that a `Failure` can stand in for `Result<T>` for any `T`. Without it, you couldn't assign a failure to a `Result<String>` variable.
- Add two static factory methods on the interface so callers don't have to write `<>` at every call site:

  ```java
  static <T> Result<T> success(T value)         { return new Success<>(value); }
  static <T> Result<T> failure(Throwable error) { return new Failure<>(error); }
  ```

- Put all three types in the same file so you can omit `permits` and let the compiler infer it.
- Since 1.8 (packages) hasn't been built yet, run this in **single-file source mode**: one `.java` file alongside this lesson, no `package` declaration, run with `java Result.java`. Constraint to know about: a `.java` file is allowed only **one `public` top-level type**, and it must match the filename. So make `Result` public and leave `Success` and `Failure` package-private (no modifier). They'll still be reachable from the same file.

Why the phantom type parameter at all? This is one of the rough edges of Java's sum-type modeling. Languages with first-class ADTs (Rust, Kotlin) don't make you do this — a failure variant simply doesn't have to mention the success type. In Java, the phantom parameter is the standard workaround and what real libraries (Vavr, jOOL, the Java Result types in various utility libraries) do. It costs nothing at runtime and keeps the type system honest at compile time. The alternative — making `Failure` implement the raw `Result` — works but produces unchecked-cast warnings the rest of your code has to suppress, which is exactly the kind of mess sum types are supposed to eliminate.

**Part 2 — write `unwrapOrThrow` using a switch expression.**

Add a default method to `Result<T>`:

```java
default T unwrapOrThrow() {
    return switch (this) {
        // your code here
    };
}
```

- If `this` is a `Success<T>`, yield its value.
- If `this` is a `Failure<T>`, throw its error wrapped in a `RuntimeException` (use `throw` inside the case body — switch expression cases are allowed to throw instead of producing a value).
- Use type patterns: `case Success<T> s -> s.value()` and `case Failure<T> f -> throw ...`. Do **not** use `if (... instanceof ...)` chains — the whole point is to feel how exhaustive pattern matching reads.
- Confirm that omitting one of the two cases is a compile error. Then put it back.

**Part 3 — exercise it.**

In `main`:
- Build a `Result<Integer> ok = Result.success(42)` and a `Result<Integer> bad = Result.failure(new IOException("disk gone"))`. (You'll need `import java.io.IOException;` at the top of the file — imports work fine in single-file source mode.)
- Call `unwrapOrThrow()` on `ok` and print the result.
- Call `unwrapOrThrow()` on `bad` inside a `try`/`catch` and print the caught exception's message *and* its cause's message.

**Things to think about while you write it:**

- The switch expression on `this` has no `default`. Why doesn't the compiler complain? (Because `Result` is sealed and you've covered both permitted subtypes.) What does it complain about if you add a third permitted subtype and don't update the switch?
- The phantom type parameter on `Failure<T>` is *never read* at runtime — type erasure deletes it. So what is it actually buying you, given that it's gone by the time the JVM runs your code? (Hint: every benefit of generics is a compile-time benefit. Think about what the *call site* of `Result.failure(...)` infers, and what assignments the compiler then permits.)
- What does this design buy you over throwing exceptions directly? (Hint: think about what the *type signature* of a method returning `Result<T>` tells a caller versus a method returning `T` and "maybe throwing.")
- Records can have additional methods. Could `Result` carry `map(Function<T, U>)` and `flatMap(Function<T, Result<U>>)` methods as defaults on the interface? Sketch what those would look like — they're the same shape as `Optional.map`/`flatMap`, which you'll meet in 4.3. You don't have to implement them, but seeing the shape now will make Optional, Stream, and CompletableFuture feel less like three different APIs.
