# 1.7 Nested, Inner, and Anonymous Classes

Java lets you declare a class inside another class. That sounds like a minor scoping convenience — a way to keep related code together — and most of the time it is. But "a class inside another class" hides four genuinely different things with different semantics, different costs, and different right uses: **static nested classes**, **inner classes**, **local classes**, and **anonymous classes**. The headline distinction is whether the nested type carries an implicit reference to an enclosing instance. That single fact drives memory behavior, serialization gotchas, and what the nested type can and can't capture. Once you internalize the static-vs-inner split, the other two forms fall out as variations on the same axis.

This submodule also closes the loop on lambdas (which you've seen in passing and which get a full treatment in Module 5). Anonymous classes were the closest thing Java had to lambdas before Java 8, and the two forms overlap enough that it's worth being explicit about what each can do that the other can't.

---

## The four forms at a glance

```java
public class Outer {

    // 1. Static nested class — a class declared inside another, with no link to an instance.
    static class StaticNested { }

    // 2. Inner class — a non-static nested class. Each instance is tied to an Outer instance.
    class Inner { }

    void method() {
        // 3. Local class — declared inside a method body. Scoped to that method.
        class Local { }

        // 4. Anonymous class — declared and instantiated in one expression. No name.
        Runnable r = new Runnable() {
            @Override public void run() { /* ... */ }
        };
    }
}
```

All four are compiled into separate `.class` files (`Outer$StaticNested.class`, `Outer$Inner.class`, `Outer$1Local.class`, `Outer$1.class`). At the JVM level there's nothing magical about "nested" — it's a source-language convenience. The differences live in what the compiler weaves in for you: an implicit outer reference, captured variables, or neither.

---

## Static nested classes vs. inner classes

The compiler treats `static class` and (non-static) `class` inside another class very differently.

A **static nested class** is just a regular class that happens to live in another class's namespace. It can be instantiated by anyone with access to it (`new Outer.StaticNested()`), it has no implicit reference to any `Outer` instance, and it can't access `Outer`'s instance fields or methods directly. It's effectively a top-level class with a longer name.

An **inner class** (non-static nested class) is something else: every instance of an inner class carries a hidden reference to the enclosing `Outer` instance that created it. You can't instantiate one without an outer instance (`outer.new Inner()` is the explicit form; inside `Outer`'s methods, `new Inner()` works because `this` is implicit). The inner class can freely read `Outer`'s private fields because, under the hood, the compiler generates synthetic accessors and threads the outer reference through.

```java
public class Outer {
    private int counter = 0;

    class Inner {
        void bump() {
            counter++;          // reaches into Outer's instance state
        }
    }
}
```

The implicit outer reference is the whole story. It's what gives inner classes their "magical" access to enclosing state, and it's what makes them dangerous in three specific ways:

- **Memory leaks.** As long as an inner-class instance is alive, the outer instance is alive too — even if no other code holds a reference to it. Stash an inner-class `Listener` in a static registry and the entire enclosing object graph is pinned in the heap. This is one of the classic Java memory-leak shapes; in Android in particular it's a near-canonical bug because activities are heavy and listeners outlive them.
- **Serialization.** Serializing an inner class transparently serializes the outer instance too. If the outer isn't serializable, the inner isn't either, even if it looks like it should be.
- **Surprising construction.** `new Inner()` only compiles inside `Outer` because the outer reference is implicit. From outside it's `outer.new Inner()`, which most engineers have never written and most readers won't recognize.

The rule of thumb is **make nested classes `static` by default**, and only drop the `static` modifier when you genuinely need access to the enclosing instance's state. IDE warnings ("inner class may be static") exist for this reason. The static form costs nothing — it's strictly more flexible and strictly less coupled.

When *do* you want a non-static inner class? Cases where the inner type is *conceptually* a piece of the outer instance and exists only for it: a custom `Iterator` over the outer's internal data, an `Entry` view that lives inside a `Map`, a builder that needs to read the half-constructed outer's state. Even in these cases, many designs end up cleaner as a static nested class that takes the outer (or just the data it needs) as a constructor argument — the coupling becomes explicit instead of implicit.

## Local classes

A **local class** is a class declared inside a method body (or any block). It's scoped to that block — nothing outside the block can refer to it by name — and it can capture variables from the enclosing method, with the same "effectively final" restriction that lambdas have.

```java
public List<String> labelled(List<String> items) {
    String prefix = "item-";

    class Labeller {
        String label(int i, String s) {
            return prefix + i + ": " + s;     // captures prefix
        }
    }

    Labeller l = new Labeller();
    return IntStream.range(0, items.size())
        .mapToObj(i -> l.label(i, items.get(i)))
        .toList();
}
```

Local classes are rare in modern Java because lambdas and method references cover almost every case where you'd reach for one. They're still occasionally useful when you need something a lambda can't give you — multiple methods, a constructor, or a name in stack traces — that's also scoped tightly to one method and doesn't deserve to be a full file. In practice, if you find yourself writing a local class, ask whether a static nested class would read better; usually it would.

---

## Anonymous classes

An **anonymous class** is a class definition fused with its single instantiation, with no name of its own. The syntax `new SomeType() { ... }` declares a one-off subclass of `SomeType` (or a one-off implementor, if `SomeType` is an interface) and instantiates it in the same expression.

```java
Comparator<String> byLength = new Comparator<String>() {
    @Override
    public int compare(String a, String b) {
        return Integer.compare(a.length(), b.length());
    }
};
```

Anonymous classes are inner classes (they carry the outer reference) when declared in an instance context, and effectively-static when declared in a static context. They can capture effectively-final local variables, just like local classes and lambdas. They can have fields and additional methods, but those extra methods are only callable from inside the class itself (since the only reference any caller has is typed as the supertype).

Before Java 8, anonymous classes were how you passed behavior around — `new Runnable() { ... }`, `new ActionListener() { ... }`, `new Comparator<>() { ... }`. Lambdas replaced almost all of that. Knowing the difference matters because both forms still exist and the compiler treats them very differently.

---

## Anonymous classes vs. lambdas

For a single-abstract-method interface, an anonymous class and a lambda look like alternatives. They aren't equivalent.

```java
// Anonymous class
Runnable a = new Runnable() {
    @Override public void run() { System.out.println(this); }
};

// Lambda
Runnable l = () -> System.out.println(this);
```

The functional differences:

- **`this` means different things.** Inside the anonymous class, `this` refers to the anonymous-class instance. Inside the lambda, `this` refers to the *enclosing* `this` (because lambdas are lexically scoped and don't introduce a new `this`). This is one of the most common surprises when migrating anonymous classes to lambdas. If your old code did `this.something()` from inside a `Runnable`, the rewrite to a lambda silently changes what `this` refers to.
- **Lambdas can only implement a single abstract method.** That's what "functional interface" means. Anonymous classes can implement an interface with multiple methods or override several methods of an abstract class. If you need a `MouseAdapter` that overrides both `mousePressed` and `mouseReleased`, you need an anonymous class (or a named class). A lambda can't.
- **Lambdas can't have additional fields or state of their own.** They can only capture effectively-final variables from the enclosing scope. An anonymous class can declare `private int callCount = 0;` and mutate it across calls. (Whether you *should* is a different question — mutable state in a callback is usually a smell — but it's possible.)
- **Compilation is different.** Anonymous classes generate a `.class` file (`Outer$1.class`); lambdas use `invokedynamic` and can be more efficient, especially when not capturing. For hot code this can matter; for most code it doesn't.

The decision is straightforward: **use a lambda when one exists**, drop to an anonymous class when you need multiple methods, real state, or a meaningful `this`. The rest of the time, lambda.

## Real-world sightings

These forms aren't just trivia — recognizing them in the standard library makes a lot of API shape clearer.

**`Map.Entry`** is the textbook nested interface. `java.util.Map.Entry<K, V>` is declared *inside* the `Map` interface, scoped there because an entry has no meaning outside of belonging to a map. Implementations like `HashMap.Node` (an inner class of `HashMap`) and `AbstractMap.SimpleEntry` (a static nested class) implement it. The nesting communicates ownership.

**Custom iterators** are the canonical use of inner classes. The simplest correct `Iterable` implementation for a collection looks like this:

```java
public class IntStack implements Iterable<Integer> {
    private int[] data;
    private int top;

    @Override
    public Iterator<Integer> iterator() {
        return new Iterator<Integer>() {     // anonymous inner class
            private int cursor = top - 1;

            @Override public boolean hasNext() { return cursor >= 0; }
            @Override public Integer next()    { return data[cursor--]; }
        };
    }
}
```

The anonymous inner class needs to read `top` and `data` from the outer `IntStack` — the outer reference makes that free. The DIY at the end of this submodule walks through exactly this shape and then asks you to rewrite it as a static nested class to feel the difference.

**Builder patterns with mutable state** are often inner or static nested classes on the type they build. `StringBuilder` is a top-level class, but builder patterns you write yourself frequently look like `Order.Builder` — a nested class whose `build()` constructs an `Order`. Making the builder a static nested class is almost always the right call: the builder is conceptually scoped to `Order` but doesn't need access to any `Order` instance (no instance exists yet — that's the builder's job). Inner-class builders only make sense when the builder must read state from an already-half-constructed outer.

---

## Picking between them

| Situation | Use |
|---|---|
| A helper type that belongs to the outer namespace but needs no outer instance | **Static nested class** |
| A helper that genuinely needs access to the enclosing instance's state | **Inner class** |
| A small, named, one-off type used inside one method | **Local class** (rarely) |
| A one-off implementation of an interface with multiple methods, or one needing its own state | **Anonymous class** |
| A one-off implementation of a functional interface | **Lambda** |

The two strongest defaults: **`static` unless you've justified why not**, and **lambda over anonymous class when both work**. Almost every nested class problem reduces to one of those two decisions.

## DIY Exercise

You're going to build an iterable in two forms and feel the difference between anonymous and static nested iterators.

**Part 1 — `RangeIterable` with an anonymous inner-class iterator.**

- Implement `RangeIterable implements Iterable<Integer>`, constructed with `RangeIterable(int start, int endExclusive)`. Store `start` and `endExclusive` as private final fields.
- In `iterator()`, return an `Iterator<Integer>` as an anonymous inner class. The iterator should yield `start`, `start+1`, ..., `endExclusive - 1`, then signal exhaustion.
- The anonymous class needs a mutable `int cursor` field initialized to `start`. It reads `endExclusive` straight from the outer instance — no need to capture or pass it in.
- In `main`, build `new RangeIterable(3, 7)` and use an enhanced for-loop to print `3 4 5 6`. Then iterate it twice in a row to confirm each `iterator()` call returns a *fresh* iterator that starts over.

If you forget to make `cursor` an instance field of the anonymous class and try to capture it as a local variable instead, the compiler will reject it — local variables captured by inner classes must be effectively final, and a cursor that mutates plainly isn't. That error is the lesson: state that has to mutate across method calls has to live on an object.

**Part 2 — rewrite the iterator as a static nested class.**

- Add `static class RangeIterator implements Iterator<Integer>` inside `RangeIterable`. Give it `private int cursor` and `private final int endExclusive` fields, and a constructor `RangeIterator(int start, int endExclusive)` that initializes both.
- Change `iterator()` to `return new RangeIterator(start, this.endExclusive);`.
- Rerun the program — same output. Nothing the caller sees has changed.

Things to think about while you write it:

- The anonymous version doesn't take `endExclusive` as a parameter; the static version does. Why? Because the anonymous (inner) version has an implicit reference to the enclosing `RangeIterable` and can read its fields directly. The static version doesn't — it has to be told what range it's iterating. This is the implicit-outer-reference cost made tangible.
- If you serialize a `RangeIterable`, the static-nested-iterator version is fine. The anonymous-inner-class version drags the outer `RangeIterable` into serialization as well (and would break if it weren't serializable). You won't observe this without writing a serialization test, but it's worth noting that "anonymous inner classes capture the outer instance" has consequences beyond memory.
- If you keep an iterator alive for a long time (stashed in a field somewhere), the anonymous-inner-class version keeps the entire `RangeIterable` alive too. The static version doesn't. For a `RangeIterable` this is trivially small; for an iterator into a 10MB cache, it's a real leak.
- The anonymous version reads more compactly at the call site — fewer lines, no separate class declaration. That's the genuine trade: tighter code in exchange for an outer reference you didn't ask for. For tiny throwaway iterators inside one class, that trade is fine. For anything that escapes the enclosing object (returned to callers, held by other objects, retained long-term), prefer the static form.
- The static nested iterator could be a top-level class. Why scope it inside `RangeIterable`? Because nothing outside `RangeIterable` has any reason to construct one directly. Nesting communicates "this is an implementation detail of `RangeIterable`." That's the *only* reason — there's no semantic difference at the JVM level.
- Lambdas can't replace this iterator: `Iterator` has two abstract methods (`hasNext` and `next`), so it isn't a functional interface. This is one of the spots where anonymous classes still genuinely earn their keep — though even here, a named static nested class is usually clearer.

Single-file source mode: one file, no `package` declaration, run with `java RangeIterable.java`. You'll need `import java.util.Iterator;`.
