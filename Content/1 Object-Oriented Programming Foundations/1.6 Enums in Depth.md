# 1.6 Enums in Depth

Most engineers meet enums as "a list of named constants" — `enum Color { RED, GREEN, BLUE }` — and stop there. That's the surface. In Java, `enum` is a full class declaration with extra compile-time guarantees: the JVM enforces that exactly the constants you declared exist, that there will never be another, and that they're singletons with safe identity-based comparison. Once you internalize that an enum constant is a class instance, the rest of this submodule — per-constant method overrides, `EnumSet`/`EnumMap`, strategy-as-enum, singletons — stops looking like a grab-bag of tricks and starts looking like obvious consequences.

The thing other languages model with "a fixed type whose values are a closed set" is exactly what Java enums are. They're the right tool for any value that comes from a small, known-at-compile-time set: HTTP methods, weekdays, account tiers, log levels, currencies, payment statuses. They're the wrong tool for "things that look like a list but might grow" — country codes, product SKUs, feature flags — because adding a value requires recompiling and redeploying every consumer.

---

## Enums as full classes

An enum declaration is a class declaration in disguise. The constants you name in the header are `public static final` instances of that class, constructed eagerly by the JVM the first time the enum is referenced. Anything you'd put in a regular class — fields, constructors, methods — works in an enum too.

```java
public enum Planet {
    MERCURY(3.303e+23, 2.4397e6),
    VENUS  (4.869e+24, 6.0518e6),
    EARTH  (5.976e+24, 6.37814e6);

    private final double massKg;
    private final double radiusM;

    Planet(double massKg, double radiusM) {
        this.massKg = massKg;
        this.radiusM = radiusM;
    }

    public double surfaceGravity() {
        return 6.67300E-11 * massKg / (radiusM * radiusM);
    }
}
```

A few things to internalize:

- **The constructor is implicitly `private`.** You can't write `public` or `protected` on an enum constructor — the compiler forbids it. The only callers are the constant declarations in the header. This is what makes the "closed set" guarantee work: outside code literally cannot construct a new `Planet`.
- **The semicolon after the last constant is required** when the enum has any members (fields, methods, constructors). It's the separator between "the list of constants" and "the rest of the class." This is the most common syntax slip when graduating from constants-only enums.
- **Constants are constructed at class-load time, in declaration order.** `Planet.values()` returns them in that order. The `ordinal()` method returns the index — but don't lean on `ordinal()` for anything that matters, because reordering or inserting a constant silently changes every ordinal and any code persisting them breaks. If you need a stable numeric mapping, store an explicit `int code` field on each constant and read that.
- **Enum constants are singletons** — there's exactly one `Planet.EARTH` per JVM. You compare them with `==`, not `.equals()` (both work, `==` is idiomatic and lets the compiler catch typos).
- **You get `name()`, `ordinal()`, `valueOf(String)`, and `values()` for free** — they're inherited from `java.lang.Enum`. `valueOf` throws `IllegalArgumentException` for unknown names; if you want a tolerant lookup, write your own static method (or use the `EnumMap` pattern below).

Enums can also implement interfaces. They can't extend a class — they already extend `java.lang.Enum` implicitly, and Java has no multiple inheritance — but implementing an interface is exactly how you slot an enum into a polymorphic hierarchy. This is what makes the strategy-via-enum pattern below work cleanly.

## Constant-specific method bodies

You can override a method per constant. Each constant gets its own anonymous-class-style body, and `EnumName.METHOD.foo()` dispatches to the body declared on that constant.

```java
public enum Operation {
    PLUS  { @Override public double apply(double x, double y) { return x + y; } },
    MINUS { @Override public double apply(double x, double y) { return x - y; } },
    TIMES { @Override public double apply(double x, double y) { return x * y; } },
    DIVIDE{ @Override public double apply(double x, double y) { return x / y; } };

    public abstract double apply(double x, double y);
}
```

What's actually happening: each constant becomes an *anonymous subclass* of `Operation`. The `abstract` modifier on `apply` forces every constant to provide an implementation — leave one out and you get a compile error, the same way you would for failing to implement an abstract method in a regular subclass. This is the cleanest way to ensure "every variant handles this case." It's the enum equivalent of the exhaustiveness guarantee you saw with sealed types in 1.5.

The alternative is a `switch` inside one shared method:

```java
public double apply(double x, double y) {
    return switch (this) {
        case PLUS   -> x + y;
        case MINUS  -> x - y;
        case TIMES  -> x * y;
        case DIVIDE -> x / y;
    };
}
```

Both forms work and both give exhaustiveness checking (the switch expression on an enum is checked by the compiler — leave a case out and it won't compile). So which to use?

- **Switch expression**: better when the behavior per constant is small (one line), when the constants share data they need to read from `this`, or when you want to read all the variants' behavior at a glance.
- **Constant-specific bodies**: better when the behavior per constant is large or carries per-constant state, or when you want each constant's code to live with its declaration so adding a constant means writing its body in one place.

For most code you'll write, the switch-expression form is the better default — it keeps the logic centralized and reads top-to-bottom. Reach for constant-specific bodies when the per-constant logic genuinely belongs with the constant.

## `EnumSet` and `EnumMap`

These are specialized collection implementations that exist because, for an enum, the JVM already knows the complete set of possible keys at compile time. That's a huge optimization opportunity that `HashSet`/`HashMap` can't take advantage of.

**`EnumSet`** is internally a single `long` (or a `long[]` for enums with more than 64 constants), with one bit per possible enum value. Adding, removing, and checking membership are bitwise operations — branch-free, cache-friendly, often a single instruction. `HashSet`, by contrast, hashes the value, walks a bucket, and calls `equals`. On any enum that fits in a single `long`, `EnumSet` is dramatically faster *and* uses dramatically less memory.

```java
EnumSet<DayOfWeek> weekend = EnumSet.of(SATURDAY, SUNDAY);
EnumSet<DayOfWeek> weekdays = EnumSet.complementOf(weekend);   // all the others
if (weekend.contains(today)) { ... }                            // bit-and against a mask
```

**`EnumMap`** is backed by a plain array indexed by the constant's `ordinal()`. Lookup is array access — no hashing, no collision handling. It also iterates in declaration order, which is occasionally useful for predictable output.

```java
EnumMap<Operation, String> symbol = new EnumMap<>(Operation.class);
symbol.put(PLUS, "+");
symbol.put(MINUS, "-");
symbol.put(TIMES, "*");
symbol.put(DIVIDE, "/");
```

Notice the constructor takes the `Class` object, not a capacity. The map needs to know the enum type at runtime to allocate its backing array — generics alone don't tell it that, because of type erasure (which we'll meet properly in 3.2).

The rule of thumb: **if your key type is an enum, use `EnumMap`. If your set type is an enum, use `EnumSet`.** There's essentially no case where the general-purpose `HashMap<MyEnum, V>` is a better choice. Switching costs nothing and you get the speed and memory benefits for free.

A small caveat for `EnumMap`: like all `Map` implementations, it doesn't permit duplicate keys but does permit `null` *values*. It does not permit `null` keys — passing one throws `NullPointerException`. That matches `EnumSet`, which also forbids `null`.

## Strategy-via-enum

Combine "enums are full classes" with "constants can override methods" and you get a clean encoding of the **Strategy pattern** (which you'll meet properly in 7.3) without any of the usual ceremony. The strategy isn't a separate class hierarchy you have to register and look up — it's just the enum constant itself.

```java
public enum DiscountStrategy {
    NONE {
        @Override public BigDecimal apply(BigDecimal subtotal) {
            return subtotal;
        }
    },
    TEN_PERCENT {
        @Override public BigDecimal apply(BigDecimal subtotal) {
            return subtotal.multiply(new BigDecimal("0.90"));
        }
    },
    FREE_SHIPPING {
        @Override public BigDecimal apply(BigDecimal subtotal) {
            return subtotal.subtract(SHIPPING_FEE).max(BigDecimal.ZERO);
        }
    };

    private static final BigDecimal SHIPPING_FEE = new BigDecimal("5.00");
    public abstract BigDecimal apply(BigDecimal subtotal);
}

// Usage:
BigDecimal final = strategy.apply(subtotal);
```

What you'd write in "classic" Java is a `DiscountStrategy` interface, three classes implementing it, possibly a factory or a `Map<String, DiscountStrategy>` registry, and some lookup code to resolve a string from a request into the right strategy. The enum version collapses all of that: you get the type, the implementations, and a built-in string-to-strategy lookup (`DiscountStrategy.valueOf(name)`) in one declaration.

When is this *not* the right shape?

- **When the set of strategies isn't closed.** If callers from other modules or plugins need to register their own strategies, an enum can't model that — you can't extend it. Use an interface and a registry.
- **When a strategy needs to be parameterized at construction time.** Enum constants are built once at class load with whatever arguments are in the header; they can't carry runtime configuration. If your `TEN_PERCENT` needs to actually be a configurable "N percent" where N comes from a config file, use a regular class.
- **When the strategies have substantial state of their own.** Enum constants are singletons; any mutable state on them is shared globally, which is almost never what you want.

The frame: enums are the right strategy implementation when the set of strategies is small, fixed, and stateless. That covers a surprising amount of real code.

## Enum singletons

The cleanest way to write a singleton in Java is:

```java
public enum Config {
    INSTANCE;

    public String dbUrl() { return System.getenv("DB_URL"); }
}
```

That's it. `Config.INSTANCE` is a singleton — there's exactly one, the JVM guarantees its single-instance property, and it's constructed lazily on first reference to the `Config` class. You access it as `Config.INSTANCE.dbUrl()`.

This is shorter than the textbook `private static final INSTANCE` pattern, but the bigger reason it's recommended (by Effective Java, among others) is that it's the only singleton form that's **automatically safe against reflection and serialization attacks** that would otherwise let an attacker create a second instance. The JVM treats enum constants specially: reflective construction is blocked, and deserialization always returns the canonical constant rather than constructing a new one.

Two things to be honest about, though:

1. The "INSTANCE" name reads awkwardly at the call site. Some teams alias it (`public static final Config CONFIG = Config.INSTANCE;`) to make calls read more naturally.
2. **Most singletons shouldn't exist in the first place.** A singleton is global mutable state with a polite haircut, and it makes testing painful (you can't substitute a fake) and concurrent code subtle. In any codebase using a DI framework or even hand-rolled constructor injection, the better answer is usually "construct one instance at startup and pass it around" — not "make it a global." We'll revisit this in 7.1 (Creational Patterns), where the case against most singletons gets the full treatment. The enum-singleton idiom is the right tool when you've actually decided you want a global; just be sure you want one.

## When *not* to use an enum

Enums are addictive — once you internalize how much they can do, the temptation is to model everything as one. Resist for:

- **Sets that aren't actually fixed.** Currencies feel like a closed set, until your business adds a new one and you don't want to redeploy every service that touches money. Use a value class with an interned set of well-known instances, or a database lookup, or both.
- **Values with rich behavior or substantial state.** Enums can carry methods and fields, but they're not great for complex behavior — the lack of per-instance configurability and the singleton nature both fight you. A regular class is often clearer.
- **Anything that needs to be subtyped by downstream code.** Enums can't be extended. If you need a sealed-but-extensible-by-permitted-subtypes hierarchy, that's what sealed interfaces (1.5) are for.

The check before reaching for an enum: "Is the set of values closed, finite, known at compile time, and stable across the lifetime of the codebase?" If yes, enum. If any of those is shaky, something else.

## DIY Exercise

Build an `Operation` enum and a tiny string-to-operation parser. The goal is to feel how per-constant method bodies, `EnumMap`, and the `values()` iteration all compose.

**Part 1 — define the enum.**

- Declare `Operation` with four constants: `PLUS`, `MINUS`, `TIMES`, `DIVIDE`.
- Each constant carries its arithmetic symbol as a field (`"+"`, `"-"`, `"*"`, `"/"`). Add a constructor and a `symbol()` accessor.
- Declare `public abstract double apply(double x, double y);` on the enum, and give each constant its own constant-specific body that implements it.
- Make sure your `DIVIDE` body doesn't bother checking for division by zero — Java's `double` arithmetic returns `Infinity` or `NaN`, which is fine for this exercise. (Money math is different — never use `double`. We'll get to `BigDecimal` in 4.1.)

**Part 2 — write the parser.**

Add a static method `Operation fromSymbol(String s)` to the enum. The naive implementation is a switch over the string:

```java
return switch (s) {
    case "+" -> PLUS;
    case "-" -> MINUS;
    case "*" -> TIMES;
    case "/" -> DIVIDE;
    default -> throw new IllegalArgumentException("unknown operator: " + s);
};
```

That works, but the point of the exercise is to use an `EnumMap`-style lookup. Do it this way instead:

- Build a `static final Map<String, Operation> BY_SYMBOL` initialized in a `static` block by iterating `values()` and putting each constant's `symbol()` → constant into the map.
- Use `Map.of`/`HashMap` for this — `EnumMap`'s keys must be enum constants, and your keys are strings. (`EnumMap` shines in Part 3.)
- `fromSymbol` becomes a one-liner: look up the symbol, throw `IllegalArgumentException` if absent. Use `Optional.ofNullable(...).orElseThrow(...)` or an explicit null check — your call.

The reason to prefer the map over the switch even though both work: when you later add `MODULO` with symbol `"%"`, the map version requires you to update *only* the enum declaration. The static initializer rebuilds itself. The switch version requires you to find and update every switch, which the compiler can't help with because the cases are strings, not enum constants.

**Part 3 — use an `EnumMap` for the other direction.**

Now add a static `Map<Operation, String> DESCRIPTIONS` that maps each constant to a human-readable description ("addition", "subtraction", etc.). This one *should* be an `EnumMap`, because the keys are enum constants:

```java
static final Map<Operation, String> DESCRIPTIONS;
static {
    DESCRIPTIONS = new EnumMap<>(Operation.class);
    DESCRIPTIONS.put(PLUS, "addition");
    // ...
}
```

Add a `description()` instance method that returns `DESCRIPTIONS.get(this)`.

**Part 4 — exercise it in `main`.**

- Parse the string `"3 + 4 * 2"` by splitting on whitespace, walking left-to-right (no operator precedence — just left-fold), and applying each operator via `fromSymbol`. Print the result. (`3 + 4 * 2` left-folded is `(3 + 4) * 2 = 14`.)
- For each `Operation` constant, print its symbol and description on one line. Use `Operation.values()` to iterate. Confirm the output is in declaration order.
- Call `Operation.valueOf("PLUS")` and confirm it returns the same object as `Operation.PLUS` (compare with `==`). Then call `Operation.valueOf("plus")` and observe the `IllegalArgumentException`.

Single-file source mode: one file, no `package` declaration, run with `java Operation.java`. You'll need `import java.util.*;` for the maps.

**Things to think about while you write it:**

- Why is the constructor `private` (implicitly)? What would go wrong if it weren't?
- The static initializer for `BY_SYMBOL` runs once, at class load. What happens if two constants accidentally share the same symbol? (Try it — add a fifth constant with symbol `"+"` and see which one wins. Then think about whether you'd want the static initializer to fail loudly instead.)
- You chose constant-specific method bodies for `apply`. The switch-expression form would also work. For four arithmetic operations, which form would you actually prefer in production code, and why?
- `EnumMap` doesn't allow `null` keys but does allow `null` values. Where in your code does that matter? (Hint: `DESCRIPTIONS.get(someOp)` returning `null` would mean you forgot to register one. Would you rather catch that at class load — by initializing every constant up-front and asserting completeness — or at first use?)
- If you were going to add a `MODULO` operation tomorrow, what's the smallest set of edits you'd need to make? Walk through it mentally. The "one place to add" property is a big part of why enums are a better tool than a `String` constant for closed sets.
