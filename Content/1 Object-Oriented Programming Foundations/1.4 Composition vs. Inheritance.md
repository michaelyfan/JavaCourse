# 1.4 Composition vs. Inheritance

"Favor composition over inheritance" is one of the most-repeated rules in OO design, and like most repeated rules it has lost most of its meaning along the way. It isn't "inheritance is bad" — it's a specific claim about coupling. Inheritance ties a subclass to *the current implementation* of its superclass, not just its public API. Composition ties one object to another's *public API only*. When the thing you're modeling really is an "is-a" specialization, inheritance is fine. When you mostly want to reuse behavior — which is most of the time — inheritance buys reuse at a coupling cost that composition doesn't charge.

---

## What "composition" means

Inheritance has had its own submodule (1.2) and you've used it for several DIYs. **Composition** is the other way one class can build on another, and it has no special syntax — it's just *one class holding an instance of another as a field and calling methods on it.* You've been doing it the whole time without anyone naming it.

```java
public class Order {
    private final Customer customer;          // Order has-a Customer
    private final List<LineItem> lineItems;   // Order has-a List of LineItems

    public BigDecimal total() {
        return lineItems.stream()             // delegating work to the held list
            .map(LineItem::price)
            .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}
```

That's composition. `Order` doesn't `extend Customer` or `extend ArrayList` — it *holds* them and calls their methods. The shorthand is **"has-a" vs. "is-a"**: a `Circle` *is a* `Shape` (inheritance); an `Order` *has a* `Customer` (composition).

The variation that's specifically the alternative to inheritance is **composition with delegation**: holding an instance of some type *and implementing the same interface*, forwarding most method calls through to the held instance and overriding only the ones you want to change. That's the pattern this whole lesson is about. The wrapper looks like a subclass from the outside (same interface, same methods) but is wired differently inside (forwarding through a field, not inheriting from a parent). The next sections show why that wiring difference matters.

---

## What inheritance actually couples you to

The promise of inheritance is "I get the parent's behavior for free, and I can change what I want by overriding." The reality is that *the parent's behavior depends on which of its own methods it calls internally*, and those internal calls are not part of the public contract. When you override a method, you're not just changing what callers see — you're also changing what the superclass sees when it calls itself.

The canonical example, from *Effective Java*, is a counting `HashSet`:

```java
public class CountingSet<E> extends HashSet<E> {
    private int addedCount = 0;

    @Override
    public boolean add(E e) {
        addedCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addedCount += c.size();
        return super.addAll(c);
    }

    public int addedCount() { return addedCount; }
}

var s = new CountingSet<String>();
s.addAll(List.of("a", "b", "c"));
// addedCount is 6, not 3
```

Why? `HashSet.addAll` is implemented by iterating its argument and calling `this.add(...)` for each element. Because `add` is overridden, the override fires for each element too, so the count is incremented twice — once in `addAll`, once again in each `add`. The class is broken not because the author misunderstood `HashSet`'s public API, but because they didn't know its *internal* call structure.

Now imagine a future JDK release rewrites `HashSet.addAll` to call a private helper instead of `add`. The bug silently flips: now `addAll` only counts once and `add`-by-itself still counts once, but the version-to-version behavior is different for the same source code. The subclass's correctness depends on the superclass's implementation choices, which are not contractual.

This is the **fragile base class problem**: changes to a base class that don't touch its public API can still break subclasses, because subclasses are coupled to internal call patterns and to the set of methods that *exist* (adding a new method to the base class can clash with an unrelated method the subclass already had).

---

## What composition does instead

Composition replaces "is-a" with "has-a." The wrapper holds an instance of the underlying type and forwards every method through it. Overrides on the wrapper do not feed back into the wrapped object's internal calls, because the wrapped object only ever calls its own methods.

```java
public class CountingSet<E> implements Set<E> {
    private final Set<E> delegate;
    private int addedCount = 0;

    public CountingSet(Set<E> delegate) {
        this.delegate = delegate;
    }

    @Override
    public boolean add(E e) {
        addedCount++;
        return delegate.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addedCount += c.size();
        return delegate.addAll(c);   // delegate.addAll calls delegate.add — not ours
    }

    public int addedCount() { return addedCount; }

    // ...forward the remaining Set methods to delegate...
    @Override public int size() { return delegate.size(); }
    @Override public boolean contains(Object o) { return delegate.contains(o); }
    @Override public Iterator<E> iterator() { return delegate.iterator(); }
    // and so on
}
```

Now `addAll` increments by `c.size()`, then `delegate.addAll(c)` runs — and when *that* calls `add`, it calls `delegate.add`, not ours. The count is right. Whether the JDK rewrites `HashSet.addAll` to call a private helper makes no difference; we never depended on that detail.

The cost is real: you have to forward every method on `Set` that you don't want to change. For wide interfaces this is tedious. The standard answer is a **forwarding class**: a base implementation that delegates everything to a held instance, which your wrapper extends and overrides only the methods it cares about. Guava's `ForwardingSet`, `ForwardingList`, etc. exist for exactly this. The standard library doesn't ship forwarding classes for collections, but the pattern is straightforward to write.

```java
public class ForwardingSet<E> implements Set<E> {
    private final Set<E> delegate;
    protected ForwardingSet(Set<E> delegate) { this.delegate = delegate; }

    @Override public int size() { return delegate.size(); }
    @Override public boolean isEmpty() { return delegate.isEmpty(); }
    @Override public boolean contains(Object o) { return delegate.contains(o); }
    @Override public boolean add(E e) { return delegate.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) { return delegate.addAll(c); }
    // ...and so on for every method
}

public class CountingSet<E> extends ForwardingSet<E> {
    private int addedCount = 0;
    public CountingSet(Set<E> delegate) { super(delegate); }

    @Override public boolean add(E e) { addedCount++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        addedCount += c.size();
        return super.addAll(c);
    }
    public int addedCount() { return addedCount; }
}
```

Notice we *do* inherit from `ForwardingSet`, but that's fine: `ForwardingSet` is a class we control, designed for extension, with a known and stable internal call pattern (none — every method just forwards). Inheritance is dangerous when the parent's internals are out of your control or subject to change. A class you wrote and explicitly designed for extension does not have that problem.

## When inheritance is still the right answer

Three situations where reaching past inheritance to composition is just extra work:

**1. The "is-a" really holds, and the parent was designed for extension.** Abstract classes like `AbstractList`, `HttpServlet`, or your own `Notification` from 1.3 exist *to be extended*. They document which methods are hooks for subclasses, which are final, and what the protected protocol is. Subclassing them is using them as intended, not abusing them.

**2. Framework hooks (Template Method, see 7.3).** When a framework hands you a base class whose only job is to invoke your overrides at specific points — `HttpServlet.doGet`, JUnit 4's `TestCase`, Swing's `JPanel` for custom rendering — inheritance is the API. There is nothing to compose.

**3. Sealed hierarchies modeling a closed set of variants (1.5).** When `Shape` is sealed and permits exactly `Circle`, `Rectangle`, `Triangle`, you genuinely have a finite "is-a" world and pattern-matching benefits from it. This is inheritance used for *modeling*, not for *behavior reuse*.

The common thread: inheritance is fine when it's the parent's intent to be extended. It goes wrong when you're reaching across a fence — extending a class whose author wasn't planning on you, whose internals you don't control, and whose next version might change in ways the public API doesn't telegraph.

---

## "I just want to add one method" is the warning sign

The most common slip into bad inheritance is wanting to add a small behavior to an existing class. `LoggingHashSet extends HashSet` to log every add. `TimestampedHashMap extends HashMap` to record when keys were inserted. `RetryingHttpClient extends HttpClient` to retry on 5xx.

In every one of these, the question to ask is: do you want a *kind of* `HashSet`/`HashMap`/`HttpClient`, or do you want *a thing that uses one and adds behavior on top*? Almost always the answer is the second, and the difference matters: the second version doesn't break when the JDK changes `HashSet.addAll`'s implementation, doesn't accidentally inherit methods you don't want exposed, and can be backed by *any* `Set`/`Map`/`HttpClient` implementation, not just the concrete one you extended.

The mechanical heuristic: if you're overriding a method to "add" behavior (count, log, time, retry) rather than to change *what* the method fundamentally does, you almost certainly want composition.

## Delegation patterns in the wild

Composition + delegation is the shape of several patterns covered in Module 7. They all have the same skeleton — hold a delegate, forward most methods, change a few — but with different intent:

- **Decorator** (7.2): wraps an object to add behavior. `BufferedInputStream` wraps any `InputStream` to add buffering; `Collections.unmodifiableList` wraps a list to forbid mutation. Both implement the same interface as the thing they wrap, so callers don't know or care.
- **Adapter** (7.2): wraps an object to expose a *different* interface. `Arrays.asList` adapts an array to look like a `List`.
- **Proxy** (7.2): wraps an object to control access or add cross-cutting behavior (logging, security checks, lazy loading).

When you see one of these in the wild, notice that they *could* have been written with inheritance — `BufferedInputStream` could have extended `FileInputStream`. They aren't, because that would have tied buffering to a specific source. Composition lets one decorator wrap *any* input stream.

---

## Picking between them

| Question | If yes, lean toward |
|---|---|
| Is this genuinely an "is-a" specialization that the base author anticipated? | Inheritance |
| Are you mostly reusing behavior and adding a little on top? | Composition |
| Is the base class out of your control (JDK, third-party library)? | Composition |
| Do you need to swap which implementation backs your wrapper? | Composition |
| Is the base class a framework hook designed for overriding? | Inheritance |
| Will you need to expose a *different* interface than the wrapped object? | Composition (adapter shape) |

When you're unsure: write the composition version. The overhead is one field and some forwarding methods. The payoff is decoupling from a base class's internals — which you'll be glad of the first time the JDK ships a point release that changes one.

## DIY Exercise

You're going to feel the fragile base class problem firsthand, then fix it with composition.

**Part 1 — reproduce the bug.**

- Write `LoggingHashSet<E> extends HashSet<E>` that overrides `add(E)` and `addAll(Collection<? extends E>)` to print a log line before delegating to `super`.
- In `main`, create one, call `addAll(List.of("a", "b", "c"))`, and observe the output.
- You should see *four* log lines (one for the `addAll`, then three for the `add` calls `HashSet.addAll` makes internally — it inherits `addAll` from `AbstractCollection`, which iterates and calls `this.add` for each element). Confirm this matches what you'd expect after reading the lesson.
- Why `HashSet` and not `ArrayList`? `ArrayList.addAll` is specifically optimized to copy into the backing array with `System.arraycopy` — it never calls `this.add`, so an override of `add` doesn't fire from `addAll`. The fragile-base-class bug is real, but whether it bites you depends entirely on the parent's internal implementation choices. That dependency is the whole point of the lesson.

**Part 2 — fix it with composition.**

- Write `LoggingSet<E> implements Set<E>` that holds a `private final Set<E> delegate` (passed in via constructor) and logs every mutating public operation: `add`, `addAll`, `remove`, `removeAll`, `retainAll`, `clear`.
- Forward every other `Set` method to `delegate` without logging.
- In `main`, build a `LoggingSet<>(new HashSet<>())`, call `addAll(List.of("a", "b", "c"))`, and confirm you see exactly one log line for the `addAll` call.

Things to think about while you write it:

- Your IDE will offer to generate the forwarding methods. Use that — it's exactly the tedium composition trades for correctness. (Guava's `ForwardingList` exists so you don't write this by hand in production; here, write it by hand once to feel the cost.)
- What happens if a caller does `loggingList.iterator().remove()`? Did your wrapper see it? If not — is that a bug, and how would you fix it? (Hint: you'd have to wrap the iterator too. Decorators compose all the way down.)
- Could you achieve the same result by passing a `Consumer<String>` logger into your wrapper instead of hardcoding `System.out.println`? What does that buy you when you want to test it in Module 2?
- If `LoggingList` is parameterized as `LoggingList<E>`, can the caller pass `new LoggingList<Number>(new ArrayList<Integer>())`? Why or why not? (This is a preview of generics variance, covered in 3.2.)
