# 2.1 JUnit 5 Fundamentals

Module 1 ended with a real package layout and a classpath you control. That was the prerequisite for this one. Every DIY from here on is verified by a JUnit test instead of an ad-hoc `main` that prints things and trusts your eyes.

The shift matters more than it sounds. A `main` that prints `balance = 100` proves nothing — *you* still have to know `100` was the right answer and notice if it changes. A test *encodes* the expected answer once, then re-checks it on every run, forever, without you. That is the entire value proposition: tests turn "I checked it once" into "it is checked every time."

This submodule is the mechanics of JUnit 5 — enough to write real test suites and run them from the classpath with no Maven or Gradle. Module 2.2 adds test doubles; concurrency-specific testing waits for 6.5.

---

## What "JUnit 5" actually is

"JUnit 5" is three things, and the distinction shows up in jar names and package names:

- **JUnit Jupiter** — the API you write tests against (`@Test`, `Assertions`, `@ParameterizedTest`). Versioned `5.x`. Its packages start `org.junit.jupiter`.
- **JUnit Platform** — the engine-agnostic launcher that *finds and runs* tests. Versioned `1.x`. This is what IDEs and build tools talk to.
- **JUnit Vintage** — a compatibility engine that runs old JUnit 3/4 tests on the Platform. You won't need it; this course is Jupiter-only.

The two version numbers travel together: Platform `1.11.x` ships with Jupiter `5.11.x`. You'll see both. When you read `org.junit.jupiter.api.Test`, that's Jupiter; when you read about `--scan-class-path`, that's the Platform.

## Project layout: `src/main/java` vs. `src/test/java`

The universal Java convention — predating Maven, enforced by every build tool — separates production code from test code into two parallel source trees:

```
2.1 JUnit 5 Fundamentals/
  src/
    main/java/
      roman/
        RomanNumeralConverter.java     // package roman;
    test/java/
      roman/
        RomanNumeralConverterTest.java // package roman;  <-- same package!
  lib/
    junit-platform-console-standalone-1.11.4.jar
  out/                                 // compiled .class files
```

Two things about this layout are load-bearing:

1. **Test code is a separate tree but the *same packages*.** `RomanNumeralConverterTest` declares `package roman;` exactly like the class it tests. The two `.java` files live in different directories (`src/main/java/roman/` vs. `src/test/java/roman/`) but compile into the *same* logical package. That's deliberate: a test in the same package can exercise package-private members (1.1) without you having to widen visibility just to test something. Test code is a first-class consumer of your package-private API.

2. **The two trees compile separately and the test tree depends on the main tree.** Production code never references test code or the JUnit jar. Test code references both. This is why they're separate roots, not one mixed folder — it makes the dependency direction physically impossible to get wrong.

The convention is `Test` as a *suffix* on the class name (`RomanNumeralConverterTest`). The Platform's classpath scanner uses naming patterns to decide what to run, and `*Test` / `*Tests` is the default it recognizes.

## Getting JUnit without Maven or Gradle

A normal project lets the build tool download JUnit. This course runs from the bare classpath, so you fetch one jar yourself: **`junit-platform-console-standalone`**. It is a fat jar — Jupiter API, Jupiter engine, the Platform launcher, and a command-line runner, all bundled. One file, no transitive-dependency hunting.

Download it once from Maven Central into a `lib/` folder:

```
https://repo1.maven.org/maven2/org/junit/platform/junit-platform-console-standalone/1.11.4/junit-platform-console-standalone-1.11.4.jar
```

(Any recent `1.1x.x` release behaves identically — the version in these commands is just an example.)

### Compile and run — the three commands

**1. Compile production code** into `out/main`:

```
javac -d out/main $(find src/main/java -name '*.java')
```

**2. Compile test code**, putting both the compiled production classes *and* the JUnit jar on the classpath (the test code references both):

```
javac -cp out/main:lib/junit-platform-console-standalone-1.11.4.jar \
      -d out/test $(find src/test/java -name '*.java')
```

**3. Run the tests** with the console launcher's `execute` subcommand, scanning the classpath for test classes:

```
java -jar lib/junit-platform-console-standalone-1.11.4.jar execute \
     -cp out/main:out/test --scan-class-path
```

A few notes on this:

- The classpath separator is `:` on macOS/Linux, `;` on Windows — same rule as 1.8.
- `--scan-class-path` tells the launcher "find every test class on the classpath I gave you." Alternatively, `--select-class roman.RomanNumeralConverterTest` runs exactly one class.
- The launcher prints a tree of results and a summary (`tests successful`, `tests failed`) and exits non-zero if anything failed — which is what makes it usable in a script or CI later.
- This recall of `compile main → compile test → run` is exactly what the prediction at the end of 1.8 was pointing at. The test command differs from a production run only by having the JUnit jar and the test classes on the classpath.

Most engineers run tests through an IDE day to day. Do the command-line version anyway, at least until it's boring. Knowing what the IDE automates keeps the magic from becoming mystery — the same reason 1.8 made you run `javac` by hand.

## A first test

```java
package roman;

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class RomanNumeralConverterTest {

    @Test
    void convertsThree() {
        RomanNumeralConverter converter = new RomanNumeralConverter();
        assertEquals("III", converter.toRoman(3));
    }
}
```

Everything here is deliberate:

- **`@Test`** marks a method as a test. No return value, no parameters (the parameterized variants come later), any name. The method name *is* documentation — name it after the behavior, not `test1`.
- **The class and method are package-private**, not `public`. JUnit 4 required `public`; JUnit 5 does not, and the convention is to drop it. Less noise, and it signals "this type is not API."
- **`assertEquals(expected, actual)`** — argument order is *expected first*. Get this backwards and the failure message ("expected X but was Y") reads inside-out, which is genuinely confusing at 2am. Burn the order in.
- **`import static`** on the assertions. This is the canonical place wildcard static imports are accepted (1.8): `import static org.junit.jupiter.api.Assertions.*;` is idiomatic in test files because `assertEquals(...)` reads far better than `Assertions.assertEquals(...)` and there's no ambiguity about where it came from.

A test "passes" if it returns normally and "fails" if an assertion throws (`AssertionError`) or any other exception escapes. There is no "return true." The absence of a thrown error *is* the pass.

## Assertions

An assertion is a checked claim. If the claim is false, it throws and the test fails with a message. The core set lives in `org.junit.jupiter.api.Assertions`:

| Assertion | Claims |
|---|---|
| `assertEquals(expected, actual)` | The two are equal (via `equals` for objects, `==` for primitives) |
| `assertNotEquals(unexpected, actual)` | They are *not* equal |
| `assertTrue(condition)` / `assertFalse(condition)` | A boolean is true / false |
| `assertNull(x)` / `assertNotNull(x)` | A reference is / isn't null |
| `assertSame(expected, actual)` | Same *object identity* (`==`), not just `equals` |
| `assertThrows(Type.class, executable)` | Running the code throws that exception type |
| `assertDoesNotThrow(executable)` | Running the code throws nothing |
| `assertAll(...)` | Groups assertions — see below |
| `fail("message")` | Unconditionally fails — useful for "should not reach here" |

### Messages: prefer `assertEquals` over `assertTrue`

`assertTrue(converter.toRoman(3).equals("III"))` and `assertEquals("III", converter.toRoman(3))` both pass and fail at the same times. They are *not* equivalent on failure. The first reports only `expected: <true> but was: <false>` — useless. The second reports `expected: <III> but was: <IIII>` — it tells you what actually happened. Reach for the most *specific* assertion available, because the specific one knows both values and the generic one doesn't.

Every assertion takes an optional last-argument message:

```java
assertEquals("III", converter.toRoman(3), "3 should convert to III");
```

Pass it as a `Supplier<String>` (`() -> "..."`) when building the message is expensive — the lambda only runs on failure. For a string literal, don't bother.

### `assertThrows` — testing the failure path

Code that's *supposed* to reject bad input needs that rejection tested. `assertThrows` runs a lambda and asserts it throws:

```java
@Test
void rejectsZero() {
    RomanNumeralConverter converter = new RomanNumeralConverter();
    assertThrows(IllegalArgumentException.class,
                 () -> converter.toRoman(0));
}
```

It *returns the caught exception*, so you can make further claims about it:

```java
@Test
void rejectsZeroWithClearMessage() {
    var converter = new RomanNumeralConverter();
    IllegalArgumentException ex = assertThrows(
            IllegalArgumentException.class,
            () -> converter.toRoman(0));
    assertTrue(ex.getMessage().contains("0"));
}
```

The body must be a lambda, not a direct call. `assertThrows(..., converter.toRoman(0))` would evaluate `toRoman(0)` *before* `assertThrows` ever runs, the exception would escape uncaught, and the test would error out instead of passing. Deferring the call into a `() -> ...` is the whole point — `assertThrows` needs to run it inside its own try/catch.

Match the exception type as *narrowly* as is correct. `assertThrows(Exception.class, ...)` passes for *any* exception including `NullPointerException` from an unrelated bug — it would happily go green on broken code. Assert the specific type you actually promise to throw.

### `assertAll` — don't stop at the first failure

A plain assertion that fails throws immediately; every assertion after it in the method never runs. Usually fine. But when you're checking several *independent* facets of one result, stopping early hides information — you fix one, rerun, discover the next, fix it, rerun... `assertAll` runs every grouped assertion and reports *all* the failures at once:

```java
@Test
void parsesFullName() {
    Name name = Name.parse("Ada Lovelace");
    assertAll("name",
        () -> assertEquals("Ada", name.first()),
        () -> assertEquals("Lovelace", name.last())
    );
}
```

If both are wrong you see both. Use it for "multiple properties of a single object." Don't use it to staple together assertions about unrelated things — that's two tests wearing a trench coat.

### Asserting on `double`

`assertEquals(0.3, a + b)` for doubles is a trap — floating-point rounding means `0.1 + 0.2 != 0.3`. The `double` overload takes a tolerance: `assertEquals(0.3, a + b, 1e-9)`. (For money, the real fix is `BigDecimal`, not a tolerance — that argument is made in 4.1.)

## The test lifecycle

Most tests need setup: build the object under test, maybe seed some state. Doing it inline in every method is repetitive. The lifecycle annotations factor it out.

```java
class BankAccountTest {

    private BankAccount account;

    @BeforeAll
    static void onceBeforeEverything() {
        // expensive shared setup: start a fake server, load a fixture file
    }

    @BeforeEach
    void freshAccount() {
        account = new BankAccount(BigDecimal.valueOf(100));
    }

    @Test
    void depositIncreasesBalance() {
        account.deposit(BigDecimal.valueOf(50));
        assertEquals(BigDecimal.valueOf(150), account.balance());
    }

    @Test
    void withdrawDecreasesBalance() {
        account.withdraw(BigDecimal.valueOf(30));
        assertEquals(BigDecimal.valueOf(70), account.balance());
    }

    @AfterEach
    void afterEachTest() {
        // per-test cleanup: close a resource, reset a file
    }

    @AfterAll
    static void onceAfterEverything() {
        // tear down the expensive shared setup
    }
}
```

| Annotation | Runs | Typical `static`? |
|---|---|---|
| `@BeforeAll` | Once, before any test in the class | Yes |
| `@BeforeEach` | Before *every* test method | No |
| `@AfterEach` | After *every* test method (even if it failed) | No |
| `@AfterAll` | Once, after all tests in the class | Yes |

### The single most important lifecycle fact: a fresh instance per test

**JUnit creates a brand-new instance of the test class for every `@Test` method.** `depositIncreasesBalance` and `withdrawDecreasesBalance` run on two *different* `BankAccountTest` objects. The `account` field is therefore not shared between them — and `@BeforeEach` rebuilds it fresh anyway.

This is a designed-in defense against the worst category of test bug: **order-dependent tests**. If tests shared one instance, a field mutated by test A would leak into test B, and the suite would pass or fail depending on the order JUnit happened to pick. Per-method instances make each test start from a clean slate. Tests must never depend on each other or on execution order — and JUnit's instance model enforces it for instance fields.

The catch: that's why `@BeforeAll`/`@AfterAll` are `static` by default — there's no single instance for them to belong to, so they belong to the class. (You *can* make them non-static by annotating the class `@TestInstance(Lifecycle.PER_CLASS)`, which switches to one shared instance. It's an advanced opt-in. Default — per-method — is the right choice almost always; reach for `PER_CLASS` only with a deliberate reason.)

`@BeforeEach` is where the bulk of your setup goes. Reserve `@BeforeAll` for things genuinely too expensive to repeat — and remember anything shared across tests is shared *mutable* state, with all the order-dependence risk that implies.

## Parameterized tests

When the same logic needs checking against many inputs, copy-pasting `@Test` methods is the wrong move — twenty near-identical methods that drift apart over time. A `@ParameterizedTest` runs *one* method body once per data row, each row reported as its own test case.

Swap `@Test` for `@ParameterizedTest`, add a *source* that supplies arguments, and give the method matching parameters.

### `@ValueSource` — one argument, simple literals

```java
@ParameterizedTest
@ValueSource(ints = {1, 3, 5, 7, 99})
void everyOddNumberIsOdd(int candidate) {
    assertTrue(candidate % 2 != 0);
}
```

`@ValueSource` carries a single array of literals (`ints`, `longs`, `doubles`, `strings`, `booleans`, ...). It's the lightest option and also the most limited: one parameter only, constants only.

### `@CsvSource` — multiple arguments per row

```java
@ParameterizedTest
@CsvSource({
    "1,    I",
    "4,    IV",
    "9,    IX",
    "40,   XL",
    "2024, MMXXIV"
})
void convertsToRoman(int input, String expected) {
    assertEquals(expected, new RomanNumeralConverter().toRoman(input));
}
```

Each string is one comma-separated row; the columns map positionally to the method parameters, with JUnit converting `"1"` to `int`, `"I"` to `String`, and so on. This is the workhorse for table-style tests — a column of inputs beside a column of expected outputs, the whole truth table visible at a glance. Notes:

- Whitespace around values is trimmed by default.
- A value with a comma in it must be quoted: `"'a,b', 2"` — `@CsvSource` uses `'` as its quote character.
- An empty cell is `""` (empty string); to express `null`, set `nullValues = "NULL"` on the annotation and write `NULL` in the cell.
- For many rows, `@CsvFileSource(resources = "/cases.csv")` reads from a file on the classpath instead.

### `@MethodSource` — when arguments aren't literals

`@CsvSource` only holds things expressible as text. When inputs are real objects — a constructed `BankAccount`, a `List`, a `LocalDate` — supply them from a method that returns a `Stream` (or any `Iterable`) of arguments:

```java
@ParameterizedTest
@MethodSource("withdrawalCases")
void withdrawalLeavesExpectedBalance(BigDecimal start, BigDecimal amount, BigDecimal expected) {
    BankAccount account = new BankAccount(start);
    account.withdraw(amount);
    assertEquals(expected, account.balance());
}

static Stream<Arguments> withdrawalCases() {
    return Stream.of(
        Arguments.of(new BigDecimal("100"), new BigDecimal("30"), new BigDecimal("70")),
        Arguments.of(new BigDecimal("50"),  new BigDecimal("50"), new BigDecimal("0"))
    );
}
```

The factory method is `static` (under the default per-method lifecycle) and its name is passed as a string to `@MethodSource`. Each `Arguments.of(...)` is one row; the elements map positionally to parameters. For a single-parameter test the method can skip `Arguments` and just return `Stream<String>`, `IntStream`, etc.

### `@EnumSource` — every constant of an enum

```java
@ParameterizedTest
@EnumSource(Operation.class)
void everyOperationHasASymbol(Operation op) {
    assertNotNull(op.symbol());
}
```

Runs once per enum constant — a clean way to assert a property holds for *all* of them, and one that automatically picks up a new constant when someone adds one.

### `@DisplayName` placeholders

Parameterized cases get readable labels via a name template on the annotation:

```java
@ParameterizedTest(name = "{0} -> {1}")
@CsvSource({"1, I", "4, IV"})
void convertsToRoman(int input, String expected) { ... }
```

`{0}`, `{1}`, ... are the arguments; `{index}` is the 1-based row number. Without this you get `[1]`, `[2]` in the report, which tells you nothing about *which* row failed.

## Nested tests

A test class for a non-trivial type sprawls. `@Nested` lets an *inner class* group related tests, and the grouping shows up as a tree in the report:

```java
class BankAccountTest {

    @Nested
    class Deposits {
        @Test void increasesBalance() { ... }
        @Test void rejectsNegativeAmount() { ... }
    }

    @Nested
    class Withdrawals {
        @Test void decreasesBalance() { ... }
        @Test void rejectsOverdraft() { ... }
    }
}
```

The lifecycle composes the way you'd hope: an outer `@BeforeEach` runs before *every* test including those in nested classes, then the nested class's own `@BeforeEach` runs. That lets a nested group layer extra setup on top of a shared base — e.g., the outer block builds an empty account, an `@Nested OverdrawnAccount` adds a `@BeforeEach` that withdraws it into a specific state, and every test inside starts from there.

The nested class must be a non-`static` inner class (1.7) — it needs the reference to the outer instance so it can see outer fields.

## Display names

Method names can't contain spaces, so `withdrawalLeavesExpectedBalance` is as readable as a method name gets. `@DisplayName` overrides the label shown in reports with free text:

```java
@Test
@DisplayName("withdrawing more than the balance is rejected")
void rejectsOverdraft() { ... }
```

Use it where the extra clarity earns its keep — and let a well-named method stand on its own where it doesn't. A report that reads like sentences is genuinely easier to scan when something breaks. (There's also `@DisplayNameGeneration` for applying a naming style class-wide; know it exists, don't over-invest.)

## Tags and filtering

`@Tag` attaches a label to a test or class so the launcher can include or exclude it:

```java
@Test
@Tag("slow")
void fullEndToEndRun() { ... }
```

Then filter at run time:

```
java -jar lib/junit-platform-console-standalone-1.11.4.jar execute \
     -cp out/main:out/test --scan-class-path \
     --exclude-tag slow
```

The point: not every test should run on every invocation. A fast unit-test pass on every save, the slow integration tag only before a commit. Tags are how one suite serves both. You won't need them for the small DIYs here, but recognize the mechanism — real projects lean on it heavily.

## What makes a test *good*

JUnit mechanics are necessary, not sufficient. A few principles outlast any framework:

- **One reason to fail per test.** When a test breaks, its name and its single assertion should point straight at the cause. A test asserting six unrelated things makes you debug the test before you can debug the code.
- **Arrange, Act, Assert.** Set up the inputs, perform the one action under test, check the outcome. Keeping those three phases visually distinct makes a test readable in seconds.
- **Test behavior, not implementation.** Assert *what the method promises* — its observable result — not *how* it computes it. A test coupled to internals breaks on every harmless refactor and stops being a safety net, becoming a tax instead.
- **Deterministic.** Same code, same result, every run. A test that depends on wall-clock time, random values, map iteration order, or another test having run first is worse than no test — a flaky failure trains you to ignore failures.
- **Test the edges.** The bug is rarely in `toRoman(3)`. It's in `0`, the negative, the max value, the empty string, the `null`. Spend your assertions at the boundaries.
- **Fast.** A suite you don't mind running constantly is a suite you'll actually run. Slow tests get skipped, and skipped tests catch nothing.

You don't need a coverage tool yet. Coverage measures which lines *ran*, not whether they ran *correctly* — 100% coverage with weak assertions proves nothing. Aim for *meaningful* cases, especially the failure paths, not a percentage.

## DIY Exercise

Two parts. Both use the `src/main/java` + `src/test/java` layout above, compiled and run with the three commands from the "Getting JUnit" section.

### Part 1 — `RomanNumeralConverter`

Write a `RomanNumeralConverter` with a method `String toRoman(int n)` that converts `1`–`3999` to a Roman numeral, and rejects anything outside that range with an `IllegalArgumentException`.

Then write `RomanNumeralConverterTest`:

1. **A `@ParameterizedTest` with `@CsvSource` covering at least 20 inputs.** Include the simple cases (`1 → I`, `10 → X`), the subtractive cases (`4 → IV`, `9 → IX`, `40 → XL`, `90 → XC`, `400 → CD`, `900 → CM`), and a few large composites (`1994 → MCMXCIV`, `3888 → MMMDCCCLXXXVIII`). Use a `name` template so each row is labeled by its data.
2. **Error cases via `assertThrows`.** Assert that `0`, a negative number, and `4000` each throw `IllegalArgumentException`. For at least one, capture the returned exception and assert its message mentions the offending value.

### Part 2 — pin the `BankAccount` invariant

Go back to the Module 1.1 `BankAccount`. Add `BankAccountTest`:

1. Use `@BeforeEach` to build a fresh account before each test.
2. Assert deposit increases and withdraw decreases the balance.
3. Assert deposit/withdraw of a negative or zero amount throws.
4. Assert that constructing with a negative initial balance throws.
5. Add the test that the 1.1 exercise asked you to *imagine*: pin the **"balance is never negative"** invariant. Apply a sequence of valid and invalid operations and assert that after every step `balance()` is `>= 0` — and that the operations which *would* have driven it negative were rejected rather than applied.

Things to think about:

- Should `BankAccountTest` live in the same package as `BankAccount`? What does that buy you, and would the answer change if you needed to verify a package-private helper?
- Your 20 `@CsvSource` rows could instead be 20 separate `@Test` methods. Articulate precisely what the parameterized version gives you — and the one thing it costs (hint: a row that throws unexpectedly vs. a row that returns the wrong value — how does each look in the report?).
- You wrote a test for `toRoman` returning the right string *and* a test for it throwing. Which of those two did the original `main`-and-eyeball approach make easy to forget? That asymmetry is most of why the failure path is where bugs hide.
- If `toRoman` had a bug only at `3999`, which of your tests would catch it? If the honest answer is "none," add the row.

From here on, every DIY ships with a `src/test/` tree. The next submodule, 2.2, handles the case your tests can't yet: a class under test that depends on *other* classes you don't want to really invoke.
