# 2.2 Mockito and Test Doubles

The tests in 2.1 had it easy. `RomanNumeralConverter` and `BankAccount` are *self-contained* — feed them inputs, check outputs, done. Most real classes aren't. A `CheckoutService` calls an inventory system, a payment gateway, an order database. You cannot unit-test it by calling those for real: the payment gateway charges an actual card, the database needs to be running, the network is slow and flaky, and a "test" that depends on all three passing is testing four things at once.

The fix is a **test double** — a stand-in object you give the class under test in place of its real collaborators. The double is fast, deterministic, and *controllable*: you decide what it returns and you can inspect how it was used. **Mockito** is the library that builds these doubles for you.

This submodule is the vocabulary of test doubles and the Mockito API for creating them. The deeper lesson runs underneath: the *reason* you can swap a real `PaymentGateway` for a fake one is that `CheckoutService` depends on an *interface* and receives it from outside (constructor injection) rather than calling `new PaymentGateway()` itself. Testability is a design property. Mockito doesn't grant it — it rewards code that already has it.

---

## The five test doubles

"Mock" gets used loosely for any test double. The precise vocabulary (Gerard Meszaros's, by way of Martin Fowler) is worth knowing — it sharpens *how you think* about a test, and Mockito's API maps onto it.

| Double | What it is | What you check |
|---|---|---|
| **Dummy** | An object passed only to fill a parameter slot; never actually used. | Nothing. It just needs to exist. |
| **Stub** | Returns hard-coded answers to the calls the test needs. | The *output* of the class under test. |
| **Mock** | A stub that *also* records how it was called, so the test can assert on those calls. | The *interactions* — was this called, with what, how often. |
| **Spy** | A wrapper around a *real* object: calls hit the real method unless you override that method. | A mix — partial real behavior, partial control. |
| **Fake** | A real, working, lightweight implementation — just not production-grade. | The class under test, end to end, against believable behavior. |

The split that matters most is **stub vs. mock**, because it's the split between two *kinds of test*:

- A **stub** supports **state verification**: "given the gateway returns `APPROVED`, the service produces a `CONFIRMED` order." You assert on the *result*.
- A **mock** supports **behavior verification**: "the service *called* `gateway.charge(...)` exactly once with the right amount." You assert on the *interaction itself*.

Some things can only be checked as behavior. "Nothing was charged when inventory was short" is not visible in any return value — the *absence* of a call is the thing under test. That's a mock's job. Mockito objects can act as either; which one you're using is determined by whether you write `when(...)` (stubbing) or `verify(...)` (mocking) — often both on the same object.

A note on **fakes**, since they're underrated: an in-memory `Map`-backed `OrderRepository` is a fake, and for a repository it's often *better* than a mock. It behaves like the real thing — store something, get it back — so the test reads naturally and survives refactors. The `Repository` you built in 1.3 was, in effect, a fake. Reach for a fake when a collaborator has real *behavior* worth simulating; reach for a mock when you only care that a call *happened*.

## Getting Mockito on the classpath

Like JUnit, no build tool here — fetch jars into `lib/`. Mockito needs three (it has two runtime dependencies that aren't bundled):

- `mockito-core-5.x.x.jar` — Mockito itself
- `byte-buddy-1.x.x.jar` and `byte-buddy-agent-1.x.x.jar` — bytecode generation; how Mockito synthesizes double classes at runtime
- `objenesis-3.x.jar` — instantiates those classes without running a constructor

Optionally, `mockito-junit-jupiter-5.x.x.jar` adds the JUnit 5 integration (the `MockitoExtension` below). All are on Maven Central. Add them to the compile and run classpaths from 2.1 — the test classpath becomes:

```
out/main:out/test:lib/junit-platform-console-standalone-1.11.4.jar:lib/mockito-core-5.14.2.jar:lib/byte-buddy-1.15.10.jar:lib/byte-buddy-agent-1.15.10.jar:lib/objenesis-3.4.jar
```

(Versions are illustrative — any recent Mockito 5 release works. A real build tool resolves this transitive set for you; doing it by hand once shows you what "add a dependency" actually involves.)

One thing worth knowing up front: **Mockito 5 made the *inline* mock maker the default.** In Mockito 1–4 you needed extra configuration to mock `final` classes or `static` methods. In Mockito 5 it works out of the box. We'll use that at the end — but the fact that it *used to be hard* is a hint about how often you should be doing it.

## Creating mocks

Two ways. Programmatic:

```java
PaymentGateway gateway = Mockito.mock(PaymentGateway.class);
```

`Mockito.mock` returns an object that *is a* `PaymentGateway` (implements the interface, or subclasses the class) but whose methods do nothing real. Out of the box, every method returns a **default value** — `null` for objects, `0` for numbers, `false` for booleans, an empty collection for `List`/`Set`/`Map`. It does not call any real code. You then *stub* the calls you care about.

The annotation style, cleaner when there are several mocks, uses the JUnit 5 extension:

```java
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
class CheckoutServiceTest {

    @Mock InventoryClient inventory;
    @Mock PaymentGateway gateway;
    @Mock OrderRepository orders;

    CheckoutService service;

    @BeforeEach
    void setUp() {
        service = new CheckoutService(inventory, gateway, orders);
    }
}
```

`@ExtendWith(MockitoExtension.class)` is the hook (a *JUnit extension* — Module 8 explains the machinery; for now it's "the thing that processes `@Mock`"). Before each test it creates a fresh mock for every `@Mock` field. "Fresh" is the same discipline as 2.1's per-method instances: every test starts with mocks that have no stubbing and no recorded calls. Stubbing or interactions never leak between tests.

`@BeforeEach` then assembles the real `CheckoutService`, handing it the three mocks through its constructor. This is the payoff of constructor injection: the service *cannot tell* it received mocks. From its perspective it has an `InventoryClient`, a `PaymentGateway`, an `OrderRepository` — that they're hollow doubles is invisible. A class that did `new PaymentGateway()` internally would give you no seam to do this.

## Stubbing: `when(...).thenReturn(...)`

An unstubbed mock returns defaults. **Stubbing** programs specific answers:

```java
when(inventory.quantityOf("SKU-1")).thenReturn(10);
```

Read it literally: "*when* `inventory.quantityOf("SKU-1")` is called, *then return* `10`." After this line, that call yields `10`; any *other* argument still yields the default `0`.

Variations:

```java
// Throw instead of returning — exercise the failure path
when(gateway.charge(any())).thenThrow(new GatewayTimeoutException());

// Different answers on consecutive calls — 1st call 5, every call after 0
when(inventory.quantityOf("SKU-1")).thenReturn(5).thenReturn(0);

// Compute the answer from the actual arguments
when(inventory.quantityOf(anyString()))
    .thenAnswer(call -> call.getArgument(0, String.class).length());
```

For a `void` method you can't write `when(mock.doThing())` — there's no return value to start the chain. Use the `do*` family, where the stub comes first:

```java
doThrow(new IllegalStateException()).when(orders).save(any());
doNothing().when(orders).save(any());   // the default anyway, but explicit
```

Two rules that prevent confusion:

- **`when(...)` does not call the real method.** Even on a spy, `when(spy.foo())` *invokes* `foo()` to figure out what you're stubbing — a footgun covered in the spy section. On a plain mock there's no real method to run, so it's harmless, but the `do*` form (`doReturn(x).when(mock).foo()`) never invokes anything and is the safe default when in doubt.
- **Stub only what the test needs.** Don't pre-stub every method "just in case." An unused stub is dead weight and, with the strict default below, an outright error.

### Strict stubbing

`MockitoExtension` runs in **strict** mode by default, and this is a feature. If you stub a call the test never makes, it fails with `UnnecessaryStubbingException`. If you stub `quantityOf("SKU-1")` and the code actually asks for `"SKU-2"`, you hear about it immediately instead of debugging a mysterious `0`. Strictness keeps stubs honest — treat the exception as the tool catching a real mismatch, not as noise to silence.

## Verification: `verify(...)`

Stubbing controls *inputs* to the class under test. **Verification** asserts on its *outputs to collaborators* — the calls it made.

```java
verify(gateway).charge(new Money("19.99"));
```

"Assert that `gateway.charge` was called exactly once with a `Money` equal to `19.99`." If it was never called, called twice, or called with a different amount, the test fails. Count and frequency:

```java
verify(orders, times(2)).save(any());      // exactly twice
verify(gateway, never()).charge(any());    // never — the "nothing was charged" test
verify(inventory, atLeastOnce()).quantityOf(any());
verify(orders, atMost(3)).save(any());
```

`never()` is doing real work, not just being tidy. "When inventory is short, the card is never charged" is a *correctness requirement* with no footprint in any return value. The only way to test it is to assert the call's *absence* — exactly what `verify(gateway, never()).charge(any())` does.

Whole-mock checks:

```java
verifyNoInteractions(gateway);          // this mock was never touched at all
verifyNoMoreInteractions(orders);       // every call on it has been verify()'d
```

Use `verifyNoMoreInteractions` sparingly — it makes the test fail when *any* new call appears, including harmless ones, so it tends to be brittle. `verifyNoInteractions` on a mock that genuinely should stay untouched is safer and reads as a clear statement of intent.

### Order

When sequence matters — charge *before* save, never the reverse — `InOrder`:

```java
InOrder inOrder = inOrder(gateway, orders);
inOrder.verify(gateway).charge(any());
inOrder.verify(orders).save(any());
```

Don't reach for it reflexively. Assert order only when order is part of the contract; otherwise you're testing implementation detail and the test breaks on a harmless reordering.

### Don't verify what a state check already covers

If you've asserted the *result* — the service returned a `CONFIRMED` order — you usually don't *also* need to verify the calls that produced it. Verifying everything re-encodes the implementation step by step into the test; the test then breaks on every refactor even when behavior is unchanged. Prefer state verification (assert the result); use behavior verification for what state can't see — `never()`, fire-and-forget `void` calls, ordering.

## Argument matchers

`verify(gateway).charge(new Money("19.99"))` matches by `equals`. Sometimes you can't or don't want an exact value — you want "any `Money`," or "any non-null string." That's a **matcher**:

```java
verify(gateway).charge(any(Money.class));
verify(orders).save(argThat(o -> o.total().compareTo(ZERO) > 0));
when(inventory.quantityOf(anyString())).thenReturn(0);
```

Common ones: `any()`, `any(Type.class)`, `anyString()`, `anyInt()`, `eq(value)`, `isNull()`, `argThat(predicate)`.

**The one rule that trips up everyone:** in a single call, *either every argument is a matcher, or none is*. You cannot mix a raw value with a matcher.

```java
// BROKEN — "SKU-1" is raw, eq(...) elsewhere would be a matcher
verify(inventory).reserve("SKU-1", anyInt());

// FIXED — wrap the literal in eq() so both arguments are matchers
verify(inventory).reserve(eq("SKU-1"), anyInt());
```

The reason is mechanical, and knowing it makes the rule stick. Matchers don't *return* a special "matcher object" — `anyInt()` returns a plain `0` and registers the matcher on a hidden stack as a side effect. Mockito then expects either zero registrations (compare all args by `equals`) or exactly one per argument. A literal registers nothing, so mixing leaves the stack count wrong and you get a confusing `InvalidUseOfMatchersException`, often blamed on the *next* line. Symptom: any "invalid use of matchers" error → look for a raw value sitting next to a matcher.

## Argument captors

A matcher answers "*was* it called with something acceptable?" An **`ArgumentCaptor`** answers "*what exactly* was it called with?" — it grabs the actual argument so you can run full assertions on it afterward.

```java
@Captor ArgumentCaptor<Order> orderCaptor;   // or ArgumentCaptor.forClass(Order.class)

@Test
void savesOrderWithCorrectTotal() {
    // ... arrange and run the service ...

    verify(orders).save(orderCaptor.capture());

    Order saved = orderCaptor.getValue();
    assertEquals(new Money("19.99"), saved.total());
    assertEquals(Status.CONFIRMED, saved.status());
}
```

`capture()` stands in for the argument inside `verify`; afterward `getValue()` hands you the object that was actually passed (`getAllValues()` for multiple calls). This shines when the class under test *constructs* the collaborator's argument internally — you never had a reference to that `Order`, so the captor is your only way to inspect it.

Captor vs. `argThat`: a complex `argThat` predicate that fails tells you only "no call matched" — it can't show you what *was* passed. A captor lets you assert field by field with normal `assertEquals`, so the failure says exactly which field was wrong. Prefer the captor when you're checking several properties of one captured argument.

## Spies — partial mocks

A **spy** wraps a *real* object. Calls run the real method *unless* you've stubbed that specific one:

```java
List<String> realList = new ArrayList<>();
List<String> spy = Mockito.spy(realList);

spy.add("a");                     // real — actually adds
assertEquals(1, spy.size());      // real — actually 1

when(spy.size()).thenReturn(99);  // now size() is stubbed
assertEquals(99, spy.size());     // stubbed
```

The gotcha — and it's a sharp one. `when(spy.size())` evaluates `spy.size()` *for real* before stubbing takes effect. Harmless for `size()`. Not harmless when the real method has side effects or throws on an unprepared object — `when(spy.dangerous())` runs `dangerous()` for real, and a real exception escapes before you ever stub it. For spies, use the inverted `do*` form, which never invokes the real method:

```java
doReturn(99).when(spy).size();    // safe — size() is not called here
```

Beyond the syntax trap, **be wary of spies as a design signal.** Reaching for a spy usually means you want to test one method of a class while faking out *another method of the same class*. That's often the class telling you it does two jobs and wants to be two classes — the second extracted as a real collaborator you can mock cleanly. Spies have legitimate uses (wrapping a third-party class you can't restructure), but a spy on your *own* code is worth a second look before you accept it.

## Mocking statics and finals

Mockito 5's inline mock maker can mock `static` methods and `final` classes. The mechanism, scoped to a try-with-resources block so the override is undone after:

```java
try (MockedStatic<Instant> clock = Mockito.mockStatic(Instant.class)) {
    clock.when(Instant::now).thenReturn(Instant.parse("2026-01-01T00:00:00Z"));
    // inside this block, Instant.now() returns the fixed value
}
```

Read this as a capability you should rarely use. The reason it sits behind a try-with-resources and *used to require special configuration* is a deliberate nudge: **needing to mock a static is usually a design smell.** A class that calls `Instant.now()` directly has a hidden, unswappable dependency on the system clock. The clean fix isn't `mockStatic` — it's to inject a `Clock` (`java.time.Clock`, built for exactly this) and pass a fixed one in the test. Same for `final`: if you must mock a `final` class you don't own, the better seam is usually a thin interface of your own that wraps it.

Legitimate uses exist — pinning time in a hot path you can't restructure, a `static` factory in third-party code. But treat `mockStatic` / mocking `final` as evidence first: *can the design change so I don't need this?* Reach for it only when the honest answer is no.

---

## When *not* to mock

A double is a *model* of the real thing, and a wrong model gives you a green test over broken code. Guard against that:

- **Don't mock types you don't own.** Mocking `HttpClient` or a JDBC `Connection` bakes *your assumption* of how it behaves into the test. If the real library behaves differently, your test passes and production fails — the worst outcome. Wrap third-party types in a thin interface of your own and mock *that*; the interface is also where you'd write a focused integration test against the real thing.
- **Don't mock value objects.** `BankAccount`, `Money`, an `Order` record — just *construct* them. They have no I/O, no slowness, nothing to isolate. A mocked `Money` is harder to read and less truthful than `new Money("19.99")`.
- **Don't mock the class under test.** If you're testing `CheckoutService`, `CheckoutService` is real. You mock its *collaborators*, never itself. (That confusion is part of why a spy on your own code deserves scrutiny.)
- **Prefer a fake when behavior matters.** For a repository, an in-memory `Map`-backed fake usually beats a mock: it actually stores and returns, so the test reads naturally and survives refactors.
- **Over-mocking produces tests that only test the mocks.** If a test stubs eight calls and verifies six, it has re-specified the implementation line by line. It will fail on every refactor and catch almost no real bug. When a test needs that many doubles, the class under test probably has too many collaborators — the test is reporting a design problem.

The throughline: mocks isolate a class from things that are *slow, non-deterministic, or have real side effects*. Anything else, use the real object. Every mock is a small lie you've decided to tell the test; keep the lies few and keep them honest.

## DIY Exercise

Test a `CheckoutService` with three collaborators. Use the 2.1 layout (`src/main/java`, `src/test/java`) plus the Mockito jars on the test classpath.

Define these interfaces and the service in `src/main/java`:

- `InventoryClient` — `int quantityOf(String sku)` and `void reserve(String sku, int quantity)`
- `PaymentGateway` — `PaymentResult charge(Money amount)` (have `charge` able to throw a `GatewayException`)
- `OrderRepository` — `void save(Order order)` and `Optional<Order> findById(String id)`
- `CheckoutService` — constructor takes all three; a `checkout(Cart cart)` method that: checks inventory for every line, **charges only if every item is in stock**, reserves the stock, saves a `CONFIRMED` order on success, and on insufficient stock returns/throws *without charging or saving*.

Then write `CheckoutServiceTest` with `@ExtendWith(MockitoExtension.class)` and the three collaborators as `@Mock` fields:

1. **Happy path.** Stub inventory so every item is in stock and the gateway so `charge` returns success. Call `checkout`. Verify `charge` was called once with the correct total, `reserve` was called for each line, and `save` was called once. Use an `ArgumentCaptor<Order>` to assert the saved order's total and that its status is `CONFIRMED`.
2. **Insufficient stock.** Stub inventory so one item is short. Call `checkout`. Assert the outcome (your chosen exception or result), and — the point of the exercise — `verify(gateway, never()).charge(any())` and `verify(orders, never()).save(any())`. Nothing charged, nothing saved.
3. **Gateway failure.** Everything in stock, but stub `charge` to throw `GatewayException`. Assert the service surfaces the failure and that **no order is saved** — a charge that failed must not leave a `CONFIRMED` order behind.
4. **Argument matchers.** Somewhere above you'll verify a call that mixes a specific SKU with a "don't care" quantity. Write it wrong first (raw literal beside a matcher), read the `InvalidUseOfMatchersException`, then fix it with `eq(...)`.

Things to think about:

- For each of the three collaborators, decide: stub, mock, or could it be a *fake*? Which would you genuinely rather replace `OrderRepository` with — a Mockito mock, or a `Map`-backed fake — and what does each choice cost you?
- Test 2's core assertions are two `never()` calls. There is no return value that proves "nothing was charged." Sit with why this *must* be behavior verification — it's the cleanest example of why mocks exist at all.
- You injected all three collaborators through the constructor. Suppose `CheckoutService` instead did `new StripePaymentGateway()` inside `checkout`. Walk through exactly where this test becomes impossible to write. That walk-through *is* the argument for dependency injection.
- You're tempted to also `mock(Money.class)` or `mock(Order.class)`. Don't — explain to yourself why constructing them real is both easier and more truthful here.
- If `checkout` had a bug where it reserved stock *before* confirming payment, which test catches it? If none does, what verification (hint: `InOrder`) would you add — and is that ordering a real contract or just current implementation?

This closes Module 2. You can now write a self-contained unit test (2.1) and isolate a class from its collaborators (2.2). From Module 3 on, every DIY ships with a `src/test/` tree — the exercises stop saying "test it" because testing is now just how you work.
